<h1 data-marxy-s="0" data-marxy-e="76">Export drops the last row when the batch size divides the row count (#412)</h1>
<p data-marxy-s="78" data-marxy-e="223"><strong data-marxy-s="78" data-marxy-e="87">Issue</strong> opened by <strong data-marxy-s="98" data-marxy-e="113">@mira-quill</strong> on 2026-09-28 · labels: <code data-marxy-s="139" data-marxy-e="144">bug</code>, <code data-marxy-s="146" data-marxy-e="154">export</code>, <code data-marxy-s="156" data-marxy-e="170">needs-triage</code> · milestone: <code data-marxy-s="185" data-marxy-e="193">v2.7.0</code> · assignee: <strong data-marxy-s="207" data-marxy-e="223">@tobias-reen</strong></p>
<h3 id="description" data-marxy-s="225" data-marxy-e="240">Description</h3>
<p data-marxy-s="242" data-marxy-e="584">When I run <code data-marxy-s="253" data-marxy-e="288">ledgerctl export --batch-size 500</code> on a table with exactly 1,500 rows, the output file has 1,499 data rows. The same command with <code data-marxy-s="384" data-marxy-e="402">--batch-size 499</code> or <code data-marxy-s="406" data-marxy-e="424">--batch-size 501</code> returns all 1,500. It looks like an off-by-one at the batch boundary, but I could not find it by reading <code data-marxy-s="530" data-marxy-e="542">batcher.go</code>, so I am filing this instead of guessing.</p>
<p data-marxy-s="586" data-marxy-e="752">This is a regression: <code data-marxy-s="608" data-marxy-e="616">v2.5.3</code> does not do it. I bisected to the range <code data-marxy-s="657" data-marxy-e="675">a41c9e2..3f8d07b</code> and stopped there because the range includes the batching rewrite from #377.</p>
<h3 id="steps-to-reproduce" data-marxy-s="754" data-marxy-e="776">Steps to reproduce</h3>
<ol data-marxy-s="778" data-marxy-e="1176">
<li data-marxy-s="778" data-marxy-e="889"><p data-marxy-s="781" data-marxy-e="820">Create a table with exactly 1,500 rows:</p>
<pre class="language-sh" data-marxy-s="825" data-marxy-e="889"><code class="language-sh" data-marxy-s="831" data-marxy-e="883">ledgerctl seed --rows 1500 --table demo_invoices
</code></pre></li>
<li data-marxy-s="891" data-marxy-e="1037"><p data-marxy-s="894" data-marxy-e="946">Export with a batch size that divides the row count:</p>
<pre class="language-sh" data-marxy-s="951" data-marxy-e="1037"><code class="language-sh" data-marxy-s="957" data-marxy-e="1031">ledgerctl export --table demo_invoices --batch-size 500 --out demo.csv

<pre class="language-sh" data-marxy-s="1096" data-marxy-e="1139"><code class="language-sh" data-marxy-s="1102" data-marxy-e="1133">tail -n +2 demo.csv | wc -l

</ol>
<h3 id="expected-behaviour" data-marxy-s="1178" data-marxy-e="1200">Expected behaviour</h3>
<p data-marxy-s="1202" data-marxy-e="1261">Every row is written exactly once, whatever the batch size.</p>

<h2 data-marxy-s="5347" data-marxy-e="5421">Pull request #415: Advance the export cursor after the batch is flushed</h2>
<p data-marxy-s="5423" data-marxy-e="5542"><strong data-marxy-s="5423" data-marxy-e="5439">@tobias-reen</strong> opened this pull request on 2026-09-30 · base: <code data-marxy-s="5488" data-marxy-e="5494">main</code> ← head: <code data-marxy-s="5505" data-marxy-e="5528">fix/412-export-cursor</code> · fixes #412</p>
<h3 id="what-this-changes" data-marxy-s="5544" data-marxy-e="5565">What this changes</h3>
<p data-marxy-s="5567" data-marxy-e="5803">The keyset cursor in <code data-marxy-s="5588" data-marxy-e="5600">batcher.go</code> was updated when a row was read, not when it was written. When a batch ended exactly at the flush boundary, the next query started one row too late. The cursor now advances only after <code data-marxy-s="5785" data-marxy-e="5794">flush()</code> returns.</p>
