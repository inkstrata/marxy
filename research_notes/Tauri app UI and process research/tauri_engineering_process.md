# Tauri / Small Cross-Platform Desktop App Engineering Process

## How do real Tauri OSS projects structure CI to keep pipelines fast while gating merges on correctness?

### Takeaway
Tauri's own ecosystem leans on two off-the-shelf actions — `Swatinem/rust-cache` (or `mozilla-actions/sccache-action`) for compiler caching and matrix-based clippy/lint jobs split by crate/feature — to keep Rust CI fast, while `tauri-action` is treated as a separate "does it still build on 3 OSes" gate rather than the primary correctness check. Verified, sourced detail on other named Tauri apps' (Spacedrive, Rustdesk, Pake, Tabby) exact workflow YAML was not obtainable through search in this pass — see Gaps.

### Cited Findings
- The official `tauri-plugin-store`/`tauri-plugin-process`/`plugins-workspace` repos run a dedicated `lint-rust.yml` workflow using a matrix strategy that runs `cargo clippy --package ${{ matrix.package }} --all-targets --all-features -- -D warnings` per package, rather than one monolithic clippy invocation — [tauri-apps/plugins-workspace lint-rust.yml](https://github.com/tauri-apps/plugins-workspace/blob/v2/.github/workflows/lint-rust.yml)
- The main `tauri-apps/tauri` repo's clippy job is matrix-driven with per-crate manifest paths and per-crate extra args (e.g. `--manifest-path ./core/tauri/Cargo.toml --all-targets ${{ matrix.clippy.args }}`), and a helper script runs clippy/test separately for crates (like `tauri` itself) that have mutually exclusive Cargo features, since running them together would mask feature-gated bugs — [tauri-apps/tauri PR #874](https://github.com/tauri-apps/tauri/pull/874)
- `tauri-action` (the official GitHub Action for building/releasing Tauri apps) has three distinct uses: (1) just testing that the build pipeline succeeds, (2) uploading artifacts to an existing release, (3) creating a new release — teams commonly use mode (1) as a "does it build on macOS/Windows/Linux" PR gate separate from unit-test CI — [tauri-apps/tauri-action](https://github.com/tauri-apps/tauri-action), [Tauri GitHub Actions docs](https://v2.tauri.app/distribute/pipelines/github/)
- `Swatinem/rust-cache` is a drop-in GitHub Action that automatically handles cache keys, paths (registry, git checkouts, build output) and restoration/eviction logic for Rust/Cargo projects, requiring near-zero configuration versus hand-rolling `actions/cache` — [Swatinem/rust-cache](https://github.com/Swatinem/rust-cache)
- `sccache` (via `mozilla-actions/sccache-action`) wraps `rustc` as a compiler-level cache rather than caching whole target directories, and can start compiling immediately while fetching only the objects needed for the current build (vs. cargo waiting on a full cache blob) — setup requires only two env vars, `RUSTC_WRAPPER=sccache` and `SCCACHE_GHA_ENABLED=true` — [Depot.dev: Fast Rust Builds with sccache](https://depot.dev/blog/sccache-in-github-actions)
- Passing `--locked` to `cargo build`/`test`/`check` in CI prevents Cargo from silently updating `Cargo.lock`, saving dependency-resolution time and guaranteeing CI tests exactly the locked dependency graph — [corrode.dev: Tips for Faster Rust CI Builds](https://corrode.dev/blog/tips-for-faster-ci-builds/)
- An uncached, fresh `create-tauri-app` build takes roughly 1 hour, which is the kind of number that makes caching strategy (sccache/rust-cache) a first-order CI concern for Tauri projects specifically, not just a general Rust nicety — [DEV Community: Ship Your Tauri v2 App Like a Pro](https://dev.to/tomtomdu73/ship-your-tauri-v2-app-like-a-pro-github-actions-and-release-automation-part-22-2ef7)

### Inferences
- The pattern across Tauri's own repos is to decompose one big "CI" job into narrow, parallel matrix jobs (per-crate clippy, per-feature-set test runs) so a failure pinpoints the exact crate/feature combination, and so unrelated crates' jobs can finish and report green independently rather than all waiting on the slowest one.
- Treating `tauri-action`'s build-only mode as a distinct, cheaper gate from full test/lint suggests small teams intentionally decouple "does the app still compile as a native bundle on 3 OSes" from "is the code correct," since the former is much slower (full native builds) and less frequently the actual failure mode.

### Gaps
- Could not verify specific `.github/workflows/*.yml` file contents for Spacedrive, Rustdesk, Pake, or Tabby in this pass — searches returned repository/directory pointers (e.g. Spacedrive's `release.yml`, `cache-factory.yaml`) but WebFetch was not used to pull their raw YAML, so no directly cited configuration detail from those specific projects is included here. A follow-up pass should `gh api`/fetch raw YAML from `spacedriveapp/spacedrive/.github/workflows/`, `rustdesk/rustdesk/.github/workflows/`, `tw93/Pake/.github/workflows/`, and `TabbyML/tabby/.github/workflows/` (confirming each still uses Tauri via `tauri.conf.json`/`@tauri-apps` deps before citing).

## What visual/screenshot regression testing approaches are used for Tauri apps, and what are the known cross-platform limitations?

### Takeaway
The maintained path is WebdriverIO's `@wdio/tauri-service`, which defaults to an **embedded WebDriver server running inside the app itself** (works identically on Windows/Linux/macOS) rather than driving the OS-native WebDriver, because macOS's WKWebView has no first-party WebDriver at all; screenshot/visual-regression on top of that stack is bolted on via `@wdio/visual-service`, not something Tauri or WebdriverIO ships as a turnkey pixel-diff solution. The core cross-platform risk is real and specifically documented: Tauri renders with three different engines (WebView2/Chromium on Windows, WebKitGTK on Linux, WKWebView on macOS), so font rendering and even CSS support differ per OS, and testing against a fourth engine (Playwright's bundled Chromium) instead of the real per-OS webview is a known trap that produces false-positive/false-negative test results.

### Cited Findings
- Tauri's own docs state plainly that "macOS has no WKWebView driver tool available" for direct `tauri-driver` use, which is why WebDriver-based Tauri testing on macOS requires either an embedded/in-app driver or a third-party bridge — [Tauri WebDriver docs](https://v2.tauri.app/develop/tests/webdriver/)
- `@wdio/tauri-service` (maintained under the WebdriverIO project) defaults to running an embedded WebDriver server inside the app binary itself, which is "how macOS is supported" — no external driver process needed on any OS with this mode. It can alternatively drive the OS-native WebDriver (`tauri-driver` on Windows/Linux only) or use CrabNebula's cross-platform fork of `tauri-driver` (paid) — [WebdriverIO Tauri Service docs](https://webdriver.io/docs/wdio-tauri-service/)
- WebdriverIO ships `@wdio/visual-service` for visual regression testing, and this is explicitly documented as usable alongside the Tauri service for screenshot-diff style checks — [WebdriverIO Tauri Service docs](https://webdriver.io/docs/wdio-tauri-service/)
- A third-party/independent effort, `tauri-plugin-webdriver` (a W3C-compliant implementation), was built specifically because the author found "nothing else worked" for driving WKWebView-based Tauri apps on macOS with standard WebDriver protocol tooling (Selenium, WebdriverIO); it works by injecting a JS bridge plus an in-process HTTP server in debug builds, with a separate CLI translating WebDriver protocol calls into plugin API calls — [Daniel Raffel: I Built a WebDriver for WKWebView Tauri Apps on macOS](https://danielraffel.me/2026/02/14/i-built-a-webdriver-for-wkwebview-tauri-apps-on-macos/)
- Tauri deliberately uses three different rendering engines per OS — WebView2 (Chromium) on Windows, WebKitGTK on Linux, WKWebView on macOS — and CSS that renders correctly on Windows can visibly break on Linux because "WebKitGTK renders fonts differently and is behind on CSS prefixes" — [DEV Community: Cross-Platform Desktop Wars: Electron vs Tauri](https://dev.to/nikolas_dimitroulakis_d23/cross-platform-desktop-wars-electron-vs-tauri-how-do-you-explain-the-tradeoffs-to-users-2948)
- A documented pitfall: running a Playwright test suite against a Tauri frontend tests it in Playwright's bundled Chromium, which can pass even though the actual shipped app (WKWebView on macOS, WebKitGTK on Linux) fails or renders differently — the suite is testing a fourth, non-representative engine. Note: this claim comes from an independent personal project wiki ("zudo-tauri-wisdom"), not an official or widely-cited source, so treat it as directionally useful but not authoritative — [zudo-tauri-wisdom: Playwright Testing Engine Mismatch](https://zudo-tauri-wisdom.takazudomodular.com/) (original path redirected; page not independently re-verified beyond the search snippet)
- WebdriverIO's Tauri service also offers a "browser mode" that runs the Tauri frontend in plain Chrome against a Vite dev server with no Tauri binary or driver at all, explicitly for fast renderer-only tests — implying the WebdriverIO project itself distinguishes fast/approximate (Chrome) tests from slow/accurate (real per-OS webview) tests rather than treating them as interchangeable — [WebdriverIO Tauri Service docs](https://webdriver.io/docs/wdio-tauri-service/)

### Inferences
- For a project like Marxy that already screenshot-diffs per rendering engine, the WKWebView WebDriver gap means macOS visual-regression coverage either needs the embedded-WebDriver approach (`@wdio/tauri-service` default mode) or accepting that macOS screenshots are captured via a different mechanism (e.g., driving the compiled app directly and screenshotting the window, not through the browser-automation protocol) — a pure Playwright-against-Chromium proxy is a known false-confidence trap and should not stand in for a real per-OS render check.
- Since font rendering genuinely differs by OS/engine, per-engine screenshot baselines (which Marxy already has) are the correct mitigation Tauri-testing writers converge on — the alternative (one shared baseline diffed loosely) is what breaks.

### Gaps
- No source found that describes a specific, named small Tauri OSS project's actual production screenshot-diff pipeline (tool + threshold + CI wiring) end to end — all sources are either Tauri/WebdriverIO's own docs or one-off blog posts about building testing tooling, not a working example lifted from a real shipping app's CI logs.
- Could not verify GPU-driver-related flakiness in headless CI runners for Tauri screenshot tests specifically (a commonly assumed but not directly confirmed risk here).

## What bundle-size tracking or performance-budget tooling do small Rust/Tauri projects use, and do any gate merges on perf numbers?

### Takeaway
The available tooling (`cargo-bloat` GitHub Actions, e.g. `orf/cargo-bloat-action`) is explicitly informational — it posts a PR comment with binary-size breakdown and dependency-tree diffs but does **not** fail the build on regression; no evidence was found of any real Tauri/Rust OSS project hard-gating a merge on a bundle-size or perf number, which matches Marxy's own current stance (measured, not gated).

### Cited Findings
- `orf/cargo-bloat-action` runs `cargo-bloat` + `cargo-tree` on every PR and posts a comment with total size, per-crate size deltas, and dependency-tree changes, but does not fail/block the workflow based on the numbers — it is a reporting tool, gated only by requiring a `GITHUB_TOKEN` for commenting — [orf/cargo-bloat-action](https://github.com/orf/cargo-bloat-action)
- A parallel project, `Reloaded-Project/devops-cargo-bloat-action`, aims to "track rust binary sizes across builds using GitHub Actions" but is explicitly marked "[WIP. Not yet working]" as of the indexed snapshot, underscoring that this space is immature/DIY even among people actively trying to build it — [Reloaded-Project/devops-cargo-bloat-action](https://github.com/Reloaded-Project/devops-cargo-bloat-action)
- One example (Refract-Protocol, a Wasm/contracts project, not confirmed Tauri) explicitly added "a wasm binary size regression gate to CI with per-contract budgets" so a dependency bump or refactor "can't silently inflate deployment cost," and notes sizes must be compared against a build from the same pinned toolchain since size varies by toolchain version — included as a general pattern, not a verified Tauri example — [Refract-Protocol/refract-contracts Issue #63](https://github.com/Refract-Protocol/refract-contracts/issues/63)
- No official Tauri documentation or `tauri-action` feature was found for automated bundle-size comparison across builds; the project's own action outputs bundle paths (`src-tauri/target/release/bundle`) but leaves size tracking to the consumer to implement — [tauri-action README via search summary](https://github.com/tauri-apps/tauri-action)

### Inferences
- Given that even the dedicated size-tracking action ecosystem is either purely advisory (`cargo-bloat-action`) or unfinished (`devops-cargo-bloat-action`), a small team gating hard on bundle size in CI would likely have to hand-roll the comparison-and-fail logic themselves; this is consistent with, and arguably validates, Marxy's current choice to measure-but-not-gate performance/bundle-size numbers rather than adopt a fragile home-grown gate.

### Gaps
- No verified example of any real Tauri app hard-failing CI on a bundle-size or startup-time regression was found. This may mean it's genuinely rare in this ecosystem, or that such gates exist but weren't surfaced by search — treat "nobody gates on this" as the current evidence, not a certainty.

## What contributor workflow patterns (branching, PR templates, squash-merge, changelog automation, conventional commits) do well-run small Tauri/Rust OSS projects use?

### Takeaway
Tauri's own release tooling is built around Conventional Commits driving automated changelog generation (scoped commits like `feat(ui): ...` become changelog entries), and the wider Node/Rust OSS ecosystem pairs this with Changesets-style tooling for versioning — but this pass could not pull a verified, named small Tauri app's actual `CONTRIBUTING.md`/PR-template/branch-naming rules, so specifics beyond the commit-message convention are thin.

### Cited Findings
- Tauri's release workflows parse git history using Conventional Commits, and scoped commit messages such as `feat(ui): add dark mode` are transformed into formatted changelog entries for the next version — [search-derived summary citing Tauri release workflow behavior; no single primary doc URL was fetched directly for this claim, so confidence is moderate]
- Changesets (the JS/TS-ecosystem tool for versioning + changelog generation from per-PR "changeset" files) is commonly recommended for use with CI so that versioning/publishing is automated, and third-party tooling exists (`iamchathu/changeset-conventional-commits`) specifically to auto-generate Changesets entries from Conventional Commit messages, indicating these two conventions (Conventional Commits + Changesets) are frequently combined in adjacent OSS ecosystems rather than treated as redundant — [iamchathu/changeset-conventional-commits](https://github.com/iamchathu/changeset-conventional-commits)

### Inferences
- Marxy's existing convention (Conventional Commits with a Jira key in the subject, squash-merge, PR-body as durable record) is directionally aligned with what Tauri's own release automation expects from commit history, which suggests no change is needed there — the main open question is changelog automation, where Marxy currently requires a manual `CHANGELOG.md` line rather than deriving it from commit messages.

## Are there known pitfalls specific to Tauri CI (cross-compiling, code-signing, WebView differences causing flaky tests)?

### Takeaway
The best-documented pitfalls are on the macOS code-signing/notarization side (slow and sometimes-stuck notarization, silent breakage on certificate expiry, entitlements misconfiguration crashing the WebView) and on the WebView-engine side (three different rendering engines per OS causing real visual and CSS differences, plus the WKWebView WebDriver gap already covered above); cross-compiling specifics (e.g., Linux→Windows/macOS cross-builds vs. native runners per OS) were not deeply covered by available sources in this pass.

### Cited Findings
- Apple notarization "usually takes 2-5 minutes but sometimes takes 15-20 minutes"; `tauri-action` polls automatically but a CI workflow should still set a reasonable timeout to avoid silent hangs — [DEV Community / blog synthesis on Tauri v2 GitHub Actions](https://dev.to/tomtomdu73/ship-your-tauri-v2-app-like-a-pro-github-actions-and-release-automation-part-22-2ef7)
- There is a documented case of a Tauri macOS build getting "stuck at notarizing... for more than an hour" — [tauri-apps/tauri Discussion #8630](https://github.com/orgs/tauri-apps/discussions/8630)
- Apple Developer ID signing certificates are valid for 5 years; if one expires, "your CI pipeline breaks silently and you ship unsigned builds" — a pitfall specifically because the failure is silent rather than a loud CI red — [search-derived summary; primary source not independently re-fetched, moderate confidence]
- Entitlements misconfiguration is called out as a common cause of a signed/notarized Tauri app crashing immediately on launch even though the unsigned build works fine, because "Tauri's WebView needs JIT and unsigned executable memory permissions" — [search-derived summary; same source cluster as above, moderate confidence]
- Required GitHub Actions secrets for Tauri macOS signing/notarization include `APPLE_SIGNING_IDENTITY`, `APPLE_CERTIFICATE` (base64 `.p12`), `APPLE_CERTIFICATE_PASSWORD`, `APPLE_ID`, `APPLE_PASSWORD`, and `APPLE_TEAM_ID` — [Tauri macOS Code Signing docs](https://v2.tauri.app/distribute/sign/macos/)
- A free (non-paid) Apple Developer account cannot notarize a Tauri app at all — the app will always show as "not verified" — a pitfall for small/indie teams who assume any Apple Developer account is sufficient — [search-derived summary of Tauri macOS signing guidance; moderate confidence, not independently re-fetched from primary doc]
- Tauri uses three separate rendering engines by OS (WebView2/Chromium on Windows, WebKitGTK on Linux, WKWebView on macOS), which is the root cause of both the visual-regression baseline problem (above) and general CSS/font inconsistency bugs reported by developers — [DEV Community: Cross-Platform Desktop Wars](https://dev.to/nikolas_dimitroulakis_d23/cross-platform-desktop-wars-electron-vs-tauri-how-do-you-explain-the-tradeoffs-to-users-2948)

### Inferences
- Because notarization is slow, occasionally hangs, and fails silently on cert expiry, a CI/release pipeline gate should treat macOS signing/notarization as a separate, explicitly-timed step with alerting on failure — not something folded silently into a generic "build" job where a hang or a silent unsigned fallback could go unnoticed.

### Gaps
- Several of the code-signing claims above trace back to secondary blog-post synthesis rather than a primary Apple or Tauri source fetched directly in this pass (search tool summarized rather than quoting a specific doc); a follow-up should WebFetch `https://v2.tauri.app/distribute/sign/macos/` directly to firm up citations before treating certificate-expiry and entitlements claims as fully verified.
- No sourced detail found in this pass on Linux cross-compilation pitfalls (e.g., building Windows/macOS targets from a single Linux runner vs. using native per-OS runners) or on Windows code-signing (EV certificate / HSM requirements) — both are plausible pitfall areas for Tauri CI but were outside what search surfaced given the query budget.
