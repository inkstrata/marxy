# Typographic craft in desktop reading/writing apps

## Which desktop apps are known for exceptional reading typography, and what techniques do they use? (Tauri vs Electron vs native)

### Takeaway
None of the well-known "great typography" writing apps (iA Writer, Ulysses, Bear, Typora) are Tauri-based — iA Writer and Ulysses are native (Cocoa/AppKit + UIKit, platform text engines), Bear is native Apple-platform, and Typora has moved *away* from Electron toward native WebKit on macOS while still using Electron/Chromium on Windows/Linux. This means their headline technique — custom **variable/duospaced typefaces** designed specifically for on-screen writing — is a font-level solution that transfers directly to a DOM-based renderer like Marxy's, but their layout engines (native text kit / WebKit) do not.

### Cited Findings
- iA Writer ships **iA Writer Duo**, a "duospaced" font built on IBM Plex where only `w`, `W`, `m`, `M` (and similar wide glyphs) get ~50% extra advance width, keeping the monospace "draft" scanning quality while avoiding squished wide letterforms — a compromise between fully monospaced and fully proportional fonts. — [iA: From Monospace to Duospace](https://ia.net/topics/in-search-of-the-perfect-writing-font)
- iA also produces other custom writing faces and discusses them as a deliberate, ongoing typography R&D effort (a "typographic Christmas" post cataloguing multiple in-house fonts). — [iA: A Typographic Christmas](https://ia.net/topics/a-typographic-christmas)
- The iA Writer Duo family is distributed as free/open fonts on GitHub. — [github.com/iaolo/iA-Fonts](https://github.com/iaolo/iA-Fonts)
- iA Writer is a native app (Wikipedia describes platform-native builds for macOS/iOS); no Tauri or Electron involvement is documented in any source found. — [Wikipedia: iA Writer](https://en.wikipedia.org/wiki/IA_Writer)
- Bear 2.0 introduced **Bear Sans**, a custom typeface commissioned from Brandon Knap's Clarika, "combining geometric and grotesque flavors" and tuned specifically for on-screen reading/writing legibility rather than adapted from a print face. — [Bear blog: Meet Bear Sans](https://blog.bear.app/2023/08/learn-about-our-new-custom-font-bear-sans/)
- Bear is a native Apple-ecosystem app (Mac/iPad/iPhone/Watch); no Electron or Tauri stack is used. — [Bear blog](https://blog.bear.app/)
- Ulysses exposes typography as user-facing controls — line height, paragraph spacing, first-line indent, and (since v25) third-party font support via system font-management apps — rather than publishing engineering detail on a custom layout algorithm. — [Ulysses: Customize the Editor](https://help.ulysses.app/dive-into-editing/editor-customization-guide); [9to5Mac: Ulysses 25](https://9to5mac.com/2022/02/07/ulysses-25-writing-app-brings-third-party-font-support-for-ios-devices-visual-revamp-more/)
- Ulysses is a native macOS/iOS app (Wikipedia); no Electron/Tauri/Chromium rendering is documented.
- Typora's macOS build (1.14.x) is a Cocoa/AppKit app that renders documents in a **system WKWebView**, not Chromium — i.e., it moved off Electron on that platform, while its Windows/Linux builds still use Electron/Chromium. — [Typora GitHub issue #3960: deprecated Electron features](https://github.com/typora/typora-issues/issues/3960); [Ry Walker: Typora research notes](https://rywalker.com/research/typora)
- Because Typora on macOS renders through WKWebView (still a DOM/CSS engine, just not Chromium), its actual typesetting techniques (CSS-based, theme-driven) are more directly comparable to a DOM/canvas-based app like Marxy than iA Writer's or Bear's fully native text stacks are.

### Inferences
- The single most transferable idea from this cohort is **font design as a typography solution**: a custom or duospaced typeface (iA Duo, Bear Sans) can solve legibility/scanning problems that would otherwise require line-breaking or letter-spacing hacks. Marxy's typeset package could evaluate bundling or recommending a duospaced/optically-tuned face for its default reading theme rather than relying solely on layout-engine tricks.
- None of these apps publish algorithm-level writeups of Knuth-Plass, hanging punctuation, or baseline-grid engineering — their public "typography engineering" content is almost entirely about font selection and user-facing settings, not layout internals. This is a genuine gap in publicly available prior art from this category of app.

### Gaps
- No source found describing iA Writer's, Bear's, Ulysses's, or Typora's internal line-breaking, hyphenation, or baseline-grid implementation at a technical level — these companies do not appear to publish that detail. Treat "these apps use Knuth-Plass" or similar as unconfirmed; only font-level engineering is documented.
- Could not confirm whether Typora's Windows/Linux (Electron) build differs functionally from its macOS (WKWebView) build in typographic behavior.
- No Tauri-based markdown/reading app with documented typography engineering was found in this search pass (see next question for JS/TS layout libraries, which are stack-agnostic and would apply equally to a Tauri app).

## Are there open-source JS/TS implementations of Knuth-Plass, hanging punctuation, or baseline-grid layout for DOM contexts worth comparing against?

### Takeaway
There is a small, well-documented lineage of Knuth-Plass JS ports (bramstein/typeset → tex-linebreak → tex-linebreak2 → a newer WASM/HarfBuzz variant), all explicitly caveated as proof-of-concept or DOM-performance-limited — useful for validating Marxy's algorithm correctness but not as drop-in production dependencies. Hanging punctuation has a native CSS property with poor support and at least one modern, glyph-metric-based cross-browser polyfill worth studying directly.

### Cited Findings
- **bramstein/typeset**: "an implementation of the Knuth and Plass line breaking algorithm using JavaScript," goal "to optimally set justified text in the browser." Works by minimizing total demerits (a cost function penalizing excessive space stretch/shrink, consecutive hyphens, and large fitness-class jumps between adjacent lines) to find the globally optimal break set, rather than greedy first-fit. Uses the **Hypher** library for hyphenation. The README/author's own site describes it as "a proof of concept" and explicitly "not ready for production use." — [github.com/bramstein/typeset](https://github.com/bramstein/typeset/); [bramstein.com/working](https://www.bramstein.com/working/)
- **robertknight/tex-linebreak**: a more actively maintained JS/TS implementation of the same algorithm. Measurement is pluggable — callers supply a custom width-measurement function via `layoutItemsFromString`, so it can be adapted to any text-measurement backend (Canvas, DOM Range, custom font-metrics code). Supports hyphenation via Hypher (`createHyphenator` with language patterns). No hanging-punctuation support is documented. The maintainers explicitly warn it is **not aware of floated content** (can cause overflow) and that DOM-based justification (inserting linebreaks / wrapping text nodes to justify existing HTML) "can be slow in large documents," recommending performance testing and limiting scope. — [github.com/robertknight/tex-linebreak](https://github.com/robertknight/tex-linebreak)
- **egilll/tex-linebreak2**: a further fork/continuation, described as "a JavaScript library for breaking text into lines of optimal width" for justified text as in a newspaper, book, or paper. — [github.com/egilll/tex-linebreak2](https://github.com/egilll/tex-linebreak2)
- **currentspace/knuth-plass-wrap**: a newer (2020s-era) implementation claiming "TeX-quality Knuth-Plass line breaking for the web, powered by HarfBuzz WASM," with "HarfBuzz-accurate measurement," automatic hyphenation in 17 languages via the Rust `hypher` crate, variable-font support, and both React and vanilla JS APIs — notable because it swaps JS-approximated text measurement for actual HarfBuzz shaping via WASM, which is a materially more accurate measurement source than `canvas.measureText` or DOM-based approximation. — [github.com/currentspace/knuth-plass-wrap](https://github.com/currentspace/knuth-plass-wrap)
- Discussion of the algorithm's continued relevance/limitations appears on Hacker News ("Knuth and Plass line-breaking Revisited"), and Matthew Petroff has written on **pre-calculated line breaks** injected into HTML/CSS as an alternative strategy to runtime JS breaking (compute breaks once, e.g. at build/parse time, and ship them as explicit `<br>`/soft-break markers) — relevant prior art for Marxy's "one parse produces one AST" model, since breaks could in principle be computed once against the source map rather than recomputed on every layout pass. — [Matthew Petroff: Pre-calculated Line Breaks](https://mpetroff.net/2020/05/pre-calculated-line-breaks-for-html-css/); [HN discussion](https://news.ycombinator.com/item?id=28537923)
- **CSS `hanging-punctuation` property**: intended to let punctuation (opening quotes, commas/full stops at line end, etc.) hang outside the text box automatically, but "the property is only supported in Safari... since 2016" — no Chromium or Firefox support as of the sources found. — [Chris Coyier: The hanging-punctuation property in CSS](https://chriscoyier.net/2023/11/27/the-hanging-punctuation-property-in-css/); [CSS-Tricks Almanac: hanging-punctuation](https://css-tricks.com/almanac/properties/h/hanging-punctuation/)
- **OpticalMargin** (over-punch/Liiift-Studio, same project mirrored under two org names): a cross-browser hanging-punctuation/optical-margin-alignment library that does **not** use a lookup table — it measures each punctuation glyph's actual visual overhang via Canvas `TextMetrics.actualBoundingBoxLeft`/`actualBoundingBoxRight` (the gap between a glyph's advance width and its inked bounds), computes a per-character hang amount, clamps it via a `threshold` (minimum effective hang) and `maxHangRatio` (cap as a fraction of advance width), applies built-in default hang fractions per character class (hyphens 1.0, quotes 0.8, commas 0.6, user-overridable), and applies the result as a negative `margin-inline-start`/`margin-inline-end` on the line box. Canvas `TextMetrics` support needed for this exists in Chrome/Edge 77+, Safari 11.1+, Firefox 74+; where Canvas metrics are unavailable (e.g. SSR) it degrades safely to zero hang (flush text), so it's safe to apply unconditionally. — [github.com/over-punch/OpticalMargin](https://github.com/over-punch/OpticalMargin)
- General background: hanging punctuation is also called "exdentation" and is related to but broader than "optical margin alignment" (which also covers non-punctuation optical adjustments); Adobe InDesign's version of the same concept is literally named "Optical Margin Alignment." — [Wikipedia: Hanging punctuation](https://en.wikipedia.org/wiki/Hanging_punctuation); [Wikipedia: Optical margin alignment](https://en.wikipedia.org/wiki/Optical_margin_alignment)
- **Prince XML** (a commercial HTML/CSS-to-PDF engine, not JS but relevant prior art for a from-scratch DOM-adjacent layout engine) implements "a TeX-style algorithm for high-quality line-breaking and justification," can hyphenate the last word of a page/column when aesthetically preferable, exposes `prince-line-break-choices` (e.g. a `title` mode favoring phrasing over hyphenation density, a `heading` mode closer to body text but less hyphenation-prone) and `prince-hyphenate-patterns` for per-language hyphenation dictionaries, plus `prince-text-justify` for CJK inter-character justification. This shows a production-grade TeX-style engine's exposed tuning knobs, useful as a checklist of parameters Marxy's own Knuth-Plass config might want to expose (per-context break-choice modes, language-specific hyphenation dictionaries, last-line/last-page hyphenation policy). — [Prince Reference Guide](https://www.princexml.com/doc/12/doc-refs/); [Prince 11 User Guide: Hyphenation](https://www.princexml.com/doc/11/hyphenation/)

### Inferences
- Every actively-referenced JS Knuth-Plass port treats **measurement** as the hard, pluggable part (not the DP algorithm itself) — bramstein/typeset and tex-linebreak both externalize width measurement rather than baking in `canvas.measureText`, and the newest entrant (knuth-plass-wrap) exists specifically because HarfBuzz shaping is more accurate than DOM/Canvas approximation. This validates Marxy's approach if it uses actual font-metrics-based measurement (FontFace/canvas) rather than heuristic character-width tables, and suggests HarfBuzz-via-WASM as a future accuracy upgrade path if current measurement proves imprecise.
- The `hanging-punctuation` CSS property's Safari-only support means any cross-browser (or cross-webview-engine, relevant to Tauri which may use different native webviews per OS) hanging punctuation implementation should not rely on the CSS property alone; a glyph-metrics-based JS approach like OpticalMargin's is the only currently portable technique, which is directly relevant since Marxy already implements hanging punctuation manually rather than via CSS.
- The universal warning across tex-linebreak and its forks — DOM manipulation for justification is slow at scale — is a concrete performance risk to watch for in Marxy's own DOM-based typeset package, particularly for long documents; pre-calculating breaks once against the AST/source map (à la Petroff) rather than re-breaking on every reflow is the documented mitigation pattern.

### Gaps
- No source directly benchmarks bramstein/typeset, tex-linebreak, or tex-linebreak2 against each other for correctness or performance; only self-reported caveats were found.
- No detail found on how (or whether) any of these libraries implement true baseline-grid enforcement — none of the line-breaking libraries surfaced discuss vertical rhythm/baseline snapping as part of their scope; that appears to be a separate, less-tooled problem space (see next question).
- Could not verify knuth-plass-wrap's real-world production adoption or maturity beyond its own README claims — treat performance/accuracy claims there as vendor-stated, not independently confirmed.

## What font-loading and font-metrics strategies avoid layout shift and get accurate baseline-grid measurement?

### Takeaway
The standard toolkit is the CSS Font Loading API (`FontFace`/`document.fonts`) for load-completion signaling combined with `@font-face` fallback-metric overrides (`size-adjust`, `ascent-override`, `descent-override`, `line-gap-override`) to make a system-font fallback occupy the same box as the eventual custom font, preventing reflow when the real font swaps in — a directly applicable, DOM-native technique for a Tauri/WebView-based app.

### Cited Findings
- The `FontFace` object mirrors `@font-face` in JS: it specifies a font source (binary or URL) and other font properties, and lets code trigger a font's download programmatically and monitor load completion; `FontFaceSet` (`document.fonts`) can additionally report when **all** fonts required by a document have loaded and layout is complete. — [MDN: FontFace](https://developer.mozilla.org/en-US/docs/Web/API/FontFace); [MDN: CSS Font Loading API](https://developer.mozilla.org/en-US/docs/Web/API/CSS_Font_Loading_API)
- `FontFace.status` exposes an explicit state machine: `unloaded` → `loading` (downloading/parsing) → `loaded` (success) or `failed` (invalid definition or fetch failure) — a concrete hook for gating baseline-grid measurement until fonts are actually ready rather than measuring against a still-swapping fallback. — [MDN: FontFace](https://developer.mozilla.org/en-US/docs/Web/API/FontFace)
- Layout shift from web fonts is commonly caused by `font-display: swap` swapping a fallback for the real font after load; the standard mitigation is to make the **fallback font's box metrics match the real font** using `@font-face` descriptors `size-adjust`, `ascent-override`, `descent-override`, and `line-gap-override`, so the fallback pre-loads with the same line box height/baseline position the real font will occupy, eliminating the shift when the swap happens. — [Simon Hearne: How to avoid layout shifts caused by web fonts](https://simonhearne.com/2021/layout-shifts-webfonts/); [DebugBear: Fixing Layout Shifts Caused by Web Fonts](https://www.debugbear.com/blog/web-font-layout-shift)
- Complementary practice: choose a fallback system font that's metrically as close as possible to the target font, and hand-tune `font-size`/`line-height`/`letter-spacing` on the fallback declaration to further reduce visible reflow. — [CSS-Tricks: How to Load Fonts in a Way That Fights FOUT](https://css-tricks.com/how-to-load-fonts-in-a-way-that-fights-fout-and-makes-lighthouse-happy/)
- Tooling exists to automate fallback-metric generation (Chrome team blog on "framework tools for font fallbacks" — e.g. Next.js's automatic fallback metric calculation), indicating this is now a common enough problem to have first-class framework support rather than being a manual, one-off tuning exercise. — [Chrome for Developers: Framework tools for font fallbacks](https://developer.chrome.com/blog/framework-tools-font-fallback)
- For actual glyph-level metrics (not just box-level `ascent`/`descent` overrides), **opentype.js** and **fontkit** are the two mature JS font-parsing libraries: opentype.js can access every glyph, measure text, and convert glyphs to SVG paths, including drawing diagnostic lines for a glyph's origin, bounding box, and advance width; fontkit (used by PDFKit) is described as "an advanced font engine for Node and the browser" with glyph substitution/positioning support, and its `layout()` method returns a `GlyphRun` with per-glyph `xAdvance`/`yAdvance`/`xOffset`/`yOffset` — i.e., real OpenType-level shaping data, a materially more precise measurement source than DOM/Canvas text measurement for baseline-grid or hanging-punctuation math. — [opentype.js GitHub](https://github.com/opentypejs/opentype.js/blob/master/README.md); [fontkit npm](https://www.npmjs.com/package/fontkit)

### Inferences
- For a DOM/canvas typesetting package with no native text-layout engine (Marxy's situation), the combination of (1) `document.fonts.ready`/`FontFace.status` to gate any measurement or baseline-grid pass until fonts are truly loaded, and (2) fontkit/opentype.js-derived exact glyph metrics (rather than `canvas.measureText`, which only reports advance width, not ascent/descent/ink bounds) would give more accurate baseline positioning than pure-CSS techniques. The `ascent-override`/`descent-override`/`size-adjust` fallback trick is primarily a *perceived-shift* mitigation for the loading window, not a substitute for real glyph metrics once the target font is loaded.
- Since Marxy already ships/bundles its own theme fonts rather than relying on arbitrary web fonts (per the theme-contract emphasis on no network requests by default), the FOUT/CLS problem is smaller in scope than for a typical website, but the `document.fonts.ready` gating pattern is still relevant to avoid measuring/laying out a baseline grid before a bundled font has finished parsing on cold start.

### Gaps
- No source specifically discusses combining the Font Loading API with **canvas-based** (rather than DOM-based) glyph measurement for baseline-grid enforcement — this pairing (relevant to Marxy's canvas/DOM hybrid, per its own description) does not appear directly documented anywhere found; the two topics (font loading and font-metrics libraries) are covered in separate, non-overlapping sources.

## How do reading apps render code blocks/monospace content differently from prose?

### Takeaway
The dominant industry pattern (well documented in code-editor tooling, less so in reading-app-specific writeups) is: a genuinely monospaced font, opt-in ligatures for operator/comparison sequences, and syntax highlighting layered on top — with GPU-accelerated native renderers (Zed) now offering visibly crisper subpixel rendering than DOM/Chromium-based renderers (VS Code/Electron), a directly relevant data point for a DOM/canvas-based app like Marxy.

### Cited Findings
- VS Code exposes monospace font and ligature control as user settings: `editor.fontFamily` for font choice and `editor.fontLigatures: true` to enable ligature rendering — ligatures are opt-in, not default. — [OpenReplay: Customizing Your Editor with Better Coding Fonts](https://blog.openreplay.com/customizing-editor-coding-fonts/)
- Zed enables font ligatures **by default**, visually combining adjacent characters (e.g. `->`, `!=`) via OpenType feature tags; fonts like Fira Code and JetBrains Mono work without extra configuration. — [Zed Discussion #36773: Ligature enhancement typefaces](https://github.com/zed-industries/zed/discussions/36773); [Zed docs: Fonts & Visual Tweaks](https://zed.dev/docs/visual-customization)
- Zed ships its own custom monospace/sans pair — **Zed Mono** and **Zed Sans** — built from Iosevka, and defaults to "Zed Plex Mono"/"Zed Plex Sans" in some configurations; its renderer is GPU-accelerated Rust with native subpixel anti-aliasing and OpenType shaping, which sources describe as producing crisper text rendering than VS Code's Electron/Chromium-based renderer. — [github.com/zed-industries/zed-fonts](https://github.com/zed-industries/zed-fonts); [search summary citing Zed docs]
- **Monaspace** (referenced in the same search) is a variable monospace font family (five variants: Neon, Argon, Xenon, Radon, Krypton) using "texture healing" — subtle per-character width micro-adjustments that improve readability while preserving monospace column alignment — a font-level technique (not a layout-engine technique) worth noting as prior art for rendering code faithfully without sacrificing the monospace grid. — [TypeSmith: Best Fonts for Zed Editor](https://typographysmith.com/best-fonts-for/zed) (font claims attributed to Monaspace's own marketing; not independently verified in this pass)

### Inferences
- The Zed-vs-VS-Code contrast (native GPU rendering vs Chromium DOM rendering) is a useful data point specifically because Marxy renders via DOM/canvas with no native text engine — it suggests that whatever crispness gap exists between Marxy's code-block rendering and a native-renderer competitor is a rendering-pipeline limitation shared with Electron/Chromium apps generally, not something fixable purely at the CSS/JS layer; canvas-based glyph rendering (if used for code blocks specifically) could potentially close some of that gap since it bypasses some DOM text-layout overhead, but no source directly confirms this trade-off.
- Ligature policy is a real, user-visible decision point apps make differently (VS Code opt-in vs Zed default-on) — Marxy's theme/operations docs likely already have a stance here, but this research did not locate an authoritative "ligatures are objectively better/worse for reading code" study; treat this as taste, not evidence.

### Gaps
- No source specifically addressed how *reading* apps (as opposed to code *editors*) style embedded code blocks (font choice, background treatment, syntax highlighting engine/grammar choice) — this pass surfaced editor-focused material (VS Code, Zed) rather than markdown-reader-specific code-block treatment. This is a real gap: none of iA Writer, Bear, Typora, or Ulysses' code-block rendering techniques were found documented at an engineering level in this research pass.
- No syntax-highlighting-library comparison (e.g. Shiki vs Prism vs highlight.js, TextMate grammars vs Tree-sitter) was researched in this pass; flagged as adjacent but out of the scope actually covered by the searches run.

## Baseline-grid layout in CSS (supplementary — implementation techniques for vertical rhythm)

### Takeaway
There is no single authoritative "baseline grid API" in CSS; the dominant practical technique remains treating line-height as a multiple of a base unit and accepting that true baseline-precise alignment across mixed content (images, headings, variable fonts) is unreliable on the web — a long-standing constraint (A List Apart's 2012-era article is still the most-cited reference) that newer CSS features (container queries, `round()`, custom properties) only partially address.

### Cited Findings
- Classic technique: set `line-height` to a multiple of a chosen baseline unit (e.g. 1.5× or 2× the base font size) so text blocks stack in multiples of that unit — described across multiple sources as the standard starting point. — [Grid Maker Pro: Baseline grid and vertical rhythm](https://gridmakerpro.com/grids/typography-grids/baseline-grid/); [B12: Baseline Grid in Web Design](https://www.b12.io/glossary-of-web-design-terms/baseline-grid/)
- A List Apart's "Setting Type on the Web to a Baseline Grid" is flagged in search results as a long-standing reference on the general problem (full content not fetched in this pass). — [A List Apart: Setting Type on the Web to a Baseline Grid](https://alistapart.com/article/settingtypeontheweb/)
- Fundamental limitation: `line-height` does not track a font's actual baseline position — the baseline is where letters visually sit, while `line-height` describes the total space around a line, and the computed relationship between the two varies by font, so nominally identical `line-height` values do not guarantee identical baseline positions across different fonts. — [Smashing Magazine: CSS Baseline: The Good, The Bad And The Ugly](https://www.smashingmagazine.com/2012/12/css-baseline-the-good-the-bad-and-the-ugly/)
- Newer CSS (container queries, `attr()`, `round()`) is being explored to snap baseline grids in pure CSS, particularly for fluid/responsive type where font-size scales with viewport width and line-height must scale in step to preserve the grid. — [DEV: Aligning images to a baseline grid with modern CSS](https://dev.to/simoncoudeville/aligning-images-to-a-baseline-grid-with-modern-css-5fi4); [maketypework.com: Web typography baseline grids made easy](https://maketypework.com/web-typography-baseline-grids-made-easy/)
- Practical framing from a design-systems perspective: pick a baseline unit (often 24px or 32px), express all margins/line-heights as multiples of it, and treat the web baseline grid as "a spacing system rather than a pixel contract" since images and variable fonts will periodically break exact alignment. — [edgdesign.co: Baseline Grids in CSS](https://edgdesign.co/blog/baseline-grids-in-css); [hnldesign: Setting a flexible baseline grid in CSS](https://hnldesign.hashnode.dev/setting-a-flexible-baseline-grid-in-css)

### Inferences
- Because Marxy already does real per-glyph measurement work for hanging punctuation and Knuth-Plass line breaking (rather than relying on browser default text layout), it is likely already better positioned than typical CSS-only baseline-grid techniques to get *true* baseline alignment — since it can compute actual font ascent/baseline offsets (e.g. via fontkit/opentype.js-style metrics, per the font-metrics findings above) rather than approximating via `line-height` multiples. This is the strongest single point of comparison this research surfaced: most of the public web-dev discourse on baseline grids assumes no access to real glyph metrics and works around that; Marxy's architecture suggests it doesn't have to accept that constraint.

### Gaps
- No source described a JS/TS library that performs baseline-grid enforcement using real font metrics (as opposed to CSS `line-height` heuristics) — this appears to be an underserved niche in open-source tooling; if Marxy's typeset package already does this, it may be closer to novel/best-in-class than derivative of any documented prior art.
