## Escalation risk

- **MARXY-156 is new territory for an implementor**: it asks for a pure
  function extracted from a script that has never had a unit test file, and for a de-duplication
  rule (one bullet per day) that is easy to get almost right (e.g. matching on the wrong prefix
  and creating a second bullet, or over-broadly swallowing a real failure that happens to mention
  the auth string). If it returns once on the de-dup matching or on over-matching a real failure,
  that is a normal narrow miss; if it returns twice, do not dispatch a third narrow fix — that is
  a sign the "exact string" precondition is too brittle against real CLI output drift, and the
  next attempt should widen the match to a small allow-listed set of known infra-failure
  substrings rather than one literal string, which is a shape decision for the next planner pass,
  not a retry.
- **MARXY-155 reuses two different rendering paths** (`packages/theme/test/page.mjs`
  for `before`, the full app boot for `after`) that have never been combined in one script before.
  Watch for the `after` path silently failing to exercise post-pass 3/4 (e.g. screenshotting before
  `handle.ready` resolves) and producing two visually-identical PNGs that pass a byte-difference
  check by accident (font AA noise) without actually showing the feature — the acceptance criteria
  ask for a *visible* difference, not just a byte difference, and a reviewer should look at the
  PNGs, not just diff their sizes.
- **MARXY-126, if reset without a redispatch-mechanism guard, could burn a tenth attempt on the
  exact same failure** if the orchestrator resets `attempts` but dispatches it headlessly again
  before `MARXY-156` lands. The Ten-line summary is explicit about in-app
  dispatch for exactly this reason.
