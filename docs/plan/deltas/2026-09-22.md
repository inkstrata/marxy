## Jira housekeeping this pass had to do first

Before writing anything, this pass found that **MARXY-183, MARXY-184, MARXY-185 and MARXY-186 in
`docs/plan/jira-issues.csv` are not real Jira keys** — `docs/plan/deltas/2026-09-21-mac-shell-gaps.md`
and MARXY-186's own landing PR wrote them as if `jira.mjs sync` had already run, but Jira's issue
counter was still at MARXY-182 when this pass started. That is a rule violation
(`orchestration/prompts/planner.md`: *"Use a placeholder key of the form `MARXY-NEW-<slug>` and
let `jira.mjs sync` replace it"*) that, left alone, would have caused real damage: this pass's
first action was `node orchestration/jira.mjs task "…"` for its own landing key, and Jira
handed back **`MARXY-183`** — the exact string the CSV already uses for the single-instance
story. Running `jira.mjs sync` with that CSV in place would have `GET`ed the real MARXY-183 (this
pass's own landing Task), matched it, and **overwritten it** with the single-instance story's
summary and description, silently, because `sync`'s "already exists" branch only fires a rename
across the tree for the `MARXY-NEW-` prefix — a literal-looking key like `MARXY-183` is treated as
already resolved and just gets `PUT`, never `POST`.

**What this pass did about it:** deleted its own accidentally-created MARXY-183 (and, walking the
same trap forward, MARXY-184/185/186 that three more `jira.mjs task` calls produced before landing
on a key clear of the CSV's reserved range) via the Jira REST API directly (`DELETE
/issue/<key>`, confirmed `404` afterward). Jira Cloud never reissues a deleted numeric key, so
this is safe and permanent. The pass's real landing key is **MARXY-187**, confirmed absent from
the CSV, `deps.json`, `jira-map.json` and `state.json` before use.

**What this pass did not do, and why:** it did not rename MARXY-183/184/185/186 to true
`MARXY-NEW-` placeholders in the CSV. Every mechanical gate (`check-deps`, `check-cards`,
`phases.test`) is green against the current text, dependencies resolve correctly by that literal
string everywhere the board consults them (`deps.json`, `state.json`, branch names once
implementors start), and `orchestration/jira-map.json` already carries the exact same shape of
mismatch for thirty-odd pre-Jira plan ids (`MARXY-001` → `MARXY-5`, etc.) — a local id that is not
the real Jira number, resolved through the map only when something talks to the Jira API. Renaming
now would touch four CSV rows, their (about-to-exist) task cards, and re-run `sync`, for a cosmetic
mismatch the map mechanism already exists to carry. **The one thing this leaves for whoever next
runs `jira.mjs sync` with these rows still in the CSV: it will silently create MARXY-183/184/185/186
as new issues under different real numbers (184 or later, since 183 is now consumed by nothing —
deleted, not reused) and record the mapping in `jira-map.json` without rewriting any file, exactly
like the pre-Jira ids.** That is correct, not a bug, and is the reason this note is this long: the
next person to run `sync` should not "fix" the mismatch by hand.
