# Structured output, front matter and logs

*Agents and tools emit text that is shaped for a machine and read by a person: JSON and JSON Lines, YAML and TOML, front matter, logs, terminal sessions with escape codes, CSV, and single lines that are 50,000 characters long. This chapter says what a reader needs from each, what Marxy does today (mostly nothing, quietly), and what the operation layer can offer without touching a byte. The recurring finding is a split: **a view can fold, mark and reflow anything; only an explicit operation may change bytes**, and most of what readers want from this material fits in the view. The direct evidence on how people read this material is thin to absent, and each section says so.*

Evidence grades: **[A]** replicated findings or a meta-analysis · **[B]** one well-designed study · **[C]** small, limited or mixed studies · **[D]** expert convention, or convergence of shipping tools, without a direct test · **[X]** contested or contradicted. Part of the [Reader Artifacts Handbook](README.md).

ESC bytes and other invisible or bidirectional characters as a security matter, and what copying them into a terminal does, are covered in [Trust and safety](07-trust-safety.md) (rules table, section 2; copy safety, section 6). Colour contrast is in [Colour, contrast and access](09-colour-access.md).

## The two lenses, and why they must not be confused

Marxy has one buffer and two ways to change what the reader sees of it. A **view lens** changes only what is drawn: a fold, a placeholder, a marker glyph, a table laid over a CSV. The buffer, the copy and the byte ranges do not move. An **operation** is a pure `string → string` function whose replacement is spliced into the buffer as one undo step (ADR-0004); it is the only thing allowed to change bytes (commitment 4).

Every mainstream tool surveyed keeps these apart:

- **CodeMirror 6.** Folding is done with decorations. `foldEffect` and `unfoldEffect` are state effects, not document changes, and a selection that touches a fold clears it.[^cm-fold] In the installed source (`@codemirror/language` 6.12.4) `foldService`, `foldNodeProp`, `foldKeymap`, `codeFolding` and `foldGutter` are all exported.[^cm-src] Both `@codemirror/language` and `@codemirror/view` declare `"license": "MIT"` in their `package.json`, and the language repository's LICENSE names Marijn Haverbeke and others.[^cm-lic]
- **VS Code.** Folding uses indentation by default, with syntax-aware folding for Markdown, HTML, CSS and JSON; the documentation says folding does not modify the file.[^vsc-fold]
- **Firefox's JSON viewer.** Arrays and objects collapse; it offers a raw view that can be pretty-printed, filtering, and per-line collapsing for `.jsonl` files.[^ff-json] Whether the raw view is byte-identical to the response was not tested; the documentation describes it as the raw JSON.

Convergence is strong (3 of 3 tools read) that folding is a display feature and pretty-printing is a separate, visible command. **[D]** (converged: 3 of 3)

### Pretty-printing is where bytes get lost

A pretty-printer that parses and re-serialises (`JSON.stringify(JSON.parse(x), null, 2)`) is not a whitespace operation. RFC 8259 lets implementations limit number range and precision and says interoperability is best within IEEE 754 double range (section 6), so a 64-bit integer id can come back changed; it says member names *should* be unique and that duplicate handling varies (section 4), so a parse may silently drop a key.[^rfc8259] A parse-and-stringify round trip also rewrites `1.0` as `1`, turns the escape `\u00e9` into a literal `é`, and, for JSONC, cannot even read a comment. Tested with Node 24.18.1 in the skeptic pass: `12345678901234567890` came back as `12345678901234567000`, a duplicate key kept only the last value, `1.0` became `1`, and `//` comments threw a parse error. Composed and decomposed `é` were *not* changed: JSON.parse does not normalise Unicode, and RFC 8259 says nothing about normalisation.

> **Trap.** Implementing "pretty-print JSON" with `JSON.parse` then `JSON.stringify`. It looks like a whitespace change and is a data change. The operation must be a token-level reflow that emits every scalar's original bytes and changes only whitespace, and it must refuse (offer nothing) on input it cannot tokenise, including anything with comments unless the language is `jsonc`.

## 1. JSON, JSON Lines and long blocks

**Evidence.** No study was found on whether folding or pretty-printing helps a reader of a JSON document. The case rests on convention (the tools above) and arithmetic. A JSON fence pretty-printed with two-space indent is about one line per scalar and two per container.

> **Measured.** A 60-item array of `{id, name, tags:[a,b], ok}` (the shape of the lab's `long-json` probe: `{ items: [60 × {id, name, tags: ['a','b'], ok}] }`, taken from `lab/probe.mjs` and recomputed in the skeptic pass) is 544 lines pretty-printed. Collapsing every container at the depth limit to a single line gives 3 lines at depth 1, 64 at depth 2 and 364 at depth 3. If a collapsed container instead keeps its opening line, a placeholder line and its closing bracket, as the Default below describes, the counts are 5, 184 and 484. Reproduce: build the object, indent 2, and count lines under each rule. On Marxy's 30px code line, 544 lines is 16,320px (about 18 screens of 900px); depth 2 is 1,920px (about two screens) on the one-line rule and 5,520px (about six) on the three-line rule.

JSON Lines is a stricter shape: UTF-8, no BOM, each line a complete JSON value, `\n` as terminator, blank lines invalid.[^jsonl] Its unit of reading is the line. Firefox folds per line;[^ff-json] [Agent artifacts](02-agent-artifacts.md) already derives a transcript view from Claude Code JSONL and keeps the default for `.jsonl` as Source.

> **Default.** In **Rendered mode, fold nothing at rest**: a fence is the author's text and chapter 2's rule stands (do not fold what the author did not fold). What the reader gets instead is a *summoned* lens, offered only when a data fence (`json`, `jsonc`, `jsonl`, `yaml`, `toml`) exceeds **60 lines** (two screens at 30px): "fold to depth 2", which replaces each collapsed container with its opening line, a text placeholder giving the omitted line count, and its closing bracket. For a 400-line fence the aim is a first screen of about 30 lines showing the top-level shape; depth steps up or down from the keyboard one level per press, and every placeholder is text in the flow, not a button. **[D]** (60 lines and depth 2 are judgement, listed as taste: they are not derived from any evidence, and with a three-line placeholder depth 2 leaves 184 lines of this fixture, not 64, so the lens would still be long.) The lens is summoned, so it does not conflict with chapter 2's rule not to fold what the author did not fold. For flat, long results (JSONL with 400 records) a summoned head-and-tail lens is possible, but chapter 2 itself says its 30 lines and 10/10 split are author judgement that the tools do not support (Codex CLI shows 5 lines per tool call and 50 for a user shell command, chapter 8), so no number is proposed here. **[D]**
>
> In **Source mode** (CodeMirror 6), install `codeFolding` with a text placeholder ("… 62 lines") and the fold commands on the keyboard (`foldKeymap`), and add `foldGutter` only where line numbers are already shown; fold state is never written to the buffer or the file. **[D]** (converged: 3 of 3)

> **Operation.** Three, and they are not the same kind of thing.
> `copy-json-pretty`: block, `string → clipboard`, the token-level reflow put on the clipboard with `replacement` equal to the input, so the buffer is untouched. This is the safe form and should be offered first.
> `format-json`: span | block | document, `string → string`, token-level reflow to two-space indent (whitespace only; scalars keep their exact bytes; refuses on invalid or comment-bearing input). Applicable when the selection is a whole JSON value or a `json` fence. It is a splice, so it is labelled "Reformat JSON (changes the file)" and is one undo step.
> `minify-json`: same applicability, `string → string`, removes insignificant whitespace only.
> Fold and unfold are *view state*, not operations (they have no replacement). Pretty-print and minify are already on the v1.1 candidate list; the finding here is the splice/clipboard split and the token-level constraint. **[D]**

> **Marxy today.** A long JSON fence is not folded: the probe case `long-json` renders the whole fence (`lab/data/probe-results.json`). `json`, `jsonc`, `yaml` and `toml` have grammars in the allow-list (`packages/core/src/highlight/languages.generated.ts`); `jsonl` is not a key, so a `jsonl` fence is plain text (probe `jsonl-fence`). The Source editor (`apps/desktop/src/source/editor.ts`) imports history, drawSelection, highlightActiveLine, line numbers, keymaps and search, and no `foldGutter`, `codeFolding` or `foldKeymap` (a text search of the file for "fold" finds nothing).

### Long single lines and blobs

Minified JSON, base64 payloads, data URIs and JWTs are single lines of 2,000 to 200,000 characters. Marxy's code rule is to wrap at 100 columns with continuation rows hung 2ch (chapter 4). A 50,000-character line is then 500 rows, or 15,000px, in the middle of a document. No study of reading such content was found; in practice a reader looks for its shape or copies it.

> **Default.** A line longer than **1,000 characters** in a fence is drawn as its first **200 characters**, a text marker `… 48,800 more characters`, and nothing more, expandable by keyboard; copy always takes every byte. **[D]** (1,000 and 200 are judgement, listed as taste: no tool surveyed converges on them and nothing was measured; the line is elided only in the drawn view, and an elision marker is chrome that appears only where a line already breaks the page.) The marker is drawn, not inserted: it has no source range and is excluded from selection and copy, as line-number gutters must be.[^code-verbatim]

> **Operation.** None new: copy already takes the bytes, and `format-json` above is the way to make a minified line readable.

> **Trap.** Truncating a long line *in the buffer or the clipboard* to keep the page tidy. The only truncation allowed is in the drawn view.

> **Marxy today.** No such rule; a long line wraps at the code width (chapter 4). Nothing is elided.

## 2. Config formats: show exactly what is there

YAML and TOML are read as configuration, and the temptation is to help: colour `true` as a boolean, show `2026-09-25` as a date, tidy the indentation. The specifications argue against helping, because the meaning of a scalar depends on a version and a schema the reader does not have.

- **YAML 1.2.** In the Core Schema only `true | True | TRUE | false | False | FALSE` resolve to boolean; `null | Null | NULL | ~` and the empty scalar resolve to null; decimal, `0o` octal, `0x` hex and float patterns resolve to numbers; whatever matches no rule is a string.[^yaml122] So `no`, `on` and `NO` are strings in 1.2.
- **YAML 1.1.** Its boolean type accepts `y|Y|yes|Yes|YES|n|N|no|No|NO|true|True|TRUE|false|False|FALSE|on|On|ON|off|Off|OFF`, so `NO` (the country code for Norway in a list of countries) becomes false.[^yaml11-bool] Its integer type also has a base-60 form: `190:20:30` is the integer 685,230.[^yaml11-int]
- **TOML 1.0.** Values are explicitly typed: booleans are lowercase `true` or `false`, dates follow RFC 3339 (offset date-time, local date), and unspecified values are invalid, so no implicit coercion occurs.[^toml]

The same bytes are a boolean to one parser and a string to another, and nothing in the text says which the author meant. A reader that recoloured `NO` as a constant would be asserting a 1.1 reading. This is an argument from the specifications; **no study was found** on whether readers are misled by scalar colouring in configuration files.

Yin, Ma, Zheng, Zhou, Bairavasundaram and Pasupathy's SOSP 2011 study of configuration errors in commercial and open-source systems exists (bibliographic details confirmed from a search result; the ACM page returned 403 and no abstract or figures were read).[^yin] It is not used for any claim here, and it studies causes of misconfiguration, not how configuration is read.

> **Default.** Config fences and files are shown **verbatim in the mono face, coloured only by the existing classes**, with no type inference, no display of "resolved" values, and no normalisation of indentation, quoting or key order. In Source mode `yaml`, `yml`, `toml` and `ini` files open with their grammar and get the fold commands (indentation folding works for YAML without a parser; TOML folds by table header). A tooltip on scalars that are ambiguous across YAML versions (match the 1.1 boolean or base-60 patterns but not the 1.2 ones) is a candidate, not a recommendation: it is chrome, and no evidence supports it. **[D]** (the spec facts are engineering; the default is a judgement.)

> **Operation.** `format-yaml` (block, `string → string`) is on the v1.1 list and carries the same hazard as JSON: a YAML round trip drops comments and can rewrite quoting and anchors. Only a whitespace-only reflow is acceptable and none is generally safe, so the recommendation is **not to ship `format-yaml`** unless it is shown to leave every non-whitespace byte alone. `copy-code-clean` (already v1) covers the common need. **[D]**

> **Marxy today.** `yaml`, `yml`, `toml`, `ini`, `json`, `jsonc` are allow-listed (`languages.generated.ts`). Nothing interprets values. The Shiki grammar decides what is a constant; its colouring of `no`/`on` in YAML was not measured.

## 3. Front matter

**What exists.** GitHub renders a YAML block between dashes at the top of a prose file as a horizontal table, for any prose format it supports (2013 announcement).[^gh-yaml] That is still the behaviour as of an October 2025 community feature request, which calls the table rendering clumsy and asks for it to show YAML instead; GitHub's own current docs pages found describe front matter only for the GitHub Docs authoring format, not for how file views render it.[^gh-yaml-now] GitHub's own docs describe front matter as a convention popularised by Jekyll, a key-value block at the top of a file.[^gh-fm] Obsidian stores properties as YAML between `---`, shows them **visible** by default (or hidden, moved to the sidebar, or as source YAML), has six types (text, list, number, checkbox, date, date and time), forbids Markdown inside values, and shows nested properties only in source mode.[^obsidian] The Agent Skills specification requires YAML front matter with `name` (1-64 characters, lowercase letters, digits and hyphens) and `description` (1-1,024 characters, what the skill does and when to use it), with optional `license`, `compatibility` (up to 500), `metadata` and an experimental `allowed-tools`; name and description are loaded for every skill at startup, before the body.[^skills] For those files the front matter is the highest-value text in the document. Cursor `.mdc` rules and Copilot path rules share the shape (from chapter 2 and the lab probe `frontmatter-mdc`; Cursor's own documentation was not fetched).

Convergence: 2 of 2 general-purpose viewers read (GitHub, Obsidian) show front matter by default, one as a table and one as a properties block. No study was found on whether a metadata head helps or hurts a reader of a rendered document. **[D]** (converged: 2 of 2 viewers; chapter 2 adds 4 of 4 instruction formats that use a header to decide applicability.)

> **Default.** Show a **quiet key/value head** above the first block, not collapsed and not hidden, whenever the file opens with a front matter node. Layout: one line per top-level key on the half-line grid (15px), the key in the label style at the small type step, values beginning at a fixed hang (key column as wide as the longest key, capped at 14 characters), the value set in the reading face at the measure and wrapping like prose, so a 1,024-character Skill description is legible rather than clipped. Nested values (a `metadata:` map, a list of `globs`) are shown as their own source lines, verbatim, in the mono face, as authored, with no interpretation; values are never pills, dates or checkboxes. If the head runs past **12 lines** it shows the first 12 and a text count of the rest ("… 9 more lines"). An empty front matter shows nothing. Both `---` (YAML) and `+++` (TOML) heads are shown. **[D]** (converged: 2 of 2 viewers, 4 of 4 instruction formats; the layout, the 14-character key column and the 12-line cap are judgement, listed as taste, and not tested; a 12-line head is itself a departure from chapter 2's rule not to fold what the author did not fold, defensible only because the head is a derived view of metadata, not the author's prose.)

> **Trap.** Splitting values by parsing YAML. Split lines only on the first `:` of an unindented line; every indented or unrecognised line belongs, byte for byte, to the previous key. A parse would have to choose a YAML version (section 2) and can fail on hostile input.

> **Operation.** `copy-front-matter`, block, `string → clipboard`: the exact bytes of the head including its delimiters. "Show in source" (already planned) navigates to the head's range. No splice operation on front matter is proposed: editing metadata is authoring, and Obsidian's typed properties show how quickly such a UI becomes an editor. **[D]**

> **Marxy today.** The parser recognises both delimiters (`packages/core/src/parse/parse.ts` enables `frontmatter(['yaml', 'toml'])`) and the AST has a `frontmatter` node with provenance; the renderer discards it: `packages/core/src/render/render-html.ts` line 127, `case 'frontmatter': … return ''`, with a comment that showing it "is a decision for the story that designs the document head". Probes `frontmatter-yaml`, `frontmatter-toml` and `frontmatter-mdc` confirm that `pdf-tools`, the description text and `alwaysApply` do not appear on the page. JSON front matter (`{ … }` at the top) is not recognised; it renders as a paragraph and the smart-typography pass curls its quotes (an earlier probe recorded in the draft; not re-run).

## 4. Logs

A log line is a timestamp, a level, a source, a message, and sometimes a stack trace. The reading tasks are finding the first error, its neighbours, and what changed between two runs.

**Colour and the level word.** WCAG 1.4.1 (level A) says colour must not be the only visual means of conveying information, and applies to text colour; the Understanding document's own example is required fields marked only in red.[^wcag141] Log levels are already words (`ERROR`, `WARN`), so colouring them is a redundant channel and satisfies the criterion as long as the word stays and nothing depends on hue alone. **No study of how developers skim or scan log files was found**: a search for eye-tracking and reading-behaviour work returned studies of skim reading in general and of source-code reading, none of logs. Level colouring is therefore convention (terminals and log viewers all do it), not evidence that it speeds finding an error. **[D]**

**Timestamps and figures.** Marxy sets code in JetBrains Mono, a monospaced face, in which every digit has the same advance, so columns of times align without a tabular-figure feature; `font-variant-numeric: tabular-nums` matters only for a proportional face, and logs are not set in one. Nothing to do; recorded so nobody adds it.

**Stack traces.** Schröter, Bettenburg and Premraj (MSR 2010) studied Eclipse bug reports and report strong evidence that stack traces help developers fix bugs.[^schroter] **[C]** (abstract only, one project, developers fixing bugs rather than readers skimming a log.) No frame-depth figure is used: those quoted in secondary summaries could not be checked against the paper and have been removed. The design consequence is modest and is judgement: do not hide a trace by default.

**A grammar Marxy could allow-list.** Shiki ships a `log` grammar sourced from the VS Code Log File Highlighter's `syntaxes/log.tmLanguage`; the Shiki project's `tm-grammars` index records the licence as MIT and the extension's own `LICENSE` reads MIT (copyright 2015, emilast).[^logfile-lic] `@shikijs/langs` 4.4.3, already installed, declares MIT and contains `log`, `jsonl`, `csv`, `tsv` and `shellsession` modules.[^shiki-langs] The `log` grammar's scopes, read from the module, are `comment log.date`, `comment log.verbose`, `constant.language log.constant`, `markup.inserted log.info`, `markup.changed log.debug`, `markup.deleted log.warning`, `string log.string`, and `string.regexp, strong log.error`, plus exception scopes (`string.key, emphasis log.exception`, `string.regexp, emphasis log.exceptiontype`). Under Marxy's twelve-class table (`packages/core/src/highlight/scopes.ts`, first prefix wins) the highlighter was run in the skeptic pass (Shiki 4.4.3, the `marxy-scopes` theme, on an eight-line sample with INFO, DEBUG, WARN, ERROR, FATAL, TRACE, a quoted string and a Java trace). Result: **timestamps and the word `TRACE` get the comment class; `ERROR`, `FATAL`, quoted strings, exception names and every `at …` trace line get the string class; bare numbers such as `8080` and `1200` get the constant class; `INFO`, `DEBUG` and `WARN` get no class**, because `markup.*` maps to none. So a whole stack trace would be drawn in the string colour.

> **Default.** Allow-list the `log` grammar (MIT, verified above) only once level can be carried by *weight*, not hue: the level word (`ERROR`, `WARN`) in the bold weight the sibling handbook already uses for definitions, which is not yet expressible as a token class (see gaps). Until then keep it off: string colour on ERROR lines and on every trace frame would say "this is a string", and numbers would light up as constants. With it on, timestamps take the comment colour (read, not dimmed) and the level word carries weight plus its text, satisfying WCAG 1.4.1 without a hue. Never fold a stack trace at rest; any shortening is a summoned lens whose numbers are judgement (chapter 2). **[D]** (level colouring is converged convention; weight-not-hue follows WCAG 1.4.1 and the restrained palette.)

> **Operation.** `copy-error-lines`, block or document, `string → clipboard`: lines whose level word matches `ERROR|FATAL|WARN` (case-sensitive, at a field position), each with its continuation lines (indented or `at …` lines), joined by newline; a pure function, useful for pasting into a bug report. Showing only matching lines is a *lens* and is find's job (`docs/navigation.md`), not an operation. **[D]**

> **Marxy today.** No `log` key in the allow-list; a `log` fence is plain (probe `log-fence`: `2026-09-25T10:00:02Z ERROR db timeout after 5000 ms` is an undifferentiated run). A whole `.log` file opens in Source mode without a grammar for the same reason.

## 5. Terminal output and ANSI

**What the bytes are.** ECMA-48 (5th edition, June 1991) specifies the control functions; SGR, "select graphic rendition", is `CSI Ps… m` with default parameter 0, and it sets rendition aspects for the text that follows until the next SGR: 0 default, 1 bold, 2 faint, 3 italic, 4 underline, 5 and 6 blink, 7 negative image, **8 concealed characters**, 9 crossed-out, with colour parameters further down the table (section 8.3.117, read from the standard's PDF text).[^ecma48] In a captured log the ESC byte (U+001B) is invisible and the reader sees `[31mFAIL[0m`.

**What tools do.** Web log viewers convert SGR to styled spans. Forum threads seen as search-result summaries indicate GitHub Actions renders ANSI colour but forgets the current style at each newline; that is secondary and unverified, and GitHub's workflow-commands page (read) does not mention ANSI.[^gha] How Jupyter and the VS Code terminal handle ANSI was **not verified** and is left out.

**Why colour-rendering is a poor default for Marxy.** These are separate arguments: SGR 8 is one parameter and colour is another, and the first does not apply to colour alone. (1) SGR 8 (concealed), and foreground colours that match the ground, let a captured stream hide text from the reader; honouring them would give any file the power to draw invisible characters, which [Trust and safety](07-trust-safety.md) treats as a defect. That argument would be met by ignoring SGR 8 and clamping colours, without dropping colour altogether. (2) Marxy promises every code token at least 4.5:1 on the code background and on selection and find highlights; a stream may request black or dark blue on the `#151412` ground, which fails unless colours are remapped to the palette, which is the same as not rendering the stream's colours. The choice of no colour is judgement, not a consequence of the spec. (3) Once colour is rendered, the drawn text no longer matches the file's text for copy and search.

Source mode already has a tool for the byte: CodeMirror's `highlightSpecialChars` matches a default set that includes U+0000 to U+001F except tab, U+007F to U+009F, the zero-width and bidirectional controls, and draws a visible placeholder.[^cm-view] Marxy's editor does not install it.

> **Default.** In **Source mode**, install `highlightSpecialChars` (with `addSpecialChars` for anything chapter 7 adds) so U+001B and the other C0 controls are visible. In **Rendered mode**, an ESC in a fence is drawn as the visible glyph `␛` (U+241B) in the comment colour and the SGR sequence after it is ordinary text: the reader sees `␛[31mFAIL␛[0m`, with chapter 7's marker. No colour is rendered from SGR by default. **[D]** (the security argument is chapter 7's; the glyph and the no-colour default are judgement.) A summoned "clean view" lens may hide `ESC [ … m` for display only; copy always carries the bytes.

> **Operation.** `strip-ansi`, block or span, `string → clipboard`: removes CSI sequences (`ESC [`, parameter bytes, intermediate bytes, one final byte) and leaves everything else, with the buffer untouched. A `string → string` splice ("remove escape codes from this file") is possible but is a byte change and belongs behind an explicit label. **[D]**

> **Marxy today.** ESC reaches the DOM unchanged inside a fence: probe `ansi-in-fence` records U+001B twice in a `text` fence, and the page draws `[31mFAIL[0m src/app.test.ts` with the byte invisible. The Source editor installs neither `highlightSpecialChars` nor folding (`apps/desktop/src/source/editor.ts`).

### Console fences, prompts and `sh`

Linguist has two entries: **Shell** (aliases `sh, shell, bash, zsh, ksh` and others) and **ShellSession** (aliases `bash session` and `console`).[^linguist] Shiki's `shellsession` module (MIT; grammar from `hronro/sublime-linguist-syntax`, which GitHub's repository page shows as MIT; its LICENSE text was not fetched) scopes the prompt as `entity.other.prompt-prefix` and `punctuation.separator.prompt`, the output as `meta.output`, and embeds the shell grammar for commands.[^shiki-langs] Run in the skeptic pass through the Marxy scope table, output lines are plain but the prompt character `$` (and `#`) takes the **punctuation** class, because `punctuation.separator.prompt` matches the `punctuation` prefix; the command text after it was plain in the sample. So the prompt would be drawn in the punctuation colour, which is quieter than the function colour the `sh` grammar gives it today but is not "no class". **[D]** (converged: 2 of 2, Linguist and Shiki both distinguish a session grammar; nothing tests readers.)

The probe shows the opposite failure today: an `sh` fence with a `$ ` prompt is highlighted by the shell grammar, which colours the prompt as a function name (`function:"$"` in probe `sh-with-prompt`), so the character that must not be copied is the one that is coloured.

> **Default.** Allow-list `shellsession` (MIT) with the aliases `console`, `shellsession`, `sh-session` and `bash session`; leave `sh`/`bash` on the shell grammar. Marxy must not turn an `sh` fence that has prompts into a console fence (a guess about the author's intent); the copy operation below makes that fence safe. **[D]**

> **Operation.** `copy-command`, block, `string → clipboard`. For a `console`/`shellsession` fence: the commands only, i.e. lines that begin with a prompt (`$ `, `# `, `% ` or `> `, after optional whitespace) with the prompt removed, continuation lines (trailing `\`) kept, output lines dropped. For an `sh` fence in which **every** non-blank, non-comment line starts with `$ `, the same prompt removal; a lone `$ ` line inside an otherwise prompt-free script is left alone, and `$HOME/bin` has no space after the dollar so it is never a prompt. `copy-code-clean` (already v1) is the general form; this is its console specialisation. `replacement` equals the input, so it cannot damage the file. **[D]**

> **Marxy today.** `console`, `shellsession` and `log` are not keys of `LANGUAGE_TO_GRAMMAR`; probe `console-fence` records "no grammar (plain)": `$ pnpm add widgetlib`, `Packages: +1` and `$ pnpm test` are one colour, and a copy takes prompts and output together. `suggestion` fences (GitHub's suggested-change syntax) are likewise plain (probe `suggestion-fence`), which is acceptable: they are a proposal, not a language.

## 6. CSV and TSV

GitHub renders any `.csv` or `.tsv` **file** as an interactive table with the first row taken as the header, a row-number gutter, a filter box and row linking.[^gh-csv] The documentation page read does not mention CSV inside a fenced code block; whether GitHub tables one was not tested, and no claim is made. Shiki's `csv` grammar (from `mechatroner/vscode_rainbow_csv`, whose LICENSE reads MIT, 2017) scopes fields `rainbow1` to `rainbow5` with names such as `keyword.rainbow2`, `entity.name.function.rainbow3`, `comment.rainbow4` and `string.rainbow5`: it colours column *n* cyclically.[^shiki-langs] Under Marxy's class table that would paint columns as keyword, function, comment and string in turn, meaning nothing.

> **Default.** A `csv`/`tsv` fence stays **verbatim** in the mono face, plain (do not allow-list `csv` or `tsv`: rainbow columns spend the restrained palette on structure that carries no meaning), with the standard wrap. No automatic table: choosing a delimiter, a header row and a quoting rule is interpretation, and a wrong guess is worse than plain text. A whole `.csv`/`.tsv` file opens in Source mode like any non-markdown file. A summoned **table lens** (view-only) may lay out the first 200 rows with the delimiter and header assumption shown and changeable, and must say it is a lens. **[D]** (1 of 1 tool read tables `.csv` files; nothing tests readers.)

> **Operation.** `copy-as-markdown-table`, block, `string → clipboard`: converts a well-formed CSV/TSV to a GFM pipe table, refusing on ragged rows. `align-table-pipes` is already v1. No splice operation on CSV. **[D]**

> **Marxy today.** `csv` and `tsv` are not allow-listed; a `csv` fence is plain text and the whole-file case is Source mode with no grammar.

## Whole files in Source mode

The rule for non-markdown files is Source mode (CodeMirror 6). What each format gets and needs:

| Format | Grammar today | Source-mode default proposed | Needs |
| --- | --- | --- | --- |
| `.json`, `.jsonc` | yes | fold commands and gutter, placeholder `… N lines` | `codeFolding` + `foldGutter` in the CM6 setup |
| `.jsonl`, `.ndjson` | none | plain, one record per line, no fold | allow `jsonl` (MIT, `microsoft/vscode`) or leave plain |
| `.yaml`, `.yml`, `.toml`, `.ini` | yes | fold by indentation or table; no interpretation | fold extensions |
| `.log` | none | timestamps only, after the class gap is closed | `log` grammar + weight class |
| terminal capture with ESC | none | visible placeholders for control characters | `highlightSpecialChars` |
| `.csv`, `.tsv` | none | plain | nothing |

CodeMirror's fold services are language-agnostic: `foldService` lets any language supply a range for a line, and `foldNodeProp` attaches fold rules to syntax nodes;[^cm-fold] whether the `@codemirror/lang-*` packages Marxy loads register `foldNodeProp` for each format was not checked.

## Spec, operations and gaps

Settings, operations, gaps and stories are recorded in `data/03.json`. In short: **fold only in a summoned lens, never at rest; offer the `copy-*` form of pretty-printing first, with splice forms behind an explicit label; show front matter as a quiet verbatim key/value head; carry log level in the word and weight, not hue; make ESC visible rather than colour it; add `shellsession` and `copy-command`; leave CSV verbatim.**

## What the evidence does not say

- No study was found of how readers read, skim or scan JSON, YAML, TOML, logs, terminal captures or CSV in a rendered reader. Every default above rests on tool convergence and arithmetic **[D]**.
- No study was found that colouring log levels speeds locating an error, or of colour-vision-deficiency effects beyond the general WCAG 1.4.1 argument.
- The only empirical result used is Schröter et al. (abstract only): stack traces help developers. Frame-depth figures were removed as unverifiable.
- Yin et al. (SOSP 2011) was not read (ACM page 403), so no finding of it is used.
- GitHub Actions, Jupyter and VS Code terminal ANSI behaviour was not verified from primary documentation.
- Cursor `.mdc` and Hugo/Jekyll front matter formats were not read from their own documentation.
