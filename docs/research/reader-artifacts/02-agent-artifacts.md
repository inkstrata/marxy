# Agent artifacts: transcripts, tool calls, plans and instruction files

*What an AI agent leaves on disk is a strange mixture: markdown that a person wrote for a machine, JSON lines that a machine wrote for itself, and metadata fenced in a header nobody sees. This chapter says which formats exist, which of them Marxy can open as documents, how a reader should tell speakers apart, when tool output should be folded, and what a reader loses today because Marxy treats the machine's markup as unknown HTML. The last is the largest finding: Marxy currently hides, without a word, the parts of an agent file that the agent reads most carefully.*

Evidence grades: **[A]** replicated findings or a meta-analysis · **[B]** one well-designed study · **[C]** small, limited or mixed studies · **[D]** expert convention, or convergence of shipping tools, without a direct test · **[X]** contested or contradicted. Part of the [Reader Artifacts Handbook](README.md).

## The artifact zoo, as files

Nearly every agent-facing file is markdown, and several carry a YAML header. Only session logs are not markdown. That decides what Marxy does with them: markdown opens in Rendered mode, anything else opens in Source.

| Artifact | Path and shape | Markdown? | Header | What Marxy shows |
|---|---|---|---|---|
| `AGENTS.md` | Plain markdown, no required fields; the nearest file to the working directory wins[^agentsmd] | yes | none | Rendered |
| `CLAUDE.md` | Markdown; `@path` imports (depth four); block-level HTML comments are stripped before the model sees the file[^claudemem] | yes | none | Rendered |
| Claude rules | `.claude/rules/*.md`; the only header field read is `paths`, and the header is removed before loading[^claudemem] | yes | YAML | Rendered, header invisible |
| Agent Skills `SKILL.md` | Required `name` (64 characters) and `description` (1,024); optional `license`, `compatibility`, `metadata`, `allowed-tools`[^skills] | yes | YAML | Rendered, header invisible |
| Codex `AGENTS.md` | Same file; discovery walks from the Git root, `AGENTS.override.md` first, 32 KiB default cap (`project_doc_max_bytes`)[^codex] | yes | none | Rendered |
| Gemini `GEMINI.md` | Markdown; `@./path` imports; file names configurable, and `AGENTS.md` may be listed[^gemini] | yes | none | Rendered |
| Cursor rules | `.cursor/rules/*.mdc`; fields `description`, `globs`, `alwaysApply`[^cursor] | `.mdc` is not `.md` | YAML | Source (extension), or invisible header if renamed |
| Copilot instructions | `.github/copilot-instructions.md`, and `.github/instructions/NAME.instructions.md` with a front-matter block for globs[^copilot] | yes | YAML | Rendered, header invisible |
| Aider history | `.aider.chat.history.md`, markdown[^aider] | yes | none | Rendered |
| Claude Code session | `~/.claude/projects/<project>/<session>.jsonl`, one JSON object per line[^hooks] | no | n/a | Source |
| Subagent transcript | Same shape, separate file under the session's `subagents/` folder | no | n/a | Source |
| Plans and to-do lists | Ordinary markdown with `- [ ]` items, regenerated by the agent | yes | sometimes | Rendered |
| XML-tagged prompts | Markdown with `<instructions>`, `<example>`, `<document>` style tags[^xml] | yes | none | Rendered, **tagged content removed** |

Two points the table hides. First, the tag vocabulary is not a standard: Anthropic's own guide gives `<instructions>`, `<context>`, `<input>`, `<document>` as examples of names one may choose.[^xml] A reader cannot allow-list it. Second, Aider's markdown history is described in the project's FAQ as containing headings and blockquotes for tool output, but the FAQ does not specify the exact layout, so this chapter does not rely on it beyond "it is markdown".[^aider]

> **Marxy today.** File type is decided by extension: `.md` opens Rendered, everything else Source (`docs/scope.md`; brief). A `.jsonl` session opens as a wall of Source, with each line one JSON object of up to tens of kilobytes (measured below). Cursor's `.mdc` opens in Source, so its header is at least visible, while the same rule renamed `.md` would lose it.

### What a session log actually contains

Claude Code documents only that `transcript_path` names a JSONL file, one message per line, written asynchronously; it does not document the line schema.[^hooks] So the schema is a fact to measure, not to cite.

> **Measured.** One local Claude Code session file of 2.46 MB, read with a 15-line Python script (`json.loads` per line, counting `type` and each message's `content[].type`): 941 lines in 15 distinct `type` values. Only 169 `user` and 334 `assistant` lines (53% of the lines) are conversation; the rest is `attachment` (195), `last-prompt`, `custom-title`, `agent-name` (54 each), `queue-operation`, `system`, snapshots and cost state. Inside those, 165 `tool_use` blocks pair with 165 `tool_result` blocks, and 112 `thinking` blocks sit beside 57 `text` blocks. The largest single `tool_result` was 19,165 characters. A `tool_result` arrives on a line typed `user`, so the JSON `role` is not the speaker a reader means. Lines carry `parentUuid`, `isSidechain` and `sessionId`, so a session is a tree, not a list. Reproduce with any file in `~/.claude/projects/*/`. Schema of one version of one tool; not a contract. **Generalisability (skeptic check, counts only, no content copied):** across 12 other local session files of 200 KB or more, the `user`+`assistant` share of lines ran from 0.15 to 0.62 (median about 0.48); thinking-to-text blocks from about 1:1 to 2:1; the largest `tool_result` from 1 to 30 thousand characters. So "about half" and "tens of kilobytes" hold as orders of magnitude, but every ratio here is one developer's sessions, not a population.

The reader-shaped facts: roughly half of a session file's lines are bookkeeping a reader never asked to see; about one line in six is a tool result (165 of 941; one in three of the conversation lines); and thinking blocks outnumbered the assistant's visible prose two to one in this file (from about equal to two to one across the others). Any transcript view is therefore a *derived* view, a filter and a regrouping, not a rendering of the file.

## Turns and roles

A transcript is a sequence of turns; a turn has a speaker; a speaker is one of *user*, *assistant*, *tool*, sometimes *system* and *thinking*. The sibling handbook has already answered the typographic half of the question for drama and chat logs: speaker labels must stay attached to and distinct from speech, and a hanging indent with the label outdented reads well at any width **[D]**.[^typo7] That is the default here too. What the sibling does not say is who the speakers are.

What was verified this session:

| Tool | Evidence | What it shows about turns |
|---|---|---|
| Claude Code | Interactive-mode reference | The transcript viewer (Ctrl+O) has `{` and `}` to jump to the previous or next user prompt, so the user turn is the unit of navigation[^cc-interactive] |
| Langfuse | Observation-types and data-model pages | A trace is made of typed observations, and `tool` is a type of its own beside `generation`, `agent` and `span`; the page does not say how tool calls nest[^langfuse] |
| Aider | FAQ | A chat log is a markdown file[^aider] |

That is three tools, one of them a tracing product rather than a reader's transcript view, and one (Aider) that shows only that the log is a file: not a convergence. Claude.ai, ChatGPT, Codex CLI, Cursor and LangSmith were on the brief's list; their transcript presentations were **not verified** this session, so no count of them is claimed. What can be said is narrower: where a tool documents its view at all, the *user's prompt* is the landmark (Claude Code) and *tool activity* is a separate typed thing rather than more speech (Langfuse) **[D]** (1 tool each; not a convergence, and Langfuse is an observability schema, not a reading view).

> **Default.** Three visible speaker kinds in a derived transcript: **you** (user), **the agent** (assistant text), and **tool** (call plus result as one unit). Each turn opens with its label outdented into the left margin, at the sibling handbook's hanging-indent rule, with the message set in the reading measure (66 characters) beneath and beside it. A user turn is separated from the previous turn by one full grid line (30px) and the agent's turns within one exchange by half a line (15px), so exchanges group. Thinking is a fourth kind, folded to nothing at rest (below). Speaker is carried by the label's *text* and by position; colour never carries it (chapter 9 owns the palette). **[D]**
>
> **Operation.** `copy-turn`, span→block, `string → clipboard`: the turn's source lines exactly, from the label's first byte to the last byte before the next turn. `copy-user-prompts`, document, `string → clipboard`: the concatenation of user-turn texts, one blank line between. Both are pure reads of provenance; neither writes.
>
> **Marxy today.** There is no turn, role or tool node. `packages/core/src/contracts/ast.ts` lists block types `document`, `heading`, `paragraph`, `blockquote`, `list`, `listItem`, `codeBlock`, `htmlBlock`, `thematicBreak` and the rest; nothing carries a speaker. A markdown transcript such as `fixtures/corpus/18-agent-transcript.md` is only headings ("## What I was asked", "## Tool: the row that was served") and fences. It reads as prose with tool output in code blocks; a reader gets no landmark to jump between turns except the outline of headings.

## Tool calls, results and long output

Long output is where readers of agent artifacts spend most of their time and where most of it is not for them: 165 tool results in a 941-line session, the largest 19 KB.

Facts about how other tools decide what to show, cited to their own sources:

- **VS Code notebooks.** The output-line setting `notebook.output.textLineLimit` defaults to 30 lines in source (`notebookOptions.ts`: `getValue(...textOutputLineLimit) ?? 30`), and is described as how many lines of text an output shows, or, with `notebook.output.scrolling` on, the scroll height. Scrolling defaults **on only in Insiders** (both re-read from source in the skeptic pass) (`default: product.quality !== 'stable'`).[^vscode-nb] A maintainer's issue asks that the description say it is the threshold at which a scrollbar appears, a sign that even the tool's authors find the semantics confusing.[^vscode-issue]
- **GitHub Actions.** `::group::{title}` and `::endgroup::` create an expandable group in the log; `::add-mask::` replaces a secret with asterisks.[^gha] (The fetched summary of the docs page says groups start expanded; this was not confirmed against the live UI and is not relied on.)
- **Claude Code.** The transcript viewer is a separate mode from the live view, with its own keys for "show all content", search in native scrollback, and open in `$EDITOR`.[^cc-interactive]

Every one of those reduces output by *policy* (a line count, a group, a mode), none by evidence about readers. Chapter 8 adds Codex CLI at 5 lines, so the only counted convergence is that line-count truncation with an omitted-count marker is common, not what the count should be.

The evidence on progressive disclosure itself is thin and old. Nielsen's 2006 note argues that showing few options and deferring the rest improves learnability, efficiency and error rate. The only study it names is a usability test of a hotel-reservation design among 46 web applications; the warning that designs beyond two disclosure levels lose users is stated as a general principle, not a finding of that study. It is a practitioner essay, so this is **[D]** (expert opinion), not **[C]**.[^nng-pd] It concerns options in an interface, not the reading of output. No study was found on whether collapsing tool output helps or hurts a reader who is checking what an agent did; chapter 1 records the developer-interview work on reviewing agent output. The convention is real (VS Code, GitHub, Claude Code all fold); its benefit for this task is unmeasured. **[D]**

The decision Marxy has to make is constrained by its rule that chrome at rest is zero: no chevron, no "show more" button in the resting page.

> **Default.** Do not fold anything in a markdown document that the author did not fold. Marxy renders the author's markdown; a tool result in a fence stays a fence. For a *derived* transcript view (below), a tool call is one line at rest: verb, target and outcome ("read `packages/core/src/x.ts` — 212 lines"), with the result behind a summoned expansion, and any result longer than 30 lines shown as its **first 10 and last 10 lines** with the omitted count between them as text ("… 192 lines omitted"). Head-and-tail because errors and totals live at the end and identity at the start. A single disclosure level only (Nielsen's expert opinion warns against more, untested here); the omitted count is text in the flow, not a button, and expansion is a keyboard command or a click on the line. The 30 and the 10/10 split are the author's judgement, not findings, and the tools surveyed do not converge on them: VS Code's 30 is a text-output line limit, which with scrolling on is the output's scroll height, not a fold threshold and not head-and-tail; Codex CLI shows at most 5 lines per tool call and 50 for a user shell command, then `… +N lines` ([chapter 8](08-teardown.md)). Two tools that give a number differ six-fold, so no number is supported; "head-and-tail because errors and totals live at the end" is likewise unsourced. **[D]** at most, listed as taste; the value is to be tuned in taste review, not cited.
>
> **Operation.** `copy-tool-output`, block, `string → clipboard`: the *whole* result's source bytes, never the truncated view, so folding can never cost the reader a byte. `expand-all`, document, is view state, not an operation on the buffer.
>
> **Marxy today.** `<details>` is dropped as unknown markup and its children kept, so an author-folded result renders **open** with the summary as a bare line: the probe case `details-closed` outputs `Tool result (212 lines)` followed by the whole fence (`lab/data/probe-results.json`, case `details-closed`; policy in `packages/core/src/sanitize/policy.ts`). Nothing is folded and nothing is marked as having been foldable.

> **Trap.** Truncating the displayed result and letting copy operate on the displayed text. Provenance makes the right thing easy (copy reads the source range, not the DOM), so an implementation that copies from the DOM gives the reader an abridged result they believe is whole.

## Plans, to-do lists and what changed since last read

Plans and to-do files are the agent artifact a reader returns to. An agent regenerates one many times in a session: items tick, a status line changes, a paragraph is added. The reader's questions are "where was I" and "what changed". No study of either question for *agent-authored* documents was found. What exists is engineering fact about Marxy, which is measured below.

Marxy already has the right primitive for the second question: byte provenance on every node, and a reload path that keeps the reader's place when a file changes under them (MARXY-194).

> **Measured.** `offsetThroughEdit` (`packages/core/src/position/restore.ts`, called from `reload.ts`) keeps a reader's place exactly when a regeneration changes *one* run of bytes, or several runs all above the reader (re-run in the skeptic pass with Node 24: a status-line change plus a ticked item, both above byte 1,495, returns 1,495). When a change above the reader is paired with one below, the function lands the reader at the end of the common prefix. On `fixtures/corpus/03-ai-plan.md`, with the reader at the `## Open questions` heading (byte 1,495), changing `draft 3` to `draft 4` (byte 56) and editing item 3 of that section returns **62**, not 1,495; the earlier figure of 119 did not reproduce and is withdrawn (the result is simply where the first difference starts). The function is correct for its contract (one run); a regenerated plan violates the contract. Reproduce by calling it with the two buffers.

> **Measured.** A task item whose text begins with a code span, strong, emphasis or link renders as a plain bullet: `- [ ] \`src/foo.ts\`: add guard` has no checkbox (re-run in the skeptic pass with `renderSafeHtml`: all four inline openers lose the checkbox; a plain-text opener keeps `<input type="checkbox">`). Cause as recorded by the author (not re-derived): `mdast-util-gfm-task-list-item` 2.0.0 shifts the empty leading text node without moving the paragraph's start, and `attachTaskMarker` (`packages/core/src/parse/from-mdast.ts`, around line 166) searches only the bytes before the paragraph start. Plans written by agents open every item with a code span constantly, so the first operation the v1 list promises, *toggle task item*, is silently unavailable on the most common plan shape. The corpus golden shows it (`packages/core/goldens/03-ai-plan.html.txt`, the `passkeys.enroll` items).

> **Default.** A plan is rendered as the author wrote it; a task item is a checkbox whether its text starts with a word or a code span. When a file reloads and its bytes differ from what the reader last saw, Marxy keeps a private copy of the last-seen buffer *in memory only* and can mark the changed blocks by byte-range difference against it; the marks are summoned, not resting (a "changed since you last read" toggle), and disappear on the next full read. No marker is written to the file. **[D]** (the need is inferred; nothing measured it for readers.)
>
> **Operation.** `toggle-task` (landed on main with MARXY-43 after this chapter was researched; block, `string → string`; it flips the bytes `[ ]`↔`[x]` at the marker's range and nothing else, and its `canApply` needs a `taskMarker` node, so on `7e0a280` it is unavailable for every item described above). `extract-open-tasks`, document, `string → clipboard`: every unchecked item's source line, in order, for pasting into the next prompt. `copy-section` (v1) is the counterpart for a plan phase.
>
> **Marxy today.** Task toggling is defined but blocked for code-span-led items (above). No previous-buffer diff exists. Position restore handles one changed run, or several above the reader; an edit below the reader as well as above throws the reader back to the first difference.

## Instruction files: what the agent sees and what a person sees

An instruction file has two audiences, and the vendors have taken opposite decisions about what the second one may see.

- Claude Code strips block-level HTML comments before the file is injected into context (verified against the docs page in the skeptic pass; the docs say they remain visible when the file is opened with the Read tool), so they are notes *for humans*; it keeps comments inside code blocks; and it strips a rule file's front matter before loading.[^claudemem] For a Claude Code reader, then, a comment in `CLAUDE.md` is the one part of the file that exists **only** for a person.
- An Agent Skill's `name` and `description` are loaded at startup for every skill (about 100 tokens), the body only on activation, and other files only on demand.[^skills] The `description` *is* the trigger: it says when the skill fires. A reader who cannot see it cannot see why a skill runs.
- Cursor's `globs` and `alwaysApply`, and Copilot's glob header, decide *whether* the file applies at all.[^cursor][^copilot] A reader who wants to know what an agent is told in a given directory needs those fields.
- XML tags in prompts are the content, not decoration: Anthropic's guide recommends wrapping instructions, context and input in named tags.[^xml]

So the metadata is the part of an instruction file that answers "when does this apply", and the comments are the part meant for the human. Marxy hides both.

> **Marxy today. (Major finding.)** In Rendered mode:
> - **Front matter renders as nothing.** `packages/core/src/render/render-html.ts` line 127: `case 'frontmatter': … return ''`, with the comment "Showing it is a decision for the story that designs the document head." The AST has a `Frontmatter` node (`ast.ts`, line 47); the renderer discards it. Probe cases `frontmatter-yaml`, `frontmatter-toml`, `frontmatter-mdc`: `pdf-tools`, `Use when the user mentions a PDF.`, `src/db/**/*.ts` and `alwaysApply` are all absent from the page.
> - **XML-tagged prompt content is removed with its contents.** Probe `prompt-xml-block` renders `<instructions>…</instructions>` and `<example>…</example>` as an `<h1>` and nothing else: "Summarise the document in three bullets." is not on the page. `prompt-xml-inline` renders "Answer inside  tags." The sanitiser reports "instructions is not in the marxy-default allow-list; removed with its contents" (`packages/core/src/sanitize/policy.ts`, ADR-0009). With blank lines inside the tags the inner markdown survives, because CommonMark ends an HTML block at a blank line, so the same prompt renders or vanishes depending on whitespace.
> - **HTML comments are removed.** Probe `html-comment`: "also push to the release branch" is gone (`packages/core/src/sanitize/sanitize-html.ts`, line 79, "A comment is a place to hide markup from a reader"). For Claude Code's `CLAUDE.md` this hides from the person the text that is stripped from the injected context (the docs add that the comments stay visible if the file is opened with the Read tool, so the model can still see them by reading the file directly); for other agents (which do not strip comments — not verified for each) it hides text the model *does* see.
> - **Nothing tells the reader.** The removals are counted and logged to the console: `apps/desktop/src/app.ts` line 428, `console.info(\`marxy: sanitiser removed ${removed.length}\`)`. The list `removed` carries each element name and reason; no notice region shows it. The `blockedContentNotice` beside it names blocked images only.
>
> This contradicts commitment 4's spirit for a *reader*: no byte is touched, but the reader is shown a document that is not the one the agent obeys, with no sign of the difference. It is also the trust problem of [chapter 7](07-trust-safety.md) in reverse: hidden content the reader cannot see.

> **Default.** Rendered mode shows an instruction file as the agent's inputs, with two additions and no loss:
> 1. **Front matter shown as a metadata head**: `name`, `description`, `globs`, `paths`, `alwaysApply`, `applyTo`, as key/value lines in the label style above the title, set in the small type step, never hidden and never rewritten. Unknown keys are shown too. It is the file's own text, laid out; the source bytes are untouched. **[D]** (converged: 4 of 4 instruction formats read use a header to decide applicability: Skills, Cursor, Copilot path rules, Claude rules.)
> 2. **A removed-content notice in the flow**, in the existing notices region: "3 elements and 1 comment are not shown: `instructions`, `example`, comment." Summoned detail lists each with its line, and one action shows it in Source at that range. Removal by the sanitiser stays (default-deny, ADR-0009); silence does not. **[D]**
>
> For an XML tag, the better resolution than removal is to keep the children and show the tag name as an inline label, since the tags are the agent's structure; that needs a decision in the sanitiser policy (see gaps). **[D]**
>
> **Operation.** `copy-front-matter`, block, `string → clipboard`: the header's exact bytes. `pretty-print-yaml` (v1.1 candidate) stays a *copy* operation on a selection, never a rewrite of the header. `show-removed`, document: a view command listing sanitiser removals with byte ranges, `string → clipboard` for the list.

> **Trap.** Reading "the agent never sees the comment" as "the reader need not". The vendors' reason for stripping comments is token cost, not that a person has no use for them; an agent's `AGENTS.md` comment that says why a rule exists is documentation.

## A derived transcript view for JSONL

A `.jsonl` session opens in Source as one JSON object per line, up to 19 KB on one line. Source mode is right for what it is (the file), and useless for reading what the session *said*.

> **Default.** For a file the reader opens as a Claude Code session, offer a **read-only derived view**: one exchange per screen, built by a pure function over the file's lines. The view groups lines into turns (user, agent, tool, folded thinking), shows the roughly half of lines (53% in the measured file) that are conversation and drops the bookkeeping types from the resting view, and sets each turn with its hanging label. It is never an edit surface. Every rendered element carries the byte range of the JSONL *line* it came from, so provenance runs into the source file exactly as for markdown: selecting a turn and choosing "show in source" opens the JSONL at that line. Nothing is saved, exported or rewritten. The view is summoned (a palette command), never the default for `.jsonl`; the default stays Source, which is what the file is. **[D]**
>
> **Operation.** `derive-transcript`, document, `string → string` (a rendering, not a splice): JSONL text to a reading-ordered markdown-shaped text with a source-line table, for the view only. `copy-turn` and `copy-tool-output` as above copy from the JSONL line's own content. The schema is undocumented and versioned by the tool, so the function must skip unknown line types, not fail.
>
> **Marxy today.** There is no way to express it. The AST contract has no turn, role or tool node (`ast.ts`), the contracts are frozen (`AGENTS.md`), and every provenance range is a `{file, start, end}` in a *markdown* buffer. A view derived from another file's lines needs either a new node family or a second, view-only structure that reuses the same range type. This is the gap below.

## Spec, operations and gaps in one place

The machine-readable version is in [`data/02.json`](data/02.json). In brief:

- **Show** an instruction file's front matter and say what was removed; do not fold what the author did not fold; make tool output one line at rest with head-and-tail (10/10 over 30 lines: author's judgement, tool numbers 5 and 30 disagree) in a derived view.
- **Do not claim** that any of it improves reading. Every default is **[D]**; no empirical study of readers is cited: the 2006 practitioner essay on progressive disclosure is expert opinion **[D]**, as is the sibling handbook's convention for speaker labels.
- **Open**: which speakers exist beyond user, agent and tool; whether reasoning blocks should be shown by default; whether a reader wants a JSONL view at all (no evidence).
