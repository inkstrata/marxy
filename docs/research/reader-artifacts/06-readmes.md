# READMEs as structured documents

*A README is the first content type Marxy meets and the least like a book: a hero block of HTML, a row of badge images, tables, callouts, folded sections, install commands, diagrams and relative links, written for GitHub's renderer and read on someone else's. This chapter goes element by element, sets what the evidence says a reader needs against what GitHub does and what Marxy does today, and names the small decisions (mostly in the sanitiser policy and the renderer, hardly any in frozen contracts) that would close the gap. Where the evidence is thin, which is most places, it says so.*

Evidence grades: **[A]** replicated findings or a meta-analysis · **[B]** one well-designed study · **[C]** small, limited or mixed studies · **[D]** expert convention, or convergence of shipping tools, without a direct test · **[X]** contested or contradicted. Part of the [Reader Artifacts Handbook](README.md).

## What a README is for, and how it is read

The best empirical description of README content is Prana and colleagues' classification of 4,226 README sections from 393 randomly sampled GitHub repositories into eight categories; their classifier reached an F1 of 0.746, and the headline finding is that "what" and "how" content is common while purpose and status content is often missing.[^prana] That is a description of what authors write, not of how readers read: it says READMEs are mostly description plus instructions, which fits the copy-a-command use in section 8. It is not evidence about reading behaviour.

The popularity literature is correlational. A study of 1,950 READMEs across ten languages found that READMEs of popular projects tend to be organised with lists and images and to link outward, and that those with contribution guidelines and references were associated with higher popularity **[C]**.[^readmepop] Popularity is a poor proxy for "was understood", and the direction of cause is not established; the study does not test whether a reader finds anything faster. No eye-tracking, task-time or comprehension study of README *rendering* (as opposed to content) was found in this survey. That is a finding: every rendering recommendation below rests on convention, on engineering fact, or on the borrowed evidence of neighbouring fields, and is graded accordingly.

What can be said with confidence is structural. A README is skimmed for one question at a time (what is this, how do I install it, how do I use it), so the outline (headings that survive as anchors), the code blocks and the first screen carry the load. Marxy's reader-side answer is already in the architecture: the outline and index are summoned, code copies clean, and headings are the only navigation. The elements below are those where GitHub-flavoured authors reach beyond CommonMark and where Marxy's default-deny sanitiser makes the reader's experience diverge from the author's.

## 1. Badges

**Evidence.** Trockman and colleagues surveyed developers and mined 294,941 npm-linked repositories; they found that non-trivial badges (build status, test coverage, up-to-dateness of dependencies) are mostly reliable signals and correlate with more tests, better pull requests and fresher dependencies **[B]** (correlational; the effects do not always persist).[^trockman] The same paper reports survey answers that packages with too many badges look cluttered or "trying too hard", and derives a hypothesis of a non-linear relation with popularity from that; I read the hypothesis section and abstract, not the full results, so the size of that effect is not verified here. Two points follow. The signal is in the badge's *value* ("passing", "92%"), which lives inside the image, not in its alt text. And restraint has some support from the authors' own survey **[C]**.

**What a blocked badge is.** With remote images blocked (ADR-0009, ADR-0027) a badge is an anchor around an `img` whose only surviving content is its alt text: `build`, `npm`, `MIT`. The value is lost, so the row conveys almost nothing except that badges exist. A row of five blocked badges is five short words in the middle of the first screen of the document.

> **Default.** Collapse a run of consecutive badge images (a paragraph, or block, containing only images, or anchors around images, two or more) into **one quiet line**: the alt texts joined by a middle dot, set at the small size of the type scale, in the muted text colour, each still a link. Where an alt text is the generic service name (`build`, `npm`), that is all that can be said. The consent notice already names the hosts (`img.shields.io`); after per-host consent the images load at line height on the grid, as for any remote image, and the row is left as the author wrote it. Never auto-load; never hide the row entirely, because a missing row reads as "Marxy broke my README" (ADR-0009 records that risk). **[D]** for the treatment (no test of readers; convention from terse fallbacks); the consent model is ADR-0027.

> **Operation.** None. A badge row is presentation. "Extract links" (v1.1 candidate) should list badge links like any other; no badge-specific operation is justified.

> **Marxy today.** `packages/core/goldens/02-readme-real-world.html.txt`: each badge is `<a href><img data-marxy-remote alt></a>` with no `src` (four `data-marxy-remote` images in that golden); the reader sees only the alt text. The notice text is built by `blockedImageNoticeText` in `packages/core/src/render/images.ts`. Nothing groups the row. Grouping is a render-time class on the paragraph (a new class name, so a `scripts/registry.json` entry first) and touches no contract. The opt-in the notice offers is not yet built: ADR-0027 is still `proposed`, the real shell has no `fetchRemoteImage` (only the in-memory test shell does), and `apps/desktop/src/render/images.ts` removes the `src` of every non-local image. The state fails closed, which is right for privacy, but a README's badges can only ever show their alt text until that lands.

## 2. Hero blocks and HTML islands

Most READMEs open with a block of raw HTML: `<div align="center">`, `<p align="center">`, a sized logo, sometimes a `<picture>` with a dark and a light source. Marxy treats the raw HTML as an *island*: sanitised by the same allow-list as everything else (ADR-0009), with no byte provenance of its own.

**Alignment.** `align` on `div`, `p`, `h1`–`h6` is inert: it cannot fetch, script or match a theme selector. It is in `WIDE_POLICY` only. Under the default policy the attribute is removed and the hero collapses to left-aligned text. The design in `docs/design/13-trust.md` already specifies the wide policy: `div`, `p`, headings gain `align: enum(left, center, right)`, `img` gains `width`/`height`/`align`, and Marxy never floats, laying an aligned image inline on the grid.

> **Default.** Honour `align` (left, center, right) on block elements in the *default* policy, because it costs no privilege; keep `width`/`height` on `img` under the default policy as well, since a reserved box prevents layout shift once images load. Keep `align` on images inline (no float). **[D]** (no reader test; GitHub and every renderer surveyed in the brief honour `align`; the security argument is engineering: the attribute is an enum with no URL).

> **Marxy today.** Measured (probe of `parseMarkdown` + `renderDocumentSafeHtml`, default policy): `<p align="center">` loses `align`; `<img width>` loses its size; under `WIDE_POLICY` both survive. Islands carry no `data-marxy-s`/`data-marxy-e` (the probe's `<p align="center"><img …></p>` has none), so a selection inside a hero cannot resolve to a byte range and no operation is offered there.

**Dark and light variants.** GitHub documents the `<picture>` element with `<source media="(prefers-color-scheme: dark)" srcset="…">` and a fallback `<img>`: the changelog announced it as a beta on 2022-05-19,[^gh-picture] the docs' basic-syntax page now says only that `<picture>` is supported,[^gh-basic] and GitHub's own blog (2025-04-18) shows the same snippet.[^gh-blog-picture] The older `#gh-dark-mode-only` / `#gh-light-mode-only` URL-fragment convention is **not documented on any current GitHub docs page I fetched** (the docs source, the changelog, the 2025 blog). A secondary source calls it legacy;[^judis] I could not verify GitHub's own status, so treat "legacy" as unverified. Authors still write it, so a reader must tolerate it.

The consequence for a reader that is dark by default (ADR-0033: `#151412` ground) is concrete: under the default policy `<picture>` is transparent and `<source>` is removed, so the fallback `<img>`, usually the *light-theme* asset (dark logo strokes), shows on the dark ground; and a `#gh-dark-mode-only` image shows in both themes, so both logos appear, one of them invisible or ugly. Probe confirms both.

> **Default.** Choose one variant by Marxy's own theme, not the OS setting the webview would use: a `<picture>` resolves to the `<source>` whose `media` is `(prefers-color-scheme: X)` for the active theme X, else the fallback `<img>`; an image whose URL fragment is `#gh-dark-mode-only` (or `-light-`) is hidden in the other theme. Resolve at render time to a single `img` so that only the visible variant is ever fetched (a reader who consents to a host should not download two images). Every `srcset` is still a subresource list: parse it to one URL (first candidate), pass it through the same deferral as any `src`. **[D]** (no reader test; GitHub behaviour is the reference).

> **Operation.** None.

> **Marxy today.** The default policy makes `picture` transparent and removes `source` with its contents (`packages/core/src/sanitize/policy.ts`, `TRANSPARENT`, `MARKDOWN_EQUIVALENT` has no `source`); `13-trust.md` chose that on purpose ("`<source srcset>` is a subresource list we do not parse"). The fragment is not interpreted anywhere.

**Policy consequences (gaps).** Everything above sits in `packages/core/src/sanitize/`, which `.github/CODEOWNERS` routes to a human owner (ADR-0028). Moving `align`/`width`/`height` into the default list, and admitting `source` with a *parsed* `srcset` and a media-feature allow-list of exactly the two `prefers-color-scheme` values, is a security-posture change: ADR-0009 §2 names `<img>`, `<details>` and `<div align>` as what the opt-in widens. It needs an ADR amendment, the policy-table test in `sanitize/policy.test.ts`, and a vector-suite run under both policies. The no-fetch invariant is unchanged (the `urlSchemes` object stays identical).

## 3. Tables

The sibling handbook settles the typography: left-align text, right-align quantities, tabular lining figures, few rules, scroll wide tables inside a focusable container.[^ct07] This section adds the one question the sibling left open: should rows be striped?

The evidence is small and mixed. Enders' 2008 online experiment (244 participants, six questions, three of them on striped tables, a 15-row by 9-column table of screw specifications) found no significant accuracy difference, mixed speed results (only one of six questions significant), 46% preferring stripes and 33% no preference.[^enders1] Her follow-up, with 2,276 analysed participants, eight timed questions and three formats (plain, lined, striped) on longer, scrolling tables, found stripes improved accuracy on three of eight questions and did no harm, with the author listing her own limits (few questions, contrast and stripe width not varied, individual differences not analysed).[^enders2] Both are web experiments with unfamiliar data **[C]**; the first article points to an accompanying peer-reviewed paper that was not read, and the second imposed a 15-second limit per question. Nothing found tests README-sized tables (typically under ten rows, few columns), where following a row with the eye is cheap; nothing tests striping against whitespace grouping. The gain, where there is one, appears on long, wide tables.

> **Default.** No stripes and no vertical rules: group by whitespace, header in weight and size, per design-language constraint 4 (no boxes, no decorative rules). This is the sibling's rule; the follow-up study is the reason to keep the question open for long tables, not to reverse it. If a stripe is ever added it should be a theme value on the existing token contract, not a new default. **[C]** (both directions).

> **Operation.** "Align table pipes" ships in v1; nothing striping-related is an operation.

> **Marxy today.** Tables render as `<table>` with `align` on cells only (`CELL_ATTRIBUTES` in `policy.ts`); no stripe token exists in `packages/theme`. Adding one needs a name in `scripts/registry.json` and, as a `--marxy-*` custom property, an ADR (token names are frozen).

## 4. Alerts and admonitions

**The syntaxes.** GitHub's alerts are a blockquote whose first line is `[!NOTE]`, `[!TIP]`, `[!IMPORTANT]`, `[!WARNING]` or `[!CAUTION]`. The changelog announcing them is dated 2023-12-14, and describes a new feature with no mention of an earlier beta;[^gh-alerts-log] a 2022 community beta existed but was for a different syntax (a bold `Note`/`Warning` blockquote), with `[!TYPE]` markers, Tip and Caution arriving in November to December 2023 (search-result summary of community discussion 16925, not fetched); GitHub's docs tell authors to use them only when crucial, to limit them to one or two per article, to avoid placing them consecutively, and note that they cannot be nested.[^gh-basic] The older `> **Note**` is plain markdown; GitHub's 2022 beta styled it specially, whereas Marxy renders it as a blockquote with a bold first word. Obsidian's callouts use the same `[!type]` marker with an optional title, a fold marker (`-` collapsed, `+` expanded by default), nesting, and any number of types.[^obsidian] MkDocs Material uses `!!! type "title"` with indented bodies, and Docusaurus uses `:::type` … `:::`.[^mkdocs][^docusaurus] Those last two are not markdown; they need each site's plugin, so in a repository README they are literal text everywhere except that site.

**What warning research says.** It concerns product labels and security dialogs, and transfers to documentation only by analogy.

- Wogalter and colleagues (1994; 135 participants, labels from household products) found that adding a signal word raises perceived hazard over none, and that the extreme words differ, and the abstract I could retrieve confirms the design (135 raters, 16 household labels, signal words NOTE to LETHAL) but not the direction of the middle-word results, which I did not verify **[C]**, in that setting.[^wogalter] At most, the word matters; the size of gradations among the middle words is not established here.
- Anderson and colleagues found, with fMRI on 25 participants, that visual-processing response to a repeated security warning drops sharply after the second exposure, and that a warning whose appearance varies resists this; a second study (80 participants, cursor tracking) agreed **[C]** (abstracts only), for security dialogs.[^anderson15][^anderson16] It concerns identical, repeated interruptions; nothing tests it on in-flow documentation callouts, so transfer is **[D]**. The safe inference is "the more callouts, the less each is read", which agrees with practitioner advice. It does not follow that varying callouts would help a reader.
- Google's developer style guide defines notes, cautions and warnings, says readers skip elements outside their focus of interest, warns against clustering notices, and forbids putting required steps or prerequisites in a note.[^google-notices] **[D]** (authoritative house style; no reader test cited).

> **Default.** Recognise `> [!TYPE]` (case-insensitive; the five GitHub types, plus Obsidian's title text after the marker) at **render time** and set it *label first*: the type's word (`Note`, `Warning`) as a run-in head at body size and semibold weight before the first line of the body, the marker itself not shown, the rest of the quote as ordinary body text with the blockquote indent Marxy already has. **No box, no fill, no icon at rest**; the type is carried by the word, never by colour (design-language constraint 4; [Colour, contrast and access](09-colour-access.md)). Where the author gives a title (`[!NOTE] Title`) the title replaces the type word as the head and the type is kept as the accessible name. `Warning` and `Caution` may take the theme's one accent on the label if the aesthetics gate confirms 4.5:1. Legacy `> **Note**` is already label-first; leave it alone. Do not recognise `!!!` or `:::` in v1: they are not markdown, they degrade to legible paragraphs, and a wrong guess rewrites meaning. Obsidian's fold marker follows the collapsible rule in section 5. **[D]** (converged: GitHub, Obsidian, MkDocs Material and Docusaurus all mark type distinctly; none tested against a plain quote, and *quiet* is Marxy's design constraint, not a finding).

This is **not** an AST change. The AST has no admonition node, and its contract is frozen (`packages/core/src/contracts/`, byte-compared against a pinned hash by `pnpm test`). The recogniser lives in the renderer: it inspects a blockquote whose first inline child is the text `[!TYPE]` followed by a soft break, adds a class and a data attribute (both need `scripts/registry.json` entries), wraps the label in a span, and leaves every byte range untouched, so "copy section" and provenance behave exactly as now. The marker stays in the source and in any copy. A real `admonition` node would let operations target it, and is the alternative if the operation layer ever needs one; it needs an ADR.

> **Operation.** None new. "Copy section" already returns the source bytes, marker included. A future "copy as plain text" (v1.1) should emit the label as `Note:`.

> **Marxy today.** Measured (probes `gh-alerts`, `other-admonitions`, and a rerun under `WIDE_POLICY`): `> [!NOTE]` parses as a blockquote whose first paragraph begins with the literal text node `[!NOTE]`, a soft break, then the body; the renderer prints the marker verbatim for all five types (and for lower-case `[!warning]`); `> **Note**` renders as a blockquote with a `<strong>` first word; `!!! note "Heads up"` and `:::tip … :::` render as ordinary paragraphs with the marker lines visible.

## 5. Collapsibles

**Evidence on hidden content.** No controlled study of collapsed sections in README-like documents was found. Nielsen Norman Group's guidance on accordions (a practitioner article that cites no experiment of its own) says an accordion can act as a table of contents, hurts findability when its heading is not descriptive enough to invite opening, and is wrong where readers are immersed in a continuous flow.[^nng] **[D]**. That splits cleanly for READMEs: `<details>` is mostly used for reference matter a reader may not want (per-platform install steps, long output, screenshots, history), which is what accordions suit, and only sometimes for prose, which they do not.

**GitHub's behaviour.** GitHub's docs describe `<details>` with `<summary>` collapsed by default, the `open` attribute for expanded, and markdown inside the block working when a blank line follows the summary.[^gh-collapsed]

**Find into closed content.** Browser Compatibility Data 8.1.3 records that `details` opens on a find-in-page match from Chrome 97, Firefox (partial from 139, full from 148) and Safari 26.2, which is flagged partial because the browser does not scroll correctly to the match (WebKit bug 304174; the current data file on the main branch, re-read in the skeptic pass), and `hidden="until-found"` from Chrome 102, Firefox 148 and Safari 26.2 with a similar caveat. `<details name>` (exclusive groups) is supported from Safari 17.2, Chrome 120, Firefox 130.[^bcd] I did not fetch the spec text for this, so the spec is not cited. Marxy's own Find (first match under 50 ms) does not run through the browser's, so it should open closed ancestor `details` itself and scroll after layout settles; depending on the webview's partial implementation would be a regression waiting on a WebKit fix. Keyboard operation of the native `summary` was not verified in this survey; styled summaries must stay focusable and are a test to write (below).

> **Default.** Honour the author's state: `<details>` renders closed unless `open` is present, the `summary` as a run-in bold line at body size with a small text glyph (`▸`/`▾`) as the only mark, no border or box. Find opens closed ancestors before scrolling to a match. "Open all sections" is a **view** state summoned from the palette, never a write to the buffer, so byte fidelity holds. Obsidian's `[!type]-` renders the same way (closed). **[D]** for honouring the authored state (converged: GitHub, Obsidian, MkDocs `???`); the glyph and run-in styling are design choices with no test.

> **Operation.** None new. "Copy section" already returns the source range that contains a closed `details`, so closed content is copied. An operation that toggled `open` in the file would edit the author's bytes and is out of scope for a reader.

> **Marxy today.** `details` and `summary` are **transparent** in the default policy (`TRANSPARENT` in `packages/core/src/sanitize/policy.ts`), so the block renders open with the summary as bare text and no provenance. Under `WIDE_POLICY` they are real elements, but measured: a `<details>` whose body is markdown after a blank line renders as an empty `<details><summary>More</summary></details>` followed by the body *outside* it. CommonMark ends an HTML block at the blank line, so open tag, markdown siblings and close tag are separate nodes. `fixtures/corpus/02-readme-real-world.md` (lines 48–49) has this shape. Honouring `details` therefore needs (a) a policy move and (b) a **pairing pass** in the pipeline that wraps the sibling blocks between an unbalanced `<details>` and its `</details>` in one element, carrying provenance from open to close. Re-run in the skeptic pass with Node 24, through `renderSafeHtml` with `options.policy` set to `WIDE_POLICY` (and `WIDE_RENDERED_POLICY`): the blank-line shape gives an empty `<details>` with the body as siblings; the same markup with no blank line (`<details><summary>…</summary>\ntext\n</details>`) keeps the body inside. Neither touches a frozen contract; (a) is in a CODEOWNERS-gated path and ADR-0009 §2 names `<details>` as a wide-policy element, so it needs an amendment. A further precondition, verified in `packages/theme/src/base.css`: it has no `details` or `summary` rule at all, so once they become real elements the browser's default disclosure marker and padding apply, off the 15 px grid. A closed or open `<details>` needs a marker, a summary line and a body inset written as grid multiples, and a row in the gate that measures block tops.

## 6. Mermaid and diagram fences

GitHub renders four fence languages (mermaid, GeoJSON, TopoJSON, ASCII STL) in issues, discussions, pull requests, wikis and markdown files.[^gh-diagrams] Its docs do not describe how; I could not verify that GitHub uses a sandboxed iframe (a GitLab merge request that does so for GitLab's own Mermaid rendering exists,[^gitlab-mermaid] but it is GitLab). Mermaid's own documentation defines four `securityLevel` values: `strict` (default; HTML in labels encoded, clicks disabled), `antiscript`, `loose`, and `sandbox` (rendering in a sandboxed iframe, which the docs mark as beta and say may break interactivity).[^mermaid-docs]

**Security record.** The advisory database has repeated XSS and HTML-injection entries against Mermaid itself: sanitisation of sequence-diagram labels (CVE-2025-54881), architecture-diagram icons through a d3 `html()` sink (CVE-2025-54880), `classDef` in state diagrams (CVE-2026-41149, mitigated by `sandbox`), and CVE-2026-41159, a CSS injection through `fontFamily`/`themeCSS` that applies outside the diagram under the default configuration (mitigated by `sandbox`), fixed in 10.9.6 and 11.15.0; downstream apps were also hit through per-diagram `%%{init}%%` directives that override the security level.[^mermaid-adv] I read advisory titles and search-result summaries, not the advisories in full. The lesson for Marxy is structural: a renderer of untrusted diagram text is a code-execution surface however well it is configured, so it must be sandboxed by construction, not by a setting the diagram can override.

**Licences.** From npm package metadata read on 2026-09-25: mermaid 12.0.0 **MIT**; its dependencies include d3 7.9.0 **ISC**, dompurify 3.4.16 **MPL-2.0 OR Apache-2.0**, dagre-d3-es, cytoscape, katex, roughjs, stylis, marked (all **MIT**), khroma (**MIT**, from its repository licence file; the registry's `license` field is empty), d3-sankey **BSD-3-Clause**, chevrotain **Apache-2.0**, and **elkjs**.[^mermaid-lic] The elkjs finding needs care. mermaid 12.0.0 declares `elkjs ^0.9.3` under `dependencies`, a hard dependency, not optional or peer (registry metadata and the repository's `packages/mermaid/package.json` agree). A `^0.9.3` range cannot reach 0.10 or later, and every elkjs 0.9.x release is **EPL-2.0** alone; the dual `EPL-2.0 OR GPL-3.0-or-later` appears only from elkjs 0.12.0, the current release, which mermaid's range does not select. So the accurate statement is: a plain `import 'mermaid'` pulls in an EPL-2.0 (weak, file-level copyleft) layout engine. That is disqualifying in Marxy's tree for a narrower reason than "GPL": ADR-0006's text names MIT/Apache/BSD/MPL allow-lists for grammars and patterns and forbids copyleft content generally, and the enforcing rule for dependencies is `PERMISSIVE` in `scripts/gate-licences.mjs`, which does not list EPL-2.0. Measured with that file's `classifyLicence`: `EPL-2.0` is `unknown` (an unknown licence fails the gate) and `EPL-2.0 OR GPL-3.0-or-later` is `copyleft`. Taking the EPL branch of the newer dual licence would not help, since EPL-2.0 is itself not on the list. Admitting EPL-2.0 would be an ADR amendment, a decision for the project, not something this chapter can assume. A separate MIT package `@mermaid-js/layout-elk` also depends on elkjs, which hints that ELK is an optional layout, yet mermaid 12.0.0 still declares it as a hard dependency; whether a bundler can exclude it was not verified. Until it is, "Mermaid, licence-clean" is not established. A `mermaid.min.js` found in the scratchpad (version not recorded) is about 5.6 MB raw and 1.6 MB gzipped, a size the desktop shell can afford but the bundle gate should record.

> **Default (v1).** Show the fence as source, as now, plus **one quiet caption** for diagram languages (`mermaid`, `plantuml`, `dot`, `d2`): a small muted line above the block, `mermaid · diagram source`, so the reader does not think the README is broken (the same reasoning as ADR-0009's remark on badges). The caption is one line, present only for those languages, and is not a per-block button. **[D]** (no test; nothing found on how readers interpret an unrendered diagram fence).

> **Default (later, if rendered).** Six requirements, none satisfied today: (1) **offline**: the library is bundled, nothing is fetched, fonts are Marxy's; (2) **sandboxed by construction**: render in an isolated frame with no network and no same-origin access and read back only the resulting SVG string, never inject Mermaid's DOM; `securityLevel: 'strict'` with `htmlLabels` off and directives that change the level ignored; (3) the SVG is reduced to an allow-list of SVG elements and shown through `img` so nothing in it executes; (4) **on the grid**: intrinsic height rounded up to a multiple of the 15 px unit, width capped at the measure; (5) themed from `--marxy-*` values so dark and light both hold contrast; (6) **the source one step away**: a summoned "Show diagram source" (or Source mode), and copy always yields the source. Licence disqualification in the paragraph above applies. **[D]**.

> **Operation.** "Copy code block clean" already copies a Mermaid fence's source. Rendering would add `copy-diagram-source` only if the source were not the block's own text, which it always is; no new operation.

> **Marxy today.** Measured: `\`\`\`mermaid` renders as `<pre><code class="language-mermaid">`, unhighlighted (`mermaid` is not on the Shiki allow-list, so there is no grammar to fail); `console` and `log` fences are plain for the same reason, unless a `console` grammar is added.

## 7. Links, anchors and the small inline elements

**Heading anchors.** GitHub's docs give the rules: lower-case, spaces to hyphens, punctuation removed, whitespace trimmed, duplicates numbered.[^gh-basic] The npm package `github-slugger` (ISC, version 2.0.0) implements them as a community port: lower-case, strip a generated character class that removes controls, punctuation and symbols except `-` and `_`, then replace each space with a hyphen; a repeated slug gains `-1`, `-2`.[^slugger] I ran it (source) on sample headings: `Install & Run` gives `install--run` (a double hyphen, because the ampersand is removed but both spaces remain), `API v2.0 (beta)` gives `api-v20-beta`, `Café ☕ menu` gives `café--menu`, and a leading emoji leaves a leading hyphen (`🎉 What's new` gives `-whats-new`). That the double hyphen and the leading hyphen match GitHub's output was not checked against GitHub itself; the docs page states only the rules. Because README authors write `[Install](#install-run)` against GitHub's slugs, a reader that generates different ids breaks intra-document links silently.

> **Default.** Every heading gets `id` = the slug above (with the duplicate counter) and the anchors resolve inside the document and across documents in the index (`docs/guide.md#setup`). Do not display anchors or a permalink glyph; the outline is the summoned view. **[D]** (GitHub convention, ported and tested by a widely used library).

> **Marxy today.** Headings carry no `id` in the goldens, although `docs/design/02-render.md` (line 17) specifies the GitHub algorithm. `followLink` in `apps/desktop/src/selection/view.ts` passes every `href` to `shell.openExternal`, which the Tauri shell does not implement, so a relative markdown link does nothing. Relative links to other markdown files in the repository should open in Marxy (ADR-0012's repository root), other files in the system handler after confirmation, `http`/`https` in the browser after showing the target host (see [Trust and safety](07-trust-safety.md)).

**Emoji shortcodes.** The CommonMark 0.31.2 specification and the GFM 0.29 specification contain no mention of emoji (I searched both pages' text and found zero occurrences); GitHub's docs describe `:EMOJICODE:` as a GitHub feature and point to a community cheat sheet.[^gh-basic][^specs] A README written on GitHub therefore contains `:tada:` where its author sees 🎉, and Marxy prints the literal text.

> **Default.** Convert `:name:` to its glyph in **text nodes only** (never in code spans, fences, link destinations or raw HTML), from a bundled table (`gemoji`, MIT per the npm registry; table size and the exact mapping of that package to GitHub's list were not checked). It is a render pass like smart typography; the buffer keeps `:tada:`, provenance is unchanged, and a copy of the selection yields the source text. Unknown names stay literal. **[D]**.

> **Marxy today.** Measured: `Shipped :tada:` renders as literal text.

**`kbd`, `sub`, `sup`.** All three are on the default allow-list (`policy.ts`, `MARKDOWN_EQUIVALENT`) and render as elements today; the probe shows `<kbd>Ctrl</kbd>+<kbd>C</kbd> H<sub>2</sub>O x<sup>2</sup>` surviving. The remaining work is typographic: they must not grow the 30 px line box, and `kbd` needs a treatment that is not a boxed keycap (constraint 4). That is a taste question; the row goes to the review queue, not a gate. **Footnotes** follow the sibling's rule: a reference opens in place as a note, with a return link as the fallback.[^ct07] GitHub's docs give only the caret-numbered definition syntax.[^gh-basic]

## 8. Copying install commands

**What GitHub does.** No GitHub documentation or changelog on the copy button's treatment of prompts was found. The evidence is user reports: a community feature request opened in October 2022 (still receiving comments in May 2026, with no GitHub staff response in the thread) asks it to strip a leading `$`, and quotes the resulting doubled-prompt paste error;[^gh-copy] a github/docs issue from 2022-10-27, since closed, reports the same for GitHub Docs' own copy buttons.[^gh-docs-copy] The prompt `$ ` is decoration for humans, not part of the command. Sphinx's copy button plugin, an MIT-licensed tool, shows one workable rule: when a block has lines beginning with a configured prompt, copy *only* those lines with the prompt removed, and when none has one, copy the whole block; it can also use the highlighter's own prompt/output classes for `console` blocks.[^copybutton] **[D]** (converged in shipping tools; no study of reader error rates was found).

> **Default.** Rendered blocks are verbatim, prompts included (the reader sees what the author wrote, and the buffer is never touched). The reader gets the *clean command* from the operation below.

> **Operation.** `copy-command`, `string → clipboard`, `appliesTo: ['block']`, pure, offered only when the selection resolves to a fenced code block **and** it contains at least one prompt line under the rules below; otherwise "Copy code" is the only offer. `replacement` is the block unchanged (nothing is spliced). Rules:
> 1. A language of `console`, `shell-session`, `shellsession`, `terminal`, or the empty language: a prompt is `$ `, `% `, `# ` (only here, root prompt), `> ` continuation, or `PS …> `. In `sh`, `bash`, `zsh`, `shell`, only `$ ` and `% `; `#` there is a comment and must never be stripped, and `> ` is a redirect or continuation that is not a prompt.
> 2. Output is every line after a command line that is not itself a prompt line, except a **continuation**: a line following one that ends in `\`, or a `> `-prefixed line, and the body up to the terminator of a here-document opened on a command line. Continuations and here-document bodies are kept, joined verbatim.
> 3. If any prompt line exists, copy the stripped command lines only, one per line. If none exists, the operation is not offered.
> 4. **No trailing newline**, unlike "Copy code" (`clipText` appends one). A trailing newline on a pasted command can execute it in a terminal without the reader pressing Return. This is engineering reasoning, not a sourced finding; it is the safer default and costs a keypress.
> 5. Unicode that changes what a terminal executes (bidi controls, zero-width, tag characters) makes the operation refuse and say why; see [Trust and safety](07-trust-safety.md).
>
> Applicable to a block; needs no selection inside it. Grade **[D]**.

> **Marxy today.** `copy-code-clean` (`packages/core/src/operations/copy-code-clean.ts`) copies the block's value verbatim, prompts included, with a trailing newline added by `clipText`. No prompt handling exists. `sh`/`bash` are on the Shiki allow-list; `console` is not, so a `console` fence is unhighlighted (probe `console-fence`), which is correct for a session.
