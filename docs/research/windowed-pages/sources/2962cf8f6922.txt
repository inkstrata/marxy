Issue body actions

Describe the issue

One of our users on Replit has a pretty unsettling file that includes an enormous expression concatenating thousands of strings. If you're on Firefox this will be fine, but on Chrome it makes Lezer hit the stack limit. If you bog down the browser enough to where Lezer avoids parsing the entire file for a little bit, it won't crash immediately on Chrome. I'm not sure what happens if you stall Lezer repeatedly and cause the entire file to be incrementally parsed in small chunks.

There is also a line near the bottom of this expression with what's clearly a mistake:

+ "unhealthy,-0.47\n"oh boy yeah let me

I'm not sure if this mistake is part of the bug here, but just letting you know it's there.

I've linked a reproduction, but you'll have to copy the document from the linked gist yourself. Including the doc in the repro generates a hilariously huge URL, lol

See also #630, which puts a limit on parse stack depth. Unfortunately, in a bottom-up parser like this, left-associative rules will not actually grow the parse stack (it'll keep reducing the left hand side before continuing), so that that limit fails to fire here. It turns out to be really annoyingly difficult to detect a situation like this during parsing, and similarly difficult to address it during tree-construction. Still looking for a reasonable way to solve this.

Sure, thank you for asking.

I have written a grammar used for finding the start and end of SQL statements in a particular dialect of SQL. It lumps almost everything into a general token and accepts a semicolon to indicate the end of a statement, except for certain types of statements that go into a scripting format that can be nested, declare variables, have loops. That format can have semicolons that don't indicate the end of a statement. I suppose it's an "island grammar".

Prior to that code addition, there was a 120,000 character MERGE INTO ... FROM VALUES statement, likely programmatically generated, that had very many entries which was correctly parsed as one statement.

Imagine like

MERGE INTO BLAH
USING ( SELECT $1 AS FOO, $2 as BAR ... $10 as BAZ )
FROM VALUES ( 'foo1', 123123, ...'foo2' ), ( 'foo3', 789789, ...'foo4' ), ...
// onwards to 120,000 characters of this

After that code change in lezer/lr 1.3.0, this single statement was parsed as multiple, with about 1080 "words" in each chunk, where I'm using word here to mean a series of characters delimited by whitespace.

The area at which "no parse" occurred was valid so I put breakpoints in the lezer code suspecting that change, and saw that I do end up with a "this.bigReductionCount" of 1001 with a stacks.length of 1 which enters that if condition.

It seems that the way I've written my grammar in conjunction with that sql statement that repeats finding a general token, makes it get into that state and it stops parsing there, then starts over with a new statement.
