# 03 · Incremental, chunked and off-thread Markdown parsing

> Question: how to make parsing of 1 to 50 MB Markdown incremental, chunked or off the main thread, and which inputs make Markdown parsers super-linear. Answer in brief: micromark is slow (about 1.3 MB/s parse plus render, 10 to 100 times slower than native parsers) and had at least one quadratic bug that is now fixed, but it is not the only cost. The safe design is to parse in a worker, in slices cut at blank-line top-level block boundaries, with a document-wide link-definition pre-scan, and to send the main thread a compact block table plus per-block HTML strings (or one JSON string), not an AST. Untrusted-input caps (nesting depth, bracket and delimiter counts, line length) must be applied before the parse because micromark's own guarantees are weaker than those of cmark or pulldown-cmark.

## TL;DR
- micromark parse plus render measured about 778 ms for ~1 MB (1.32 MB/s); remark 1134 to 1439 ms; markdown-it about 90 ms parse-only (102.62 ms parse plus render, so about 100 ms like-for-like with the micromark figure); md4c (md4w) about 8.6 ms; pulldown-cmark about 4.4 ms [PRS-01]. Budget roughly 1 s per MB in the worker, and the 78 s open is therefore not parsing alone.
- The cmark pathological suite (25 cases) is the right fuzz corpus; one quadratic (event splices) was fixed in 2024, remark's nested-list report (#1010, 2022) was closed in 2025-02 by a documentation change, not a fix, and micromark has open quadratic reports from Sep to Nov 2026 [PRS-02][PRS-03][PRS-13]. Public replies: a remark team member (2022) calls polynomial time "not a security vulnerability" and welcomes a pull request; closing the issue in 2025, the maintainer wrote that performance improvements "would go in micromark".
- Lezer's Markdown parser reuses fragments only at block boundaries, never directly after an indented code block, list item or list; it does not validate link references, which is what makes it incremental [PRS-05].
- Link reference definitions "can come either before or after the links that use" them, so a whole-document definition index is the correct (and already present) answer; parse-ahead to restart points is the part to harden [PRS-06].
- Cross a worker boundary with strings or transferable buffers, not object trees: in a 2016 benchmark stringifying was faster than posting an object (150 ms plus for objects) [PRS-08].

## Recommendation for this setup

1. **Move the parse into a worker now** (one module worker owning bytes, definition index and block table). Keep `packages/core` DOM-free, which it already is, so it runs unchanged in a worker. Only the worker calls `parseMarkdown`; the main thread gets messages. Rationale: at about 1 s per MB, a 5 MB file blocks the main thread 4 to 7 s even if slices are perfect, and slicing on the main thread only delays the freeze into many tasks.
2. **What crosses back** (PRS-08, PRS-09): per slice, post one message holding (a) a compact block table as typed arrays (`Uint32Array` triples: start byte, end byte, kind; transferred, not cloned), (b) the sanitised HTML for each block as one string array or one concatenated string with an offsets `Uint32Array`. Do not post the mdast-like tree unless a panel truly needs it; panels (links, metadata, outline) should receive small derived tables made in the worker. Measure structured clone of the real tree once, in WKWebView, before ruling it in or out; no current benchmark exists for JSON trees [PRS-10].
3. **Slice at safe restart points.** Slice only at a blank line that ends a top-level block, outside fences, HTML blocks and indented code, with no open list (a list can continue after blank lines; Lezer refuses to stop after CodeBlock, ListItem, OrderedList, BulletList for this reason) [PRS-05]. Safe: a blank line at column 0 between top-level paragraphs, ATX headings, thematic breaks, closed fences. Unsafe: inside a fence (closed only by matching fence, or end of file), inside an HTML block type 1 to 5 (ends at its end marker, not a blank line), after an indented code block (blank lines continue it), within a list or blockquote with lazy continuation, immediately before a line that would turn a paragraph into a setext heading, and any line starting with `[` that may be a definition [PRS-06].
4. **Definitions first.** Do a linear pre-scan in the worker over the bytes for line-start `[label]:` and footnote `[^x]:` candidates (the current index design). Keep the rule "a definition change reparses the whole file", but move that reparse into the worker, run it cancellable, and keep showing the old page. Cap definition count and the total expansion (pulldown-cmark caps reference expansion at `max(text.len, 100_000)`) [PRS-04].
5. **Pre-bound hostile input before micromark** (the app's `budget`/`take` shape): cap container nesting (blockquote and list depth, e.g. 64 to 100), total `[` and `![` counts per paragraph, delimiter run counts per paragraph, table columns (cmark-gfm CVE-2023-37463; pulldown-cmark limits to 1 << 18 autocompleted cells), and paragraph length. Over the cap, render that block as an escaped literal block with a note and keep going. Test with the 25 cmark pathological cases, scaled by 2x and 4x, in a doubling check [PRS-02][PRS-04].
6. **Time-budget and cancel.** Parse slices of about 100 to 300 KB; after each, check a cancel token (a generation counter posted from main) and a deadline. CodeMirror's budgets are a useful template: 20 ms applied immediately on change, 25 ms minimum idle slice, 3000 ms per 30000 ms chunk of background work, no parse more than 1e5 characters past the viewport [PRS-07]. Parse the viewport region first, then outward, then the rest, so the first screen appears at a few tens of milliseconds regardless of size.
7. **Consider a native parser for 1 to 50 MB only after measuring.** md4c via wasm is about 20 to 40 times faster than micromark but at 91.7 percent CommonMark conformance and without micromark's extension set (front matter, maths, byte-exact events). A byte-offset-preserving parser would have to replace the provenance pipeline. A cheaper first step is using it (or the Rust shell, which has pulldown-cmark available) only to find block boundaries for slicing; unverified and a separate spike [PRS-01].
8. **Do not** adopt tree-sitter-markdown for the page (its README: "not recommended to use this parser where correctness is important") or Lezer for rendering (no link reference validation); both are fine for source-view colouring, which CodeMirror already does [PRS-05].

**Rules for new features**
- Markdown is parsed only in the parse worker; a feature on the main thread asks the worker for a derived table, never calls `parseMarkdown` or `micromark` on the whole file.
- A message between the worker and the main thread carries strings, transferred typed arrays or numbers; a test fails if a message contains an array of more than 1,000 plain objects.
- Any new parse entry takes a byte range and a cancel token, and checks the token at least every 20 ms of work or every block.
- A parse slice starts and ends on a top-level block boundary the pre-scan proved safe; no slice starts inside a fence, HTML block, list or indented code.
- Every new Markdown construct or extension ships with a doubling test (input n and 2n, work counted, ratio under 2.5) and a case in the pathological suite.
- A parse that adds container depth, bracket or delimiter counts must `take(n)` from a budget before micromark sees the text.
- A change to link or footnote definitions re-runs the definition index only; it must not re-parse the whole file on the main thread.
- No whole-file `Array.prototype.splice`, repeated `slice` or `concat` of event or token lists in new parse code; use a gap buffer or batch edits.

## Findings

### PRS-01 · Parser throughput: micromark is the slowest practical option, native parsers are 10 to 200 times faster  `[measured]`
A benchmark sweep generated 2026-09-25 (median of 7 runs, Node v26.8.1, AMD EPYC, from a competing project, so treat the ordering with care) gives, for parse plus render of 48.7 KB: micromark 32.10 ms, 1.48 MB/s; remark 38.55 ms; marked 2.78 ms; markdown-it 3.42 ms; and, for about 1 MB: micromark 777.83 ms, 1.32 MB/s; remark 1439.29 ms, 0.71 MB/s; pulldown-cmark plus push_html 4.40 ms, 232.55 MB/s; md4w (md4c) 8.64 ms, 118.39 MB/s [1]. Parse only at about 1 MB: markdown-it 89.82 ms (11.39 MB/s), marked 65.78 ms, remark 1134.23 ms (0.90 MB/s) [1]. md4w scored 91.7 percent of CommonMark spec examples there versus 100 percent for micromark and markdown-it [1]. A Chrome 126 browser benchmark ran markdown-it at 1343 ops/s against micromark at 80.8 ops/s (single run, secondary) [2]. The micromark maintainer wrote that micromark "is currently slower than what used to be in remark-parse. About 50% slower" and "I don't see it ever being as fast as say markdown-it, because the priorities are different" [3]. Extrapolated, 50 MB through micromark is on the order of 40 s in Node, longer in WKWebView; this is inference. No memory-per-MB figure for micromark was found (see PRS-11).

### PRS-02 · cmark's pathological suite lists the known super-linear inputs  `[confirmed]`
cmark's `pathological_tests.py` has 25 cases with a 5 s timeout per case: nested strong emphasis (`*a ` x 32500 then `b` then ` a** a*`), many emphasis closers without openers (`a_ ` x 32500), openers without closers (`_a `), `a]` x 32500, `[a` x 32500, mismatched `*a_ ` x 25000, `[ a_` x 25000, `[ (](` x 40000, `![[]()` x 160000, nested brackets (`[` x 25000, `a`, `]` x 25000), `> ` x 25000, 500 lines of deeper-indented `* a`, backticks `e` plus N backticks for N = 1..2499, unclosed `[a](<b` and `[a](b` x 30000, `<!--` x 300000, `- ` x 30000 then `x` then 30000 newlines, the same inside a blockquote, `>` x 100000 then `a*` x 100000, and about 25000 reference definitions hashing to one bucket [4]. The file uses a wall-clock timeout, not a complexity check [4]. Comrak and pulldown-cmark port this idea: comrak's tests run with `#[timeout(4000)]` for emphases, table columns and footnotes [5]. Use the list as the seed fuzz corpus, scaled by doubling.

### PRS-03 · What micromark and remark have fixed or still have  `[confirmed]`
Fixed: micromark/micromark#169 (March 2024) reported that parsing generated MDX with long code-in-JSX segments was "unmanagably slow"; PR #171 added a `SpliceBuffer` (a gap buffer) so that "the largest samples go from taking about 55 seconds to parse to taking less than 2 seconds", described as going from approximately quadratic to approximately linear [6][7]. It reached `micromark-util-subtokenize` 2.0.1 [8]. The same root cause (repeated array splices) then appeared in the Rust port as `add_impl` in the edit map [8]. Reported in 2022 and since closed: remark issue #1010 (2022) shows `"* ".repeat(8000) + "a"` taking 27.79 s elapsed and ending in `RangeError: Maximum call stack size exceeded`, "quadruples each time the input size is doubled"; the reporter says a private reply indicated that "security against computational complexity attacks is not considered to be goal of this project" [9]; that is the reporter's account of a private reply, not a public statement. The first public reply (a remark team member, July 2022) says polynomial time "does not meet the standard of" a DDoS or "a security vulnerability" (the page's own wording: "Polynomial time is unfortunate but at times necessary"), and that "a pull request would be welcome" [9]; it concerns remark, not micromark. The issue was closed on 2025-02-12 by commit cdab8fa, which adds a paragraph on security to the readmes: a documentation change, not a fix. Closing it, the maintainer wrote "Improvements to performance are welcome. Most of that would go in micromark!" [9]. The lead checked the commit's files and message through the GitHub API on 2026-11-27. So deep lists are not known to be fixed in micromark. (A first-pass correction had called the issue fixed; the second pass and the lead found that wrong.) Remark's list parser then was remark-parse v9 or later on micromark (remark 14.0.2), so deep lists in micromark remain a risk to retest. See also PRS-13 for micromark's own open quadratic reports. Also reported: remark-gfm tables, where ~187 rows took 300 ms and 2000 rows around two minutes in discussion 978 (user reports of 2022-era versions, current status unknown) [10]. Not confirmed: a micromark test against each of the 25 cmark cases. See PRS-11.

### PRS-04 · cmark-gfm CVEs and how pulldown-cmark bounds the same classes  `[confirmed]`
cmark-gfm CVE-2023-37463 (GHSL-2023-117 to 119, fixed in 0.29.0.gfm.12): a table with a very large number of columns is quadratic because a linked list is searched per cell to find its alignment [11]. cmark CVE-2023-24824 (GHSL-2023-031): "a very deeply nested list followed by a large number of empty lines can trigger quadratic behavior" in `check_open_blocks` [12]. pulldown-cmark's guide lists the guards it uses: link nesting depth `LINK_MAX_NESTED_PARENS` = 32, `MAX_AUTOCOMPLETED_CELLS` = `1 << 18` for table empty cells, and a link reference expansion limit of `text.len().max(100_000)` [13]. These are concrete numbers to adopt as pre-parse caps in this app.

### PRS-05 · Lezer's Markdown parser: fragment reuse at block boundaries only  `[confirmed]`
`@lezer/markdown` consumes fragments of old trees "for its incremental parsing", and "in order to be single-pass and incremental, it doesn't do" some CommonMark work, "specifically, it doesn't validate link references", so `[a][b]` becomes a link even without a definition [14]. In the source, `reuseFragment` takes nodes from the old tree only when `matches(this.block.hash)` (same parent context hash), and `takeNodes` says never to stop directly after an indented code block and keeps a list `[CodeBlock, ListItem, OrderedList, BulletList]` of types it will not end on [15]. CodeMirror's language layer drives it with time budgets: `Apply = 20` ms on change, `MinSlice = 25` ms idle, `Slice = 100`, `MinPause = 100`, `MaxPause = 500`, `ChunkBudget = 3000` ms per `ChunkTime = 30000` ms, `ChangeBonus = 50`, `MaxParseAhead = 1e5`, `InitViewport = 3000` [16]; `ensureSyntaxTree` defaults to a 50 ms timeout and `forceParsing` to 100 ms [16]. Lezer's authors accepted incorrect link semantics for editor speed, which is why it cannot replace micromark for rendering. Lezer is already in the app through CodeMirror: reuse it for source-view structure and for "which block contains byte x" queries in Source, not for the page.

### PRS-06 · Non-locality: which constructs break local reparse  `[confirmed]`
The CommonMark spec says link reference definitions "can come either before or after the links that use" them, so any edit to a definition can change any link anywhere [17]. A definition "cannot interrupt a paragraph", an indented code block "cannot interrupt a paragraph", and "HTML blocks of type 7 cannot interrupt a paragraph", so the classification of a line depends on the line above [17]. Lazy "paragraph continuation text" lets a line without a container marker continue a paragraph inside a blockquote or list, so a restart inside a container is unsafe [17]. Fences close only on a matching fence or end of container or file, and HTML blocks of types 1 to 5 end on an end marker, not a blank line (spec text; not re-quoted). Consequence: the safe restart point is a blank line at top level, not in a fence, HTML block 1 to 5, indented code, list or blockquote, with the next block start not a continuation; the Lezer rule (PRS-05) is the same list. An edit that creates or closes a fence changes everything after it, so the reparse must run to the next point whose old and new states agree (compare the block's start state: open fence, open HTML block, list depth) rather than a fixed window.

### PRS-07 · Tree-sitter-markdown is for highlighting, not rendering  `[confirmed]`
Its README says the goal is "to provide syntactical information for syntax highlighting" and "it is not recommended to use this parser where correctness is important", because Markdown is restricted by tree-sitter's grammar rules; it parses block structure and inline structure as two grammars [18]. Not benchmarked here. It would add a native or wasm dependency for no rendering gain; the app has no use for it that CodeMirror/Lezer does not already cover.

### PRS-08 · What crosses the worker boundary: strings and transferables beat object trees  `[measured]`
Nolan Lawson's 2016 benchmark (50,000 messages, Chrome, Firefox, Safari, Edge of the time): "it's actually faster to JSON.stringify() then postMessage() a string than to postMessage() an object", and wrapping a stringified payload in an object loses the gain [19]. A 2011 test of a 32 MB `ArrayBuffer` took 302 ms round trip by structured clone and 6.6 ms by transfer, on a 2010-era laptop [20]. Both are old, and Lawson notes that recent Chrome no longer shows the cliff; no 2024 to 2026 benchmark of a large JSON-like tree in WKWebView or WebView2 was found. Direction: HTML strings, typed-array block tables and `ArrayBuffer`s transferred; a tree only on demand.

### PRS-09 · Streaming and yielding in micromark  `[likely]`
micromark's design makes a streaming API available, but the issue that discusses its trade-off says the document "is constantly changing" is "typically not true for micromark", that it "needs to be complete, perfect" and the maintainers did not make incremental reparsing a goal [21]. The app's existing slice design therefore has to be built on top (splitting input and merging events), as it already is; mdast-util-from-markdown has no yield points, so a slice of n bytes blocks for its whole duration. Slice sizes must be set from the measured 1.3 MB/s (a 200 KB slice is about 150 ms), not from line counts, which is why a worker matters more than the slice size. The micromark API read for this was via issue text only; the docs were not opened (see Open questions).

### PRS-11 · No micromark memory-per-MB figure and no micromark result against the cmark suite  `[absence]`
Neither a memory-per-MB measurement for micromark or mdast-util-from-markdown nor a published pass/fail of micromark against the cmark pathological cases was found. The remark #1010 run reported `182780maxresident` kB at its crash on 16 KB (about 11 MB per KB under attack; not a normal figure) [9].
**Searched:** GitHub issue search via WebSearch "micromark slow large document performance issue github", "micromark deeply nested stack overflow quadratic"; micromark discussion 29 and issues 9, 169; ox-content benchmark page (no memory column).

### PRS-12 · Table parsing in micromark-extension-gfm-table was slow in 2022 reports  `[likely]`
Discussion 978 reports ~187 rows taking 300 ms with micromark 3.0.10 and remark-gfm 3.0.1, and 2000 rows about two minutes; another comment gives 30.86 ms without versus 34.455 ms with `gfmTable` on a small input [10]. The maintainer's reply that the cost is in checking two lines per row suggests per-row work grows with table size; not confirmed against current versions. Test the app's GFM table path with a 20,000-row table before shipping.

### PRS-13 · micromark has open quadratic-time reports from September to November 2026  `[confirmed]`
Open issues on micromark/micromark: #246 "Block quotes, nested lists, and setext headings take quadratic time in 4.0.3" (opened 2026-09-28): a 32 KB input of `'> a\n\n'.repeat(6554)` takes 3.2 s in 4.0.3 against 168 ms in 4.0.2, and "Four times the input takes 20 to 25 times as long" [22]. #263 "Quadratic time in initializeDocument when many containers close" (2026-11-11): "A 1 MiB document of short block quotes takes about 107 s" [23]. #265 "Lazy continuation lines in a list item or block quote take quadratic time" (2026-11-12), reproduced in 4.0.2: 1000 lines 67 ms, 8000 lines 3.0 s [24]. #246 links an open fix PR #249 (EditMap.consume), which it says brings times back to the 4.0.2 level [22]. A further open PR, #236 (HTML compile performance), is known only from the verifier's GitHub search and was not read: `[unverified]`. All three issues were open when read, 2026-11-27. Consequence: the 2024 `SpliceBuffer` fix (PRS-03) is not the end of micromark's quadratic cases, and a 1 MB document of block quotes can take over a minute in the current release. The app should keep a size and time budget and a cancel path for the worker parse.

## Options compared
| Option | Fit for this app | Cost | Risk | Verdict |
|---|---|---|---|---|
| Keep micromark, move to worker, slice at safe points | High: keeps provenance, extensions, sanitiser | 1 to 2 weeks | Main-thread freeze disappears; worker pipeline needs cancel and generation tokens | Do first |
| Whole parse on main thread, slices with `scheduler.yield` | Low: slices of ~150 ms still block input; contention with typesetting | Low | Ongoing jank | No |
| Native parser (md4c wasm, pulldown-cmark in Rust shell) | Medium: 20 to 200 times faster, but different extension set and event model | Large (provenance, GFM, maths, front matter) | Conformance 91.7 percent for md4w; byte ranges must be rebuilt | Spike, after worker |
| Lezer Markdown for the page | Low: no link reference validation, tree not mdast | Medium | Wrong links on page | Source view only |
| tree-sitter-markdown | Low | Medium | "not recommended where correctness is important" | No |
| Pre-parse caps (depth, brackets, columns, definitions) | High | Low | Truncates hostile files visibly | Do with the worker |
