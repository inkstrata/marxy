Linter Plugins

Biome supports two forms of plugins:

GritQL, a powerful DSL to build small and expressive rules.

JavaScript, which allows you to tap into Biome’s infrastructure, such as CST, semantic model, and more.

Decide the plugin format
Section titled “Decide the plugin format”

It’s important you understand how the two plugin formats work so that you can make an informed decision on how
they will impact your work, your users, and Biome itself.

GritQL:

For Biome to enable plugins for a language, both GritQL and Biome must support it.

It’s a DSL; you have to learn how it works. A DSL plugin can be more expressive and require way less code to write, depending on the use case.

Plugins run on every file, regardless of whether the content of the file matches the query.

Plugins use a different pipeline from the one used by Biome’s Rust lint rules, and they don’t have access to information such as the semantic model, file kind, etc.

The memory usage is minimal and can be controlled by Biome.

JavaScript:

They can support the same languages that Biome’s Rust lint rules support.

They are very verbose, so writing a rule for a small thing could take 10x more lines of code compared to GritQL.

They have access to more information, such as the file being analyzed, the semantic model, CST navigation, and more.

It’s way easier to write a plugin that can negatively impact the performance of downstream users.

The memory used by the plugins can’t be controlled by Biome.

GritQL plugins
Section titled “GritQL plugins”

Biome Linter supports GritQL plugins. Plugins can match
specific code patterns, report customized diagnostics, and suggest fixable
rewrites.

Here is an example of a plugin that reports on all usages of Object.assign():

plugin.grit

1

`$fn($args)` where {

2

$fn <: `Object.assign`,

3

register_diagnostic(

4

span = $fn,

5

message = "Prefer object spread instead of `Object.assign()`"

6

)

7

}

You can put a GritQL snippet in a file anywhere in your project, but make sure
you use the .grit extension. Then, you can simply enable it as a plugin with
the following configuration:

biome.json

1

{

2

"plugins": ["./path-to-plugin.grit"]

3

}

can see its results when running biome lint or biome check. For example:

Rewrite behavior:

Without --write, rewrites are shown as suggestions but not applied.

With --write, Biome applies plugin rewrites marked with fix_kind = "safe".

With --write --unsafe, Biome also applies unsafe plugin rewrites.

If fix_kind is omitted, the rewrite is treated as unsafe by default.

Restricting Plugins to Specific Files
Section titled “Restricting Plugins to Specific Files”

By default, a plugin runs on every file Biome processes. However, you can use the includes option to restrict files and folders where the plugin can or can’t run.

In the following example, the first plugin only runs on files inside
src/components/. The second plugin runs on all files that have the extension .ts under the src/ folder, except for files that end with .test.ts in the src/ folder:

biome.json

1

{

2

"plugins": [

3

{

4

"path": "./react-plugin.grit",

5

"includes": ["src/components/**"]

6

},

7

{

8

"path": "./ts-only-plugin.grit",

9

"includes": ["src/**/*.ts", "!src/**/*.test.ts"]

10

}

11

]

12

}

When includes is set, the plugin only runs on files that match at least one
positive pattern and are not excluded by a negated pattern. Patterns follow the
glob syntax reference.

Resolve plugins from shared configurations
Section titled “Resolve plugins from shared configurations”

By default, Biome resolves plugin paths in a shared configuration from the directory containing the configuration that extends it. To load a plugin that ships with the shared configuration, set resolutionKind to "config":

biome.shared.jsonc

1

{

2

"plugins": [

3

{

4

"path": "./plugins/no-object-assign.grit",

5

"resolutionKind": "config"

6

}

7

]

8

}

Then extend the shared configuration:

biome.json

1

{

2

"extends": ["./biome.shared.jsonc"]

3

}

Biome resolves the plugin path from the directory containing biome.shared.jsonc, while includes globs are still resolved from the directory containing the extending configuration.

See plugins.<ITEM>.resolutionKind for the full option reference.

Target Languages
Section titled “Target Languages”

A GritQL snippet always attempts to match against a given target language.
If no target language is specified, JavaScript or one of its super languages is
assumed.

If you want to use a different target language, you must specify it explicitly.
For example, here is a CSS plugin to report any selector that sets a color
outside the allowed .color-* classes:

plugin.grit

1

language css;

2

3

`$selector { $props }` where {

4

$props <: contains `color: $color` as $rule,

5

not $selector <: r"\.color-.*",

6

register_diagnostic(

7

span = $rule,

8

message = "Don't set explicit colors. Use `.color-*` classes instead."

9

)

10

}

Biome currently supports JavaScript, CSS, and JSON target languages.

Plugin API
Section titled “Plugin API”

In addition to Grit’s
built-in functions,
Biome currently supports one extra function:

register_diagnostic()
Section titled “register_diagnostic()”

Registers a diagnostic to be reported whenever the pattern matches.

Supports four arguments:

span (required): The syntax node to attach the diagnostic to. This is
typically a variable that you matched within a code snippet.

message (required): The message to show with the diagnostic.

severity: The severity of the diagnostic. Allowed values are: hint,
info, warn, and error. By default, error is used.

fix_kind: Safety of an associated rewrite fix (safe or unsafe). This is
only relevant when the pattern also uses the rewrite operator (=>). By
default, fixes are treated as unsafe.

JavaScript plugins
Section titled “JavaScript plugins”

Caution

JavaScript plugins are in the Developer Preview stage. Breaking changes can happen in patch releases, and some features are missing. Share your feedback in the JavaScript plugins tracking issue.

Biome accepts .js and .ts as file extensions. If you decide to use TypeScript to write a plugin, we strongly recommend installing the @biomejs/runtime package, which provides the relevant types.

The plugin must export an object composed by the defineRule function. The object must have two fields:

query: which CST nodes to query.

run: the core logic of the lint rule. If the rule detects a violation, use the function registerDiagnostic to return the node to highlight, the severity of the diagnostic, and a message.

plugin.ts

1

import { defineRule, ast, registerDiagnostic } from "@biomejs/runtime/plugin"

2

3

export const noAssign = defineRule({

4

query: ast("JS_CALL_EXPRESSION"),

5

run(node, ctx) {

6

registerDiagnostic(node, "error", "Can't assign anything.")

7

}

8

})

Query APIs
Section titled “Query APIs”

You use query to tell the plugin which nodes to inspect. You can select nodes by their syntax kind with ast or semantic, or select them by matching a GritQL pattern with grit.

To find the syntax kind of a node, use the command biome inspect file or the playground. Each node has a name assigned by the Biome grammar, usually in all caps. For example, the name associated with the debugger statement is JS_DEBUGGER_STATEMENT, so you can import its interface called JsDebuggerStatement and use the kind field:

plugin.ts

1

import { defineRule, ast, JsDebuggerStatement } from "@biomejs/runtime/plugin"

2

3

export const noAssign = defineRule({

4

query: ast(JsDebuggerStatement.kind),

5

})

ast query
Section titled “ast query”

Type: string | ...string, and an optional { semantic?: boolean } options object

It accepts one name or a list of nodes to query. Pass { semantic: true } as the last argument to make the semantic model of the current file available via ctx.model.

plugin.ts

1

import { defineRule, ast, registerDiagnostic } from "@biomejs/runtime/plugin"

2

3

export const noAssign = defineRule({

4

query: ast("JS_CALL_EXPRESSION", "JS_DEBUGGER"),

5

run(node, ctx) {

6

registerDiagnostic(node, "error", "Can't assign anything.")

7

}

8

})

plugin.ts

1

import { defineRule, ast, registerDiagnostic } from "@biomejs/runtime/plugin"

2

3

export const noAssign = defineRule({

4

query: ast("JS_CALL_EXPRESSION", "JS_DEBUGGER", { semantic: true }),

5

run(node, ctx) {

6

const model = ctx.model;

7

registerDiagnostic(node, "error", "Can't assign anything.")

8

}

9

})

grit query
Section titled “grit query”

Type: string, and an optional { semantic?: boolean } options object

It accepts a GritQL pattern and selects the nodes and tokens that the pattern matches, instead of selecting them by syntax kind. This is useful when matching a snippet requires inspecting the shape of several AST nodes, which would otherwise take several checks in run.

plugin.ts

1

import { defineRule, grit, registerDiagnostic } from "@biomejs/runtime/plugin"

2

3

export const noConsole = defineRule({

4

query: grit("`console.log($args)`"),

5

run(node) {

6

registerDiagnostic(node, "error", "Unexpected console.log.")

7

}

8

})

The pattern is executed against the analyzed file, and run is called once for each match. When a pattern matches a sequence of nodes, such as several sibling statements, run is called for each node in the sequence. The sequence must match exactly, so `foo(); bar()` doesn’t match a list that also contains baz();:

plugin.ts

1

export const noFooThenBar = defineRule({

2

query: grit("`foo(); bar()`"),

3

run(node) {

4

registerDiagnostic(node, "error", "Don't call foo() immediately before bar().")

5

}

6

})

A grit query can’t contain a rewrite (=>), because the query only selects nodes and doesn’t edit the source. Report violations from run instead. The plugin fails to load if the pattern is invalid or contains a rewrite. The pattern must target JavaScript; patterns that declare another target language are not yet supported.

By default, run doesn’t receive the semantic model. If your rule needs to inspect bindings or scopes, pass { semantic: true } as the second argument to make ctx.model available, similar to a semantic query:

plugin.ts

1

export const noConsole = defineRule({

2

query: grit("`console.log($args)`", { semantic: true }),

3

run(node, { model }) {

4

// Inspect the bindings of the logged arguments if needed.

5

}

6

})

Note

Variables captured by a Grit pattern, such as $args in `console.log($args)`, aren’t exposed to run yet.

Run APIs
Section titled “Run APIs”

The run function accepts two arguments:

The first argument is the node that matched the query. We call it node.

The second argument is of type RuleContext, which contains useful information. We call it ctx.

ctx.filePath
Section titled “ctx.filePath”

Type: string

The absolute path of the file being linted.

ctx.sourceType
Section titled “ctx.sourceType”

Type: JsFileSource

Information about how the file was parsed, such as whether it’s JavaScript or TypeScript, whether it’s a module or a script, and whether the code is embedded in another file, such as an Astro, Vue, or Svelte component.

ctx.model
Section titled “ctx.model”

Type: SemanticModel

Bindings and references in the original analyzed source. Only available when the query passes { semantic: true }.

SemanticModel.binding
Section titled “SemanticModel.binding”

Type: (reference: AnyJsIdentifierReference) => Binding | undefined

Resolves an identifier use to the binding it refers to, respecting shadowing. Returns undefined for configured globals and unresolved references.

SemanticModel.asBinding
Section titled “SemanticModel.asBinding”

Type: (node: AnyJsIdentifierBinding) => Binding | undefined

Looks up the binding introduced by a declaration’s identifier node. Returns undefined when the model does not track that declaration.

SemanticModel.allBindings
Section titled “SemanticModel.allBindings”

Type: () => readonly Binding[]

Returns all tracked bindings in the source, including nested scopes. Declarations with the same name can introduce separate bindings.

SemanticModel.allExportedBindings
Section titled “SemanticModel.allExportedBindings”

Type: () => readonly Binding[]

Returns the bindings marked as exported by the model, with each binding appearing once even if it has multiple export sites. Order is unspecified. Re-exports that introduce no local binding are not included.

SemanticModel.hasExports
Section titled “SemanticModel.hasExports”

Type: () => boolean

Returns whether the model tracks at least one exported binding. This is not a check for export syntax: an empty export, a re-export without a local binding, or an exported literal can leave this value false.

SemanticModel.scopes
Section titled “SemanticModel.scopes”

Type: () => readonly Scope[]

Returns all scopes in this source, including the global scope and nested scopes.

SemanticModel.globalScope
Section titled “SemanticModel.globalScope”

Type: () => Scope

Returns the outermost scope of this source, including for an empty file. This scope has no parent. It is unrelated to the global references returned by allGlobalReferences().

SemanticModel.scope
Section titled “SemanticModel.scope”

Type: (node: AnyJsAstNode) => Scope | undefined

Returns the most specific scope containing the node’s trimmed source range. Returns undefined for an empty node. Use globalScope() to obtain a scope for an empty file.

SemanticModel.scopeHoistedTo
Section titled “SemanticModel.scopeHoistedTo”

Type: (node: AnyJsAstNode) => Scope | undefined

Returns the scope a declaration’s identifier was hoisted to, if the model records one. This can differ from the scope containing its source text.

SemanticModel.allGlobalReferences
Section titled “SemanticModel.allGlobalReferences”

Type: () => readonly GlobalReference[]

Returns references resolved to globals configured in the supplied model. Locally shadowed names resolve to local bindings instead.

SemanticModel.allUnresolvedReferences
Section titled “SemanticModel.allUnresolvedReferences”

Type: () => readonly UnresolvedReference[]

Returns references that resolve to neither a local binding nor a global configured in the supplied model.

SemanticModel.isGlobalReference
Section titled “SemanticModel.isGlobalReference”

Type: (reference: AnyJsIdentifierReference) => boolean

Returns whether an identifier use resolves to a configured global. Returns false for local bindings and unresolved references.

SemanticModel.isUnresolvedReference
Section titled “SemanticModel.isUnresolvedReference”

Type: (reference: AnyJsIdentifierReference) => boolean

Returns whether an identifier use has no local binding or configured global. A reference to a declaration later in the source can still resolve.

SemanticModel.isImported
Section titled “SemanticModel.isImported”

Type: (node: AnyJsIdentifierBinding | AnyJsIdentifierReference) => boolean

Returns whether a declaration is imported, or a reference resolves to an imported declaration. Returns false when a reference has no local binding.

SemanticModel.isExported
Section titled “SemanticModel.isExported”

Type: (node: AnyJsIdentifierBinding | AnyJsIdentifierReference) => boolean

Returns whether a declaration is exported, or a reference resolves to an exported declaration. Returns false when a reference has no local binding.

Binding.syntax
Section titled “Binding.syntax”

Type: () => AnyJsIdentifierBinding

Returns the identifier node introducing this binding, rather than the enclosing declaration statement. The node can be used in diagnostics and fixes.

Binding.declarationKind
Section titled “Binding.declarationKind”

Type: () => "class" | "enum" | "function" | "generic" | "hoistedValue" | "import" | "importType" | "interface" | "module" | "namespace" | "type" | "unknown" | "using" | "value"

Returns the model’s declaration classification, such as "function", "importType", or "hoistedValue". This describes how the binding was declared, rather than the syntax kind of its identifier node.

Binding.exports
Section titled “Binding.exports”

Type: () => readonly (AnyJsIdentifierBinding | AnyJsIdentifierReference)[]

Returns the identifier nodes at this binding’s tracked export sites. A directly exported declaration yields its identifier binding; an export specifier yields the local identifier reference, not
its exported alias. Returns an empty array for a binding with no tracked export sites.

Binding.exportRanges
Section titled “Binding.exportRanges”

Type: () => readonly { readonly start: number; readonly end: number }[]

Returns the model’s source ranges for this binding’s export sites. Offsets count UTF-8 bytes, with an inclusive start and exclusive end; they are not JavaScript string indices. Returns an empty array when no export sites are tracked.

Binding.scope
Section titled “Binding.scope”

Type: () => Scope

Returns the scope containing the declaration’s identifier in the source. For hoisted declarations, use ctx.model.scopeHoistedTo(binding.syntax()) to inspect the destination scope instead.

Binding.allReferences
Section titled “Binding.allReferences”

Type: () => readonly Reference[]

Returns all references that resolve to this binding, including reads and writes. References to a different binding with the same name are excluded.

Binding.allReads
Section titled “Binding.allReads”

Type: () => readonly Reference[]

Returns references classified as reads by the semantic model.

Binding.allWrites
Section titled “Binding.allWrites”

Type: () => readonly Reference[]

Returns references classified as writes by the semantic model.

Binding.isImported
Section titled “Binding.isImported”

Type: () => boolean

Returns whether this binding was declared by an import.

Binding.isExported
Section titled “Binding.isExported”

Type: () => boolean

Returns whether this binding is exported from the source.

Reference.syntax
Section titled “Reference.syntax”

Type: () => AnyJsIdentifierReference

Returns the identifier node at the reference site. The node can be used in diagnostics and fixes.

Reference.binding
Section titled “Reference.binding”

Type: () => Binding | undefined

Returns the binding this reference resolves to.

Reference.scope
Section titled “Reference.scope”

Type: () => Scope

Returns the scope containing this identifier use, which can differ from the scope containing its declaration.

Reference.isRead
Section titled “Reference.isRead”

Type: () => boolean

Returns whether the model classifies this reference as a read.

Reference.isWrite
Section titled “Reference.isWrite”

Type: () => boolean

Returns whether the model classifies this reference as a write.

Scope.syntax
Section titled “Scope.syntax”

Type: () => AnyJsAstNode

Returns the syntax node associated with this scope, such as a module, function, or block. The node can be used in diagnostics and fixes.

Scope.isGlobalScope
Section titled “Scope.isGlobalScope”

Returns whether this is the source’s outermost scope.

Scope.parent

Scope.children

Kind sets
Section titled “Kind sets”

A common operation in lint rules is checking the kind of a syntax node or token. Sometimes, you want to check for multiple kinds at a time.

1

if (node.kind === "JS_CALL_EXPRESSION" || node.kind === "JS_NEW_EXPRESSION") { ... }

However, there is a performance cost when you check this way. It results in multiple string comparisons. To avoid most of this cost, we provide these “kind sets” APIs that can check for any number of kinds in constant time.

Build each set once at module scope, then reuse it in every run() call:

plugin.ts

1

import { ast, defineRule, nodeKinds, registerDiagnostic, tokenKinds } from "@biomejs/runtime/plugin"

2

3

const CALLS = nodeKinds("JS_CALL_EXPRESSION", "JS_NEW_EXPRESSION");

4

const LOOSE_EQUALITY = tokenKinds("EQ2", "NEQ");

5

6

export const kindSets = defineRule({

7

query: ast("JS_EXPRESSION_STATEMENT"),

8

run(statement, ctx) {

9

const expression = statement.expression;

10

if (!expression) return;

11

if (CALLS.has(expression)) {

12

registerDiagnostic(expression, "information", `${expression.kind} is in CALLS.`)

13

}

14

for (const element of expression.childrenWithTokens()) {

15

if (LOOSE_EQUALITY.has(element)) {

16

registerDiagnostic(expression, "warning", `${element.text} is in LOOSE_EQUALITY.`)

17

}

18

}

19

}

20

})

nodeKinds
Section titled “nodeKinds”

Type: <K extends keyof JsNodeByKind>(...kinds: K[]) => NodeKindSet<K>

Creates a set of node kinds. It accepts the same names as ast, such as "JS_CALL_EXPRESSION". Pass each kind as a separate argument, not as an array. nodeKinds() with no arguments returns an empty set, which matches nothing.

It throws a TypeError for an unknown name or a token kind. For a token kind, the message names the function to use instead:

1

nodeKinds() received the token kind "IDENT", but it only accepts node kinds. Create a set of token kinds with tokenKinds("IDENT") instead.

tokenKinds
Section titled “tokenKinds”

Type: <K extends JsAstToken["kind"]>(...kinds: K[]) => TokenKindSet<K>

Creates a set of token kinds. It accepts any name that token.kind can return, such as "IDENT" or "LET_KW". This includes "EOF", "ERROR_TOKEN", and trivia kinds such as "WHITESPACE" and "COMMENT".

Like nodeKinds, it throws a TypeError if a name is unknown or is a node kind.

NodeKindSet.has
Section titled “NodeKindSet.has”

Type: (element: JsAstElement | undefined) => boolean

Returns whether element is a node whose kind is in the set. It returns false for tokens and for undefined, so you can pass optional fields and the results of childrenWithTokens() directly.

It throws a TypeError for anything that isn’t a node, a token, or undefined. That includes kind strings and null, so CALLS.has("JS_CALL_EXPRESSION") throws.

In TypeScript, a true result narrows element to the node types in the set. After CALLS.has(element), element is a JsCallExpression | JsNewExpression.

TokenKindSet.has
Section titled “TokenKindSet.has”

Type: (element: JsAstElement | undefined) => boolean

Returns whether element is a token whose kind is in the set. It returns false for nodes and for undefined, and throws a TypeError for anything else.

In TypeScript, a true result narrows element to a token with one of the set’s kinds. After LOOSE_EQUALITY.has(element), element.kind is "EQ2" | "NEQ".

NodeKindSet.union
Section titled “NodeKindSet.union”

Type: (other: NodeKindSet) => NodeKindSet

Returns a new set with the kinds of both sets. Neither set changes, so you can share a base set and extend it in several places:

plugin.ts

1

import { nodeKinds } from "@biomejs/runtime/plugin"

2

3

const CALLS = nodeKinds("JS_CALL_EXPRESSION", "JS_NEW_EXPRESSION");

4

const CALLS_AND_IMPORTS = CALLS.union(nodeKinds("JS_IMPORT_CALL_EXPRESSION"));

other must be a set returned by nodeKinds(). Passing a token kind set throws a TypeError that says so:

1

set.union() received a token kind set, but this is a node kind set. Pass a set returned by nodeKinds() instead.

It also throws for a kind name, an array, or anything else that isn’t a node kind set, and when you pass zero or more than one argument. To add a single kind, wrap it in a set first, as in CALLS.union(nodeKinds("JS_IMPORT_CALL_EXPRESSION")).

In TypeScript, the result’s type has the kinds of both sets, so has() on it narrows to any of them. After CALLS_AND_IMPORTS.has(element), element is a JsCallExpression | JsNewExpression | JsImportCallExpression.

TokenKindSet.union
Section titled “TokenKindSet.union”

NodeKindSet and TokenKindSet types
Section titled “NodeKindSet and TokenKindSet types”

The two set types are separate. You can’t pass a node kind set where a token kind set is expected, or the other way around. That includes union: TypeScript rejects CALLS.union(LOOSE_EQUALITY), and it throws at runtime.

Each set’s type records exactly the kinds it was built with. nodeKinds("JS_CALL_EXPRESSION", "JS_NEW_EXPRESSION") has the type NodeKindSet<"JS_CALL_EXPRESSION" | "JS_NEW_EXPRESSION">, and you can’t assign it to a NodeKindSet with any other kinds, whether fewer, more, or a plain NodeKindSet. Traversal APIs
Section titled “Traversal APIs”

Many rules look for a few node kinds anywhere inside a node, often the whole file. You could walk the tree yourself with children(), but then every node in the file becomes a JavaScript object and goes through your code, even the ones you don’t care about.

node.descendants() and node.walk() take a node kind set and do the search inside Biome. Biome only creates JavaScript objects and calls your code for the nodes whose kind is in the set, which is much faster than a children() walk.

node.descendants
Section titled “node.descendants”

Type: <K extends keyof JsNodeByKind>(kinds: NodeKindSet<K>) => readonly JsNodeByKind[K][]

Returns a new array with the nodes inside node whose kind is in kinds, in source order. Each call creates new node objects, so calling it twice returns different objects for the same nodes.

kinds must be a set returned by nodeKinds(). A kind string, an array, or a set from tokenKinds() throws a TypeError:

1

The kinds argument to node.descendants() is not a node kind set. Create one with nodeKinds(), such as nodeKinds("JS_CALL_EXPRESSION"), and pass it instead of a kind string or array.

In TypeScript, the result has the node types in the set. root.descendants(nodeKinds("JS_CALL_EXPRESSION", "JS_NEW_EXPRESSION")) returns a readonly (JsCallExpression | JsNewExpression)[].

Trivia APIs
Section titled “Trivia APIs”

Comments, whitespace, and line breaks are called trivia: text that doesn’t affect how a program runs. In Biome, trivia is attached to individual tokens:

A token’s leading trivia is everything between the previous token’s trailing trivia and the token.

A token’s trailing trivia is everything after the token, up to but not including the next line break. Line breaks inside a block comment don’t count, so a block comment that starts on the token’s line is trailing trivia even if it spans several lines.

This means a comment on its own line is leading trivia of the token that follows it, and a comment at the end of a line is trailing trivia of the token before it:

example.js

1

// Adds two numbers.

2

export function add(a, b) {

3

return a + b; // fast path

4

}

Here, // Adds two numbers. is leading trivia of the export keyword, and // fast path is trailing trivia of the ; after a + b.

token.text never includes trivia. node.text leaves out the trivia before the node’s first token and after its last token, but keeps the trivia between its tokens. To read the trivia around a node or a token, call leadingTrivia() or trailingTrivia(). To read only the comments around a token, call leadingComments() or trailingComments().

TriviaPiece
Section titled “TriviaPiece”

A piece of trivia has three read-only properties and one method:

kind: a TriviaKind, which is one of "newline", "whitespace", "singleLineComment", or "multiLineComment".

text: the source text of the piece. Comments include their delimiters, such as //.

token: the JsAstToken whose leading or trailing trivia contains the piece.

isComment(): returns true if kind is "singleLineComment" or "multiLineComment", and false otherwise. In TypeScript, it narrows kind to those two kinds.

Comments are classified by whether they contain a line break, not by their syntax. A // comment and a block comment that fits on one line are both "singleLineComment", and only a block comment that spans several lines is a "multiLineComment".

In files with syntax errors, the text that the parser skipped isn’t included in the trivia.
