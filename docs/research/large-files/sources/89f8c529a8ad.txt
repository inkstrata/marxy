Description of changes

This addresses #23 and more-or-less solves #169 by making the event-holding data structure a double-array structure, a SpliceBuffer (effectively just a gap buffer) that allows efficient repeated splices. On the benchmark from #169, the largest samples go from taking about 55 seconds to parse to taking less than 2 seconds, a better-than-25x speedup. (And an asymptotic speedup, as I believe that family of examples goes from being approximately quadratic to approximately linear.)

Two things worth noting:

I think this is taking a different direction than the edit map @wooorm pointed to here in the discussion of Refactor to improve performance w/ push, reverse #170.

There are a lot of other array data structures in micromark that would benefit from using the SpliceBuffer - if a splicebuffer is just being used like a regular array, it has very little overhead, and using a SpliceBuffer instead of the array would have made pr Refactor to improve performance w/ push, reverse #170 unnecessary, and SpliceBuffer could be used to get rid of every place that the splice helper from micromark-util-chunked is being used. I kept the usage of SpliceBuffer here very narrow because any more pervasive change would have changed exposed types. But would a wider refactor be valuable?

Assuming this seems like a reasonable edit, should the splicebuffer data structure live in a different util package? (pacakges/micromark-util-splice-buffer)?

How, at a high level, is the edit map making the process more efficient?

Together with code in subtokenize, it’s my 2nd iteration of the “subtokenize algorithm”.

One thing that often happens in micromark/markdown-rs is that, say, it’s parsing flow (headings, thematic breaks, stuff like that). After all that is done, you can parse things inside that. The links/emphasis/etc inside headings/paragraphs. You cannot do it at the same time, it has to be after everything “above” is done.

Some things remain in the original result: the heading markers remain in the list of events.

Other things are removed/added: the links/emphasis/etc inside.

The edit map is a collection of what to add/remove and where. It collects these changes for a while. And then, finally, applies all changes.

Vec<(usize, usize, Vec<Event>)>

You can read it as a js/ts Array<{at: number, remove: number, add: Array<Event>}>: It’s the changes. What to add/remove and where!
