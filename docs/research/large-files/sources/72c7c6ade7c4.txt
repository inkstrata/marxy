I'm working on a tool that converts webpages to markdown. For very large pages, the (rendering?) performance of react-markdown becomes pretty bad. I'm not entirely sure where most time is spent (parsing / transforming / compiling / rendering), but I suppose we could speed up things further if we use virtualization.

I.e. render only things that are close to the actual viewport. This would speed things up even for very very large documents. We could render chunks using InteractionObserver, keep track of scroll position to prevent janky texts. Still, It would probably be difficult, but I think it could drastically improve performance in larger markdown documents.

Not sure if this usecase is extremely rare, and therefore not worth it, though!

Any other ideas?

Hi @joepio!

Improving performance and supporting larger documents is a goal of the community, and is something which is already actively being worked on.

@wooorm has been working on refactoring https://github.com/micromark/micromark which is the parser backing remark, to further improve performance.

If you're interested in supporting these efforts consider contributing development resources and/or sponsoring the community https://github.com/sponsors/unifiedjs or https://opencollective.com/unified

Improve rendering performance.

I take your meaning, subtle clarification on terminology.

micromark and remark do parsing (text to AST), transforming (AST to AST), and compiling (AST to text).

There are performance gains to be made in each.

Remark does not render (text to graphic/raster) though, that would be handled by a browser (for HTML) or by a framework like React, Vue, or Svelte for JS/serverside rendering.

Remark and micromark don't have much, if any control, over rendering performance.

Even if we can speed it up with factor 10, large pages will still be slow.

Right, computers have limited memory and limited CPU, there will always be a page large enough to slow the machine down. No amount of performance optimization will change that.

Use some form of virtualization. I.e. render only things that are close to the actual viewport. This would speed things up even for very very large documents. We could render chunks using InteractionObserver

Thanks for sharing the idea, though it doesn't really fit with remark or micromark for a few reasons.

remark isn't a renderer

remark is used as often, if not more often, serverside where there is no concept of a viewport

the full markdown document needs to be parsed before compiling HTML/JS output, due to features that need lookahead or look behind, like definition links https://spec.commonmark.org/0.30/#link-reference-definitions where the two parts of the link could be on opposite sides of a massive document.

ChristianMurphy

Maintainer

Thanks for the clarification.

All of the points from https://github.com/orgs/remarkjs/discussions/1027#discussioncomment-3385057 still hold.

react-markdown compiles to hyperscript, React itself still handles the rendering.

react-markdown and its sibling project react-remark can also be used server side.

Markdown still has features that require look ahead or look behind for parsing.

virtualization approach could make sense.

In some limited cases, react-markdown could be wrapped with virtualization.

It's important to be aware of the limitations/caveats though.

Virtualization relies on consistent content structure, like lists or tables. (e.g. https://github.com/bvaughn/react-window)

Markdown is not that, any content type can appear anywhere and could be any size, there isn't a good way to chunk pure commonmark.

You could diverge from commonmark, and try to break the document into section chunks. (for example building off https://github.com/jake-low/remark-sectionize)

Because that is non-standard markdown, it wouldn't live in react-markdown core, instead living in a plugin. (more information on how plugins work here: https://unifiedjs.com/learn/)

Sectioning would still have the limitation that you'd need to pre-determine the size of each section to be able to render, which could easily negate the benefit of virtualization.

That's a big if, though, we'd need metrics on where the bottlenecks are to make sure virtualization would actually help here.

Agreed.

Profiling and metrics of where the bottlenecks are in your content pipeline would be critical to determining what will actually improve performance.
