## Briefs

### budgets-2 (structure)
1. TOML: `reading/tree.ts` `child()` looks up a table header among the parent's children linearly, so ~150k `[tN]` headers in 1.5 MB is ~10^10 comparisons. Index children by key, then put a step budget on header resolution. Proof: a hostile test of ~150k headers runs in bounded CPU time and fails on base by time.
2. Outline: `outline/outline.ts` `found.push(...headingsOf(child))` throws RangeError past ~100k headings in one container, and the Outline has no cap (heading-scan has 20,000). Make the walk iterative or push without a spread, and cap entries with the shared budget; the reader sees that the Outline is capped (match heading-scan's `capped` and the desktop wording it already has). Proof: 200k headings opens, the Outline is capped, no throw; fails on base.
3. `page/clean.ts:207` `<title ...>([\s\S]*?)</title>` on raw HTML is quadratic with many unclosed `<title>`. Replace with a linear scan (or bound the search). Proof: a hostile page of many unclosed `<title>` in bounded time, and the normal title cases unchanged.
Docs: extend "Work on untrusted files" in `docs/architecture.md` with what is now bounded.

### budgets-3 (bytes in)
1. `render/punycode.ts`: `splice` is O(n^2) in label length, no RFC 3492 overflow checks, `fromCodePoint(...output)` spread, no label length cap. Cap the label (DNS labels are 63 octets; a decoded label past the cap is refused, shown as written), add the RFC overflow checks, drop the spread. Proof: a long hostile label in bounded time; an overflowing label refused; known vectors unchanged.
2. `viewer/archive-read.ts:1092,1163`: `inflate(bytes,'gzip')` unpacks a `.gz` whole before `STREAM_CAP` applies. Pass a limit to the injected `Inflate` (core side), and make both `Inflate` implementations (memory and the Tauri side, if any reaches here) honour it; the reader sees the existing stream-cap wording. Proof: a gzip bomb stops at the limit and says so.
3. `viewer/image-facts.ts:246-248`: PNG `iCCP` inflated with no size limit; JPEG ICC segments concatenated with no cap. Bound both under the existing `MAX_META_BYTES` (4 MiB) or a named ICC limit; facts past it are left out and the facts card says so rather than silently. Proof: hostile PNG and JPEG.
4. `sanitize/sanitize-html.ts`: no cap on `removed` records (1M `<x>` gives 1M) or on the writer's open stack. Cap the records (keep a count of the rest) and bound the open stack; what reaches the DOM must be unchanged for normal input. Proof: 1M removed elements in bounded memory and time, the count right; sanitiser tests unchanged.
Docs: as budgets-2, in its own paragraph (the two will merge in the same section; keep edits to separate paragraphs).

### shell-teardown (F23)
Round 14's `shell-destroy` made close, menu and open-files subscriptions return disposers that clear only if still current. What it left:
1. Opens drained by `take_pending_opens` (`shell/tauri.ts:723`) while no boot is subscribed are dropped. Keep them until a boot subscribes (or say in a comment why dropping is right, if a test shows the Rust side re-queues them).
2. `mountNativeMenu` (`menu/menu-boot.ts`) starts `watchMenuState` and a document signal that outlive a destroyed boot, which keeps calling `setMenuEnabled`. Return a disposer and call it from `app.destroy`.
3. The close guard's module-level `installed` (`close.ts:73`) is not cleared by its disposer, so a second boot cannot install its guard. Clear it in the disposer, only if still the current host.
Proof: browser or unit tests that boot, destroy, boot again and show each leftover gone; each fails on base.
