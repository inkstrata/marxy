## Briefs

### key-lookup

`readingRoot` in `apps/desktop/src/parts/reading-parts.ts` (about line 21) runs `article.querySelectorAll(PAGE)` over the whole article to find a reading page (`[data-marxy-reading]`, `[data-marxy-derived]`, a log or diff run). A Markdown page has none, so the answer is null and is recomputed every time: the `made` WeakMap in `partsOf` (`parts/cursor.ts` about 67-81) is keyed by the root that does not exist. Measured on a 195 KB Markdown page (about 10,000 nodes): about 40 calls per `j` or `k` (from `partsOf`, from `makeParts` through `readingPage`, and from `cursorReady` in `selection/view.ts` about 1099), about 38 ms of a 40-51 ms key handler; the palette calls it on every key through each command's `when()` (`parts/commands.ts` to `partsHere`, `parts/cursor.ts` about 195), 15 ms a key; the verb bar calls it on every key typed in Source.

Do: make the answer cost one scan per drawing of the article, not per call. Find every way a reading root can appear in or leave an article after the first look (a reading mounted late, "Show as", a derived view, progressive mount, a re-render, the article element reused for another document) and make sure the remembered answer cannot outlive it; `cursor.ts` already bumps a `generation` that may be the right key. If reading roots only ever sit at a known place in the article, a query scoped to that place may be simpler than a cache: prefer whichever is harder to get wrong.

Also, if it is as small as it looks: `setText` in `apps/desktop/src/source/frame.ts` (about 142) writes `node.hidden` even when unchanged, which wakes the verb bar's MutationObserver on every key in Source; write only on change.

Proof: a browser test that opens a long Markdown page (plant `fixtures/corpus/32-long-reference.md` or build one), counts calls of `querySelectorAll` with the reading-page selector while pressing `j` several times, and fails on the old count; and tests that a reading root arriving after the first look is found (each way you identified, or the existing tests that already cover it, named). Before and after: the call count per key and, as information only, the handler time (`C:\Dev\reader\work\wave1\profilers\read\b-keys.mjs` and `b-count.mjs` show how it was measured; they expect a dev server).

Not yours: `pageModalOpen`, quiet dates, find, the spine, `table-aids`.

### first-click

Two things force layout of a whole long page on ordinary actions.

1. Margin notes. `apps/desktop/src/proposals/notes-in-place.ts`: a ResizeObserver on the article and pane (about 231-237) queues `relayOut` each time the article grows, which is continuously while the typesetter sets paragraphs after open. `layOut` (about 136-187) removes every margin box, clones every footnote, appends them, then reads layout (`roomOf` about 60-66 pays the flush, 60-90 ms a call on a 10,000-node page; more reads at about 162-171). Measured on the 195 KB reference (30 footnotes): 1.1 s of the open's main-thread time, 139 ms of the first click, most of a selection release. First find out when this code runs at all: whether it is behind a proposal switch, whether it runs for a page with no footnotes, and whether it runs when there is no room for a margin. Then make it do nothing and read nothing when it has nothing to place; and when it has, read what it needs before it changes anything, change in place what moved instead of tearing down and rebuilding, and do it once per frame at most. The notes must still end up beside their references after the page's heights change (that is why the observer is there): prove that they do.

2. The verb bar. The first selection shows the bar: `showsBar` in `apps/desktop/src/selection/verb-bar.ts` (about 77-83) sets `data-marxy-verb-bar` on the pane and `data-marxy-verb-room` on the root, and `place` (about 104) then reads `host.getBoundingClientRect()`, which pays for a relayout of the whole article inside the click handler: 159 ms of a 215 ms click on the long page. Profile it first (the read-mode profiler scripts in `C:\Dev\reader\work\wave1\profilers\read\`, `c-scroll-pointer.mjs` and `lib.mjs`, show how): is the cost style recalculation of the whole tree because an attribute on the root is matched by descendant selectors, or layout because the article's box changes? Then remove the cause without changing what the reader sees: for example carry the room on the element that needs it, or as a custom property on one element, or keep the article's box unchanged when the bar appears. If nothing invisible works, stop and report the options with pictures (`shots`).

Proof: browser tests on a long page with footnotes that (a) click a paragraph and show the margin notes were not removed and re-added (a MutationObserver on their container) and that the notes sit beside their references after the page has finished setting; (b) count layout-forcing reads or style-wide invalidations on the first click by a means that works in WebKit (the suite's engine), failing on the old count. Before and after, as information: the click's handler time and the `relayOut` total across an open.

Not yours: the typesetter's own slices, the spine, `table-aids`, the reading-page lookup (another branch).

### perf-record

Nothing records what the reader feels on an ordinary long document. The evaluation measured it by hand with the scripts in `C:\Dev\reader\work\wave1\profilers\` (`read\` and `edit\`; start from `lib.mjs` in each). Turn that into one tool in the repository that anyone can run before and after a change.

`node scripts/measure-interactions.mjs` (and a root package script for it): starts the app from this tree's source over the memory shell the way `apps/desktop/scripts/shots.mjs` does (its own Vite, headless Edge through Playwright, so Chromium's `Performance.getMetrics` and Event Timing are available), plants `fixtures/corpus/32-long-reference.md` (195 KB, 30 footnotes) and a 25 KB document, and for each records:

- open: time to first content, main-thread task time until the page stops changing, the longest task, DOM nodes;
- a cursor key (`j`, twenty presses spaced so they do not queue): script and layout time per key, layout count and style-recalc count per key;
- the first click on a paragraph;
- undo after one small edit, and a one-line change on disk reloaded: task time, and how many top-level nodes of the article were replaced (a count that does not depend on the machine);
- a tab switch away and back;
- Source to Read with nothing edited.

Prefer the browser's own attributed durations and counts (`Performance.getMetrics` deltas: `TaskDuration`, `ScriptDuration`, `LayoutDuration`, `RecalcStyleDuration`, `LayoutCount`, `RecalcStyleCount`) over wall-clock time, and report the median of several repetitions. Output: a table on stdout; `--record <path>` writes one JSON record (commit, date, machine class, Edge version, the numbers); `--compare <record>` prints this run against a saved record with the change in each number. It is a measurement and never a gate: it exits non-zero only when it could not produce a number it was asked for, like `scripts/perf-harness.mjs`. It writes nothing inside the repository unless told a path. Launch time is `scripts/measure-startup.mjs`'s job: say so in the docs, do not duplicate it.

Also: a unit test for the pure parts (the record's shape, the comparison), an entry in `scripts/README.md`, and a section in `docs/testing.md` under the measurement tools saying when to run it. Then run it on your worktree (which is master's code plus your tool) and save the record to `C:\Dev\reader\work\wave1\interactions-master-17cfe661.json`: the orchestrator compares the integrated wave against it.

Expected on master, so you can tell the tool is measuring the right thing: cursor key 40-110 ms on the long page and under 10 ms on the short one; first click 166-250 ms; undo 4-5 s with the whole page replaced (about 2,700 top-level nodes); reload of one appended line 5 s with the whole page replaced; tab switch 0.5 s to show.

Not yours: fixing any of what it measures.
