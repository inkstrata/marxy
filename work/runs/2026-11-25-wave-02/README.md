## Briefs

### typeset-waste

Scope: `packages/typeset` only (source and tests). The view in `apps/desktop/src/view/rendered-view.ts` is another branch's; where the view must change to use what you add, leave it calling the old way and say in your report what the caller should do. No change in what the reader sees: every paragraph still ends up set exactly as today.

Measured on a 195 KB Markdown page (1,245 top-level blocks, about 10,000 nodes): the typesetter accounts for 2.3 s of main-thread time after open, and each idle slice costs 90-190 ms against a 24 ms budget because every layout read lays out the whole article. This piece removes the work that is pure waste; bounding what is set, and containing layout, come later and are not yours.

1. Tear-down without revert. `destroy()` calls `restoreAll()` (`packages/typeset/src/index.ts` about 983-1019), which reverts every set paragraph (three `querySelectorAll`, span unwrapping, `normalize()` each: `apply.ts` about 112-125). Three of its four callers in the view discard the page straight afterwards. Add `destroy({ discard: true })` that disconnects observers and listeners and reverts nothing. The default stays as it is (a test pins "attach then destroy leaves the article exactly as it was").
2. A pass is announced only when it moved something. The IntersectionObserver callbacks call `opts.onPass?.('visible')` unconditionally (about 843-844 and 857-858), while background batches call it only `if (moved)` (about 907). The view answers a visible pass with a grid pass over the whole article. Return whether lines moved from `setBatch` through to those callbacks, call `onPass` only when they did, and hand the callback the paragraphs that were set (an added argument the view may ignore for now), so the view can later re-pad just their blocks.
3. No read of every paragraph at open. `layout()` (about 785-811) reads `getBoundingClientRect` of every candidate in the article to find the ones in the viewport and to sort the idle queue by distance. Find the paragraphs in the viewport without measuring them all (paragraphs are in document order, so tops are monotonic: a binary search needs about a dozen reads for a thousand paragraphs), and order the queue outward from there by position in the document. The queue's order need not be identical to today's, only "nearest first" in the same sense; say what changed.
4. `killed()` calls `getComputedStyle(article)` at every step (about 544 and 754). Read it once per batch, or less, without making the kill switch slower to act than one batch.

Do not: change `void article.offsetHeight`, the slice budget, `keepPlace`, the observers' margins, or what "done" means.

Proof, by counts and not by time: tests in `packages/typeset/test` that (a) attach to an article of 200 paragraphs and of 2,000 and show the layout reads made before the first slice do not grow with the count (wrap `getBoundingClientRect` and `getClientRects` in the page and count); (b) `destroy({ discard: true })` makes no DOM mutation (a MutationObserver) and the default still restores exactly; (c) a visible pass that sets paragraphs whose heights do not change does not call `onPass`, and one that does passes the set paragraphs; (d) the existing suite passes unchanged, in particular "the chunks end with every paragraph set as one pass sets them" and the keep-place tests. Each new test fails on the old code.

### definitions-index

Scope: `packages/core/src/parse` (and `chunked.ts` there), their tests, and nothing in `apps/desktop`. This is the hard piece: a wrong answer here is a wrong document that no test yet looks for, so the proof is written first.

Today `reparseMarkdown` (`reparse.ts`) parses only the region around an edit, and falls back to the whole file whenever the previous parse holds a link-reference or footnote definition (`'a definition applies across the file'`, about line 65) or the region holds one (about 67). The reason is real: micromark decides while tokenising whether `[x]`, `[x][]` or `[a][x]` is a reference by looking the label up in `parser.defined` (`micromark-core-commonmark` `label-end.js` about 211), which is filled only by the definitions in the text being parsed (`definition.js` about 177); the footnote extension keeps its own list (`micromark-extension-gfm-footnote` `syntax.js` about 63, 93, 420), and the two are not normalised the same way; and `documentFromMdast` (`from-mdast.ts` about 49-61, 636-649) resolves a reference's target from the definitions in the tree it is given, first definition wins. Measured cost of the fallback on a 195 KB reference with 30 footnotes: a one-line reload takes 5.1 s where the same file without its definition lines takes 0.8 s.

Goal: when the edit neither touches nor creates a definition, the region parse runs with the file's definitions known to it and gives exactly what a whole parse gives. When the edit adds, removes or changes a definition (in the old region or the new), fall back to the whole file as today.

What that needs, as far as the scouting went (verify each before relying on it):

- An index of the file's definitions, taken from the previous parse: every link-reference definition and footnote definition wherever it sits (top level or inside a block quote or list item), its normalised label in the form each of micromark's lists uses, and for link definitions the target the resolver needs, in the order that makes "first wins" come out the same.
- A way to tell micromark those labels before it tokenises the region: an extension that fills `parser.defined` and the footnote list at the start of the parse, or driving `parse` / `postprocess` / the compiler directly if `mdast-util-from-markdown` allows it. Do not change `patches/micromark@4.0.2.patch` unless nothing else works, and say why if you do. If a package must become a direct dependency, it goes through `scripts/allowlists/dependencies.json`.
- The definitions handed to `documentFromMdast` for the region, so a reference in the region resolves to a definition outside it.
- The checks that decide "this edit touches a definition": the old blocks of the region (from the previous parse) and the new region (from its parse). Think about an edit that turns a paragraph into a definition or a definition into a paragraph, an edit to text directly above a definition (a definition cannot interrupt a paragraph), a definition inside a container the edit re-indents, and a reference whose label the edit changes (that one is fine: it resolves against the same set).
- `parseMarkdownChunked` (`chunked.ts`) gives up on definitions for the same reason. If the same index lets it keep slicing, do that in a second commit; if it is not natural, leave it and say so.

Order of work:

1. Read `reparse.ts`, `parse.ts` (`parseBlocksIn`), `from-mdast.ts`, `chunked.ts`, `reparse.test.ts`, `chunked.test.ts`, and the two micromark files named above in `node_modules`.
2. Extend the proof first. `reparse.test.ts` asserts that a reparse equals `parseMarkdown(after)` by JSON equality, over chained random edits on corpus files (a pool that today excludes files with definitions), on structured random documents, and on named cases; it also requires that region parses outnumber whole ones. Add pools and generators that carry definitions and footnotes (definitions at the top, the bottom, in the middle, inside block quotes and lists, duplicated labels, labels that differ only in case or whitespace, references before and after their definitions, shortcut, collapsed and full references, images, footnote references and definitions), with edits that do and do not touch them, and require the region path to be taken for most edits that do not. See these new cases fail on the old code for the right reason (whole parse taken), then make them pass.
3. Run the stress forms once before you report: `REPARSE_SEEDS=1500` for the structured test (set the variable in the shell, since the package script form does not work on Windows), and say how many cases ran and how many took the region path.
4. Keep every existing case and reason string that still applies; a test that pinned "a definition forces the whole parse" changes to pin the new rule, and its name says the rule in plain words.

Not yours: the store (it still calls the region parse only for reloads), the view, the page splice and its footnote refusal (`apps/desktop/src/render/incremental.ts`), footnote rendering. Update `docs/architecture.md` where it describes the reparse.

Report as the rules ask, and add: the exact rule you implemented for "touches a definition", every case you found where the seeded region parse differed from the whole parse and what you did about it, and anything about micromark's behaviour you had to assume rather than verify.
