## Bottom line

Most of the pain is one shape: after the first screen, the whole-page mount does work over the whole article for each
small chunk it adds, so a page's busy time grows with the square of the file. Profiles name two places. In each typesetting batch, hanging punctuation and the overflow check read the layout between writes, and each read lays out the whole mounted article: 45 s of a 155 s open. The mount itself forces a layout after each idle chunk: 33 s more, and the largest single cost on plain text. The first screen of a big Markdown file appears in
about a second; the page then stays busy for minutes on the worst shapes. It answers between tasks, but every key,
scroll and panel costs more while it is busy, and a second big file opened meanwhile takes tens of seconds. Code, CSV, JSON Lines, logs and minified JSON, which take other paths, are linear
and cheap even at 4.9 MB. So the first rows to build are the open cliff (L1 to L3), then the few interaction paths that
walk every heading or block (L4, L7, L10). The structural work the research recommends (L20 to L26: one scheduler, a
scale class at open, typesetting by distance, windowed pages, the parse in a worker, indexes for JSON, lazy derived data)
removes these classes rather than the instances. The guardrails make new features show their growth before they land.

## What the measurements show

Headless Chromium on the Mac, from this tree's source over the in-memory shell. Six catchers shared the machine with
other sessions (load average 30 to 120), so wall times ran 4 to 10 times CPU time; the verifiers re-measured in CPU or
the browser's task time, and several severities came down. The open cliff did not: it is there in CPU time.

Verified figures, in the browser's main-thread task time (CPU), unless marked as the catcher's wall time:

| --- | --- | --- |

`scripts/measure-scale.mjs` (the new tool) shows the same at small sizes: Markdown prose open grows 4.0x from 0.2 to
0.4 MB, a cursor key 2.6x.

## How comparable apps do it

No comparable app renders a 1-5 MB Markdown file as one whole, fully typeset page; that is what Marxy does below its
5 MiB lines threshold. Code editors decide once, at open, how heavy a file is and turn whole-document features down
(VS Code: 20 MB or 300,000 lines; lines over 20,000 characters not coloured). Obsidian's reading view mounts only the
blocks near the screen, and still fails on one huge block. E-book readers load one section at a time. Log, JSON and CSV
viewers build a typed-array index of offsets in the background and draw a window. All of them search the model, not the
DOM, and cap results (VS Code: 19,999 matches). WebKit, Marxy's engine on macOS, has no `scheduler.yield`, `postTask`
or stable `requestIdleCallback`, no scroll anchoring before Safari 27, and finds text skipped by `content-visibility`
only from Safari 26, while Marxy supports macOS 13: the app needs its own yield, anchoring and find. The synthesis is
`docs/research/large-files/SYNTHESIS.md`.

## Keeping it fixed

`agent/scale-guard` lands the guardrails: `check-scale` fails `pnpm check` when a file gains an unbounded spread into a
call, a DOM query or layout read in a loop, a queue operation in a loop, a whole-text line split or a run-time pattern,
unless a `// scale: <why>` comment says why the input is small (363 such shapes are recorded today, a ratchet that may
only fall); `packages/core/src/scale.test.ts` holds the parse, render, readings, line index, splice, diff and sanitiser
to linear growth in CPU time; `scripts/measure-scale.mjs` measures the browser build per shape, size and action;
`docs/big-files.md`, a rule in `AGENTS.md`, the `big-files` skill and a Claude Code hook put the rules in front of an
agent at the moment it edits the app. One lesson from building it: timed by the wall clock on this loaded Mac, the
sanitiser's linear growth read as quadratic; in CPU time it read 1.0. Guardrails count work; they do not time it.

## What was not checked

WebKit (every number is Chromium), the real window, Windows, memory; notebooks, archives, office documents and books
at size; Markdown shapes other than prose at 2 MB and above. L27 is the row for the first three.
